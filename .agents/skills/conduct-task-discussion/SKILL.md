# タスクを議論し独立レビューする

## 目的

利用者が前提知識を推測せずに判断できる形でTaskを進め、現在の成果物がIssue #1と直接の後続Issueに矛盾しないかを、独立した別サブエージェントの証拠付きレビューで確認する。現在の成果物を後続へ渡せることと、後続Issueの全依存が揃って実際に着手できることは別に判定する。

ここで「直接の後続Issue」とは、現在のTaskの成果物を着手条件または入力として明記している次段階のIssueを指す。Issue番号が現在のIssueより大きいという理由だけでは後続に分類しない。

## 用語と前提知識

- Task Issue（実行対象の課題）: GitHub上で管理する、独立した完了条件を持つ最小の作業単位である。議論と変更の範囲を限定するために必要である。
- Issue #1（要求の原典）: このプロジェクトで実現する利用者要求を記録したGitHub Issueである。個別Taskの成果物が、元の目的から外れていないか確認するために必要である。
- 固定Planning snapshot（計画固定版）: Taskの分割、依存関係、担当範囲を特定のGit Commit時点で固定した計画である。作業中に計画が変わっても、開始時に従った条件を再現できるようにするために必要である。
- Task Map（作業構成表）: 大分類から実行単位までのTask、担当成果物、依存関係をまとめた現在の計画である。固定版からの正式な変更と、現在のTaskの位置を確認するために必要である。
- 接続台帳: 成果物を作るTaskと、その成果物を入力として使うTaskの対応表である。現在のTaskから直接の後続Issueを漏れなく逆引きするために必要である。
- 決定記録: 利用者が承認した変更内容、理由、影響範囲を履歴として残す文書である。固定版より後の変更が正式承認済みかを判別するために必要である。
- 計画中の項目: 後続Issue、Task Map、接続台帳などに記載され、今後のTaskで詳細を決める予定の要件、設計、実装内容である。未確定であっても、既存の決定との矛盾や重複を早期に見つけるためレビュー対象にする。
- worktree（分離作業ディレクトリ）: 一つのGitリポジトリからTask専用の作業場所を分ける仕組みである。他Taskの未完了変更を混ぜないために必要である。
- branch（変更履歴の作業系列）とHEAD（その系列の現在位置）: どのTask用の履歴で、どのCommitまでを含むかを識別する値である。別Taskや誤った起点で作業する事故を防ぐために必要である。
- Gate（次工程へ進む前の確認条件）: 設計確定など、後続作業を始める前に満たす必要がある条件である。未確定の前提に基づく実装を防ぐために必要である。
- 成果物Owner（変更責任の所在）: 各Taskが作成・変更してよいファイルや設計領域の担当である。並行Task同士の競合と責任の混在を防ぐために必要である。
- 非阻害差異: Issue、計画、作業セッションなどの記載が一致しないものの、正本、正しい値、影響範囲を証拠から特定でき、現在Taskの成果物の妥当性を変えない差異である。Owner外の同期漏れだけで現在Task全体を止めないために区別する。
- Commit（Gitへ変更履歴として保存する操作）とstaging（次のCommit候補として変更を一時登録する操作）: 成果物を履歴へ確定する段階を区別する語である。利用者の承認前に変更を確定または確定準備しないために区別する。

## 必須の併用スキル

作業開始時に `$explain-with-context` の `SKILL.md` を全文読み、次のすべてへ適用する。

- 利用者への途中報告と最終回答
- 利用者へ判断を求める質問
- 仕様書、設計書、データ構造、変数、属性、列挙値などの成果物
- `.codex/task-session.local.md` の質問・回答・判断記録

英語名や専門用語だけを提示せず、その場で日本語の意味、必要な理由、該当条件、似た項目との違いを説明する。Commitは、利用者が明示的に承認するまで行わない。

## メインエージェントとサブエージェントの役割

サブエージェントを利用できる場合、Taskの一次資料調査、整合確認、成果物の作成・修正、Task固有の検証を、実行担当サブエージェントへ委任する。メインエージェントは次の統括作業だけを担当し、同じ調査や成果物編集を重複して行わない。

- 利用者との対話、途中報告、設計判断が必要な質問の提示
- Taskの目的、参照すべき一次資料、Owner境界、禁止操作、Commit承認状態を実行担当へ伝えること
- サブエージェント間の書込み範囲と担当の重複を防ぐこと
- 実行担当の報告と独立レビュー結果を照合し、`revise`への対応を指示すること
- 最終結果、未解決事項、検証結果、Commitの有無を利用者へ報告すること

実行担当には、結論だけでなく、確認した一次資料、変更箇所、実行した検証、残課題を証拠付きで報告させる。共有ファイルシステム上で作業するため、Owner Path外を変更しないこと、他担当が編集中のファイルを変更しないこと、利用者の明示承認前にstaging・Commit・pushを行わないことを依頼時に明記する。

利用者の判断が必要な未確定事項を実行担当が見つけた場合、実行担当は推測で確定せずメインエージェントへ返す。メインエージェントは `$explain-with-context` の質問手順に従って利用者へ確認し、回答と採用理由を実行担当へ渡す。

実行担当と独立レビュー担当は別のサブエージェントにする。成果物を作成・修正したサブエージェントへ、その成果物の独立レビューを兼任させない。

サブエージェントを利用できない場合、メインエージェントが黙って調査・実装を代行しない。利用できない理由、未実施の作業、完了条件への影響を利用者へ報告し、続行方法の指示を求める。

## 開始時の確認

実行担当サブエージェントへ次の確認を依頼し、根拠とともに報告させる。

1. `.codex/task-session.local.md`、現在のTask Issue、固定Planning snapshotを読む。
2. 現在のbranch、HEAD、依存Task、Gate、成果物Owner、書込み可能なPathを照合する。
3. Issue #1を読み、現在のTaskが満たすべき利用者要求、用語、状態、受け入れ条件を抽出する。
4. Issueの依存関係、固定Planning snapshotと現在のTask Map、`docs/task-connections.md`（成果物を作るTaskと利用するTaskの接続台帳）から直接の後続Issueを特定し、後続が現在の成果物へ期待する入力と開始条件を抽出する。
5. Issueが特定の決定記録を参照している場合は、その記録も読み、承認済みの変更理由と影響範囲を確認する。
6. Issue、Planning snapshot、作業セッションの差異を見つけた場合は、勝手に意味を追加せずメインエージェントへ報告し、後述の「差異を止めずに扱う」に従う。

Issue #1、後続Issue、固定Planning snapshotの取得方法が分からない場合も、推測で代用しない。リポジトリ内の対応資料やGitHub Issueを読み取り、確認できなければ未確認と明記する。

固定Planning snapshotの作成後に、利用者が変更を正式承認している場合は、次の優先規則を使う。

1. 後発の承認記録について、置き換える固定Planning snapshotの項目、承認日、承認内容、影響するTaskを特定する。
2. 証拠を特定できた項目だけは後発の承認内容を現在正式に適用される条件として扱い、それ以外は固定Planning snapshotを維持する。
3. 置換関係を作業セッションと成果物へ明記する。固定Planning snapshotの過去内容は履歴として消さない。
4. 承認記録を特定できない差異は独自解釈で解消しない。現在Taskの成果物へ影響しない範囲は続行し、影響する判断だけを未確定として利用者へ確認する。
5. 新しいPlanning snapshotの作成とIssueへの同期にCommitが必要な場合は、Commit前の成果物不備とは区別し、利用者のCommit承認後に行う最終手順として記録する。

この優先規則は、作業開始時にどの条件が正式に適用されているかを特定するための規則であり、設計上どちらが妥当かを無条件に決める規則ではない。過去の決定、現在の成果物、計画中の項目は、作成時期や承認状態だけを理由に正しいものとして固定せず、独立レビューで目的と根拠を再評価する。

## 差異を止めずに扱う

依存関係、Gate、成果物Owner、Issue本文、Task Map、接続台帳、作業セッションに差異があっても、差異の存在だけを理由に現在Task全体を停止しない。

1. 固定Planning snapshot、固定後の承認済み決定記録、現在のTask Mapと接続台帳、Git上の成果物Evidenceを照合し、正本、正しい値、影響範囲を特定する。
2. 正本と正しい値を特定でき、現在Taskの着手条件、Owner境界、成果物の妥当性を変えない差異は「非阻害差異」とする。誤っている資料、正しい値、根拠、後続への影響を作業セッションへ記録し、正本に従って作業を続ける。
3. 非阻害差異がOwner外のIssueや計画同期にある場合、外部更新の承認がなくても現在Taskを続ける。同期修正は後続の引継ぎ事項として残し、現在Taskの完了条件にはしない。
4. 正本または正しい値を一意に特定できない差異は、影響する判断だけを未確定として利用者へ確認する。調査、説明補強、検証など、その判断に依存しない作業は続ける。
5. 差異が現在Taskの成果物へ実害を与える場合はOwner境界内で修正する。Owner外の変更は承認なく行わないが、未承認であることだけを理由にOwner内の修正と検証を止めない。

## 議論と実行

1. 実行担当は、現在のTaskで確定済みの内容、未確定の内容、今回変更できる範囲を分ける。
2. 実行担当は、資料から安全に確定できる内容を質問せず進める。
3. 利用者の判断が必要な場合、実行担当は判断材料をメインエージェントへ返す。メインエージェントは、`$explain-with-context` が定める前提知識、未確定事項、質問理由、選択肢の影響、判断基準、推奨、質問本文を省略せず、会話と `.codex/task-session.local.md` の両方へ記録する。
4. メインエージェントは利用者の回答を実行担当へ伝える。実行担当は、採用した設計、その理由、影響する成果物へ反映し、質問履歴を消さない。
5. 実行担当は、成果物をOwner境界内で作成または変更し、Task固有の検証を実行する。
6. 実行担当は、Task範囲外の矛盾を承認なく変更せず、対象Ownerと次に必要な対応をメインエージェントへ報告する。正本と正しい値を特定できる場合は非阻害差異として記録し、Owner内の作業を続ける。

## 独立レビュー

利用者へ完了を返す前、かつCommit前に、実行担当とは別の最低1つのサブエージェントへ読取り専用のレビューを依頼する。レビュー担当へファイル、GitHub Issue、Gitの履歴や登録状態を変更させない。実行担当やメインエージェントの結論、期待する答えを渡さず、現在のTask Issue、Issue #1、直接の後続Issue、固定Planning snapshot、現在のTask Mapと接続台帳、Issueが参照する決定記録、変更成果物、`.codex/task-session.local.md`、現在のbranch・HEAD・`git status`・差分という元資料を渡す。

レビューでは、少なくとも次を確認させる。

- Issue #1の要求、用語、状態、受け入れ条件との矛盾または欠落
- 直接の後続Issueが必要とする契約、入力、依存関係、開始条件との矛盾または引継ぎ漏れ
- 現在のTask Issueと固定Planning snapshotのOwner、範囲、依存関係、Gateとの整合
- 成果物内の説明不足、型・制約・分類条件・必要理由の欠落、内部矛盾
- Task固有の受け入れ条件と検証結果の不足
- 未承認Commit、範囲外変更、次のIssueへ判断を先送りした未解決事項の有無
- 後続Issueごとの成果物受渡し可否と、他の依存Taskを含む現在の着手可否の混同
- 過去の決定、現在の成果物、計画中の項目の間にある矛盾、重複、または現在では不要になった項目

レビュー担当には、過去・現在・将来のどれかを時系列だけで正しいと仮定させない。矛盾または不要点を見つけた場合は、次の順序で妥当な対応先を判定させる。

1. 対立する各項目について、目的、決定理由、根拠、前提条件、影響範囲を並べる。
2. Issue #1の利用者要求、現在も有効な制約、後続全体の整合性、重複の回避、実装と運用の単純さを基準に比較する。
3. 過去に承認済みであること、現在の成果物に存在すること、将来のTaskに記載されていることのいずれも、単独では妥当性の根拠にしない。
4. 過去または現在の項目が妥当なら、計画中の項目を修正・削除する方向を示す。計画中の項目が妥当なら、過去の決定または現在の成果物を見直す方向を示す。
5. 根拠が不足して一方を選べない場合は、無理に新旧の優先順位を付けず、必要な判断材料と利用者へ確認すべき事項を示す。
6. 妥当な対応が現在のTaskとOwner境界内なら `revise` として修正させる。境界外の資料または承認済み決定の変更が必要なら、変更対象、Owner、必要な承認、放置した場合の影響を示す。正本と正しい値を特定でき、現在成果物の妥当性を変えない場合は非阻害差異として引き継ぎ、現在Taskを続ける。

レビュー結果は次のいずれかで分類し、根拠となるIssue、ファイル、該当箇所を示させる。

- `verified`（問題なし）: 根拠を確認でき、修正が不要である。
- `revise`（修正が必要）: 根拠比較の結果、現在のTaskの範囲内で直す必要がある。範囲外の変更が必要な場合は、修正対象とOwnerを明示して利用者判断へ送る。
- `reject`（指摘を採用しない）: 指摘は元資料と一致せず、採用しない理由を説明できる。

現在のTaskとOwner境界内で対応できる `revise` が一つでもあれば成果物を修正し、修正箇所を明かしたうえで再レビューを依頼する。境界外または承認済み決定の見直しを求める `revise` は、対象を勝手に変更しない。正本と正しい値を特定でき、現在成果物の妥当性を変えないものは非阻害差異として引き継ぎ、完了を妨げない。現在の成果物の妥当性に影響するOwner内の `revise` が解決するまで完了扱いにしない。サブエージェントを利用できない場合はレビュー済みと主張せず、その事実を利用者へ伝えて作業を完了扱いにしない。

## 完了条件

次をすべて満たした場合だけ、Commit直前まで完了したと報告する。

- Task固有の成果物と検証が完了している。
- Issue #1、現在のTask Issue、固定Planning snapshot、直接の後続Issueの差異について、正本、正しい値、影響範囲を説明できる。後発の正式承認がある差異は置き換えた項目と承認記録を、非阻害差異は誤った資料と後続の同期事項を追跡できる。
- 独立レビューで、現在の成果物の妥当性に影響する未解決の `revise` が残っていない。
- 後続Issueが開始時に必要とする確定事項と証拠が明記されている。
- 直接の後続Issueごとに、今回の成果物を渡せるかと、全依存を含めて現在着手できるかを分けて記録している。
- 未回答の質問がない。ある場合は、前提から質問本文までを会話と作業セッションへ明記している。
- 利用者がCommitを承認していない限り、Commitもstagingも行っていない。

最終回答では、変更した成果物、実行した検証、独立レビューの結論、未解決事項、Commitの有無を端的に伝える。
