# 候補検索・索引のライフサイクル要件と正本設計確認基準

## 1. 目的と対象

本書は、保存済みの知識から比較・評価の対象になり得る記録を探す**候補検索**と、その検索を速くするために正本から作る**索引**について、技術製品に依存しない要件を定める。ここでいう正本は、主張、根拠、関係、改訂履歴、操作履歴を正しい記録として保存する領域である。索引は正本を複写又は変換して検索を速くする派生データであり、正本そのもの、利用者の知識状態、検索結果の真偽ではない。

この区別は、索引が壊れた又は古い場合でも正本と履歴を失わずに再構築できるようにするために必要である。また、候補が見つかったこと、見つからなかったこと、順位が高いことを、主張の正しさ、利用者本人が知っていること、矛盾の成立と取り違えないためにも必要である。

対象は、L1で公開済みの八つの検索・取得操作が必要とする候補取得、更新後の索引整合、正本からの再構築、障害時の安全な読取り・復旧、および正本永続化設計を確認する基準である。特定のデータベース、検索製品、埋め込みモデル、類似度計算式、順位しきい値、同期方式、物理索引構造、運用コマンドは決めない。これらを先に固定すると、後続の技術選定と詳細設計の責任を奪い、同じ要求を満たす技術比較ができなくなるためである。

## 2. 用語と責務の境界

| 用語 | 意味 | 必要な理由と、指さないもの |
| --- | --- | --- |
| 正本 | 主張、根拠、関係、改訂、操作の事実を、来歴を失わずに保存する基準記録。 | 索引の欠落・破損時に復元の出発点を一意にするため必要である。検索用の複製、画面表示、呼出し元の一時データを指さない。 |
| 派生索引 | 正本の検索可能な内容から作る、候補を効率よく選ぶためのデータ。 | 正本を直接全走査せず検索できるようにするため必要である。真偽、既知性、矛盾、採否の結論を保存する領域ではない。 |
| 候補 | 指定条件に対応する可能性があるとして検索が返す保存済み主張又は関係付き主張。 | 後続が原文、根拠、適用範囲、時点を比較する入口を得るため必要である。候補だけで正しい、同一、矛盾している、利用者が知っているとは決めない。 |
| 正本変更境界 | 一つの更新操作が、競合確認を通過して正本の変更事実として確定した範囲。 | 索引が何を反映すべきかを、通信要求の受付時点や途中失敗と混同せず決めるため必要である。未確定の要求や表示時刻ではない。 |
| 索引世代 | 同じ索引定義・入力範囲に対して、再構築又は更新により作られた一まとまりの索引データ。 | 作成途中の索引を読取りへ公開せず、旧世代から安全に切り替えるため必要である。正本の改訂版や公開CLI契約の版とは別である。 |
| 索引鮮度 | 読取りに使う索引世代が、どの正本変更境界までを反映済みかを示す状態。 | 検索結果がどの正本時点に対応するかを追跡し、古い候補を最新と誤認しないため必要である。検索要求を受けた時刻や候補の順位値ではない。 |
| 再構築 | 正本を読み直して、既存の派生索引に依存せず索引世代を作り直す処理。 | 索引の破損、定義変更、同期失敗から回復できるようにするため必要である。正本や履歴を削除して作り直すことではない。 |
| 検索結果時点 | 一つの集合検索と継続取得で同じ候補集合・順序を解釈する基準時点。 | ページをまたいだ重複・欠落を防ぐため必要である。索引鮮度の代替ではなく、集合取得契約が定める読取り上の基準である。 |

Codex又は利用者は、候補の採否、意味的同一性、矛盾の成立、時点上の正しさ、更新操作を判断する。CLIと検索基盤は、公開契約に従う入力を検証し、正本に存在する記録から候補と取得事実を決定的に返し、更新に付随する索引整合を保つ。検索基盤が意味判断を行うと、順位又は類似度を根拠比較なしの結論へすり替えるため、この責務分離を守る。

## 3. 検索・取得に必要な能力

各能力は「何を候補として取得できなければならないか」を表す。物理索引の種類、検索回数、上位件数、類似度の計算は指定しない。L4-M2-S1の探索要求とL3-M2-S2の既存知識比較要求が、同じ候補を異なる判断目的で必要とするため、能力ごとに候補の意味と取得後に必要な情報を固定する。

| 能力 | 必要な候補・取得事実 | 必要な理由 | 禁止する読み替え |
| --- | --- | --- | --- |
| 文字列候補検索 | 文字列、API名、識別子に対応する主張候補。 | 表記どおりに現れる既存知識を調べ、検索用表現の基本経路を提供するため。 | 一致しないことを保存知識全体の不存在又は新規命題としない。 |
| 意味候補検索 | 入力文と意味が近い可能性がある主張候補。 | 言い換えや表記揺れで既存命題を見逃さず、比較対象を集めるため。 | 近さ、順位値、又は上位表示を意味的同一性・既知性・真偽としない。 |
| 概念候補検索 | 指定した検索用索引語に対応する主張候補。 | 概念、別名、固有名詞から関連する主張を探すため。 | 索引語そのものを主張又は利用者の知識として扱わない。 |
| 関係候補検索 | 指定主張から、関係種別と向きを保って到達する相手側主張候補。 | 関連、前提、因果、寄与、置換、矛盾候補を辿り、比較に必要な文脈を取得するため。 | 到達した関係だけから因果、優先、矛盾の成立を判断しない。 |
| 矛盾候補検索 | 同じ又は重なる適用範囲で両立しない可能性がある主張候補。 | 訂正・競合の可能性を、根拠と条件を比較する対象として見つけるため。 | 候補ヒットを矛盾成立、どちらかの偽、更新操作の決定としない。 |
| 時点・製品版候補検索 | 指定主張と時点又は製品版が異なる可能性がある主張候補。 | 古い情報、改訂、製品版差を比較し、時間差を矛盾と混同しないため。 | 時点差だけを訂正、矛盾、現在無効としない。 |
| 主張の詳細取得 | 主張の現在又は指定改訂版、来歴、必要時の履歴参照。 | 検索順位だけでは本文、適用範囲、時点、改訂履歴を比較できないため。 | 現在版を指定改訂版へ、又は履歴参照を現在内容へ暗黙に置換しない。 |
| 根拠の詳細取得 | 主張に結び付く根拠、出典・観測内容、改訂版、結び付き。 | 候補が何に基づくかを検証し、根拠不足を真偽や未知へ誤分類しないため。 | 根拠がないことを主張の偽又は利用者の未知としない。 |

すべての候補検索は、L1の集合取得契約に従い、同一の正規化済み条件と検索結果時点では安定した順序、重複しない候補、継続取得可能な結果を返す。検索方式間の順位値は比較できず、履歴・根拠の取得結果へ検索順位値を付けない。これは、異なる検索手段の数値を一つの品質尺度と誤認せず、ページをまたぐ候補比較を再現可能にするためである。

`search-text`、`search-semantic`、`search-concept`、`search-contradictions`、`search-temporal`に対応する五つの候補検索では、`scope`（適用範囲。主張がどの技術分野、プログラミング言語、対象製品について成り立つかを絞る公開条件）を任意で指定できなければならない。指定した場合は、その同じ適用範囲を候補母集団の選択、順位付け前の絞込み、継続取得、再試行で維持する。省略は「認可済み記録を意味上の適用範囲で追加絞込みしない」ことを表し、空の適用範囲を「すべての範囲で成立する」という主張へ読み替えてはならない。

関係候補検索は、既存の公開入力である`relation_kinds`（対象にする関係種別）と`direction`（起点から出る関係、起点へ入る関係、又は両方を選ぶ関係の向き）によって候補範囲を定め、`scope`を追加してはならない。関係候補検索へ未承認の条件を足すと、L1が固定した公開入力と検索ごとの候補範囲契約を変更するためである。五つの検索で`scope`を索引構築時に失う、又は後続ページで別条件へ変えると、同じ公開操作でもどの範囲から候補を選んだか再現できず、候補の欠落又は混入を比較判断へ持ち込む。

## 4. 正本と索引の整合要件

### 4.1 正本を唯一の判断基準にする

1. 検索が返す候補は、読取り時に正本で存在確認できる主張を指さなければならない。索引だけに残る削除済み又は無効な参照を候補として確定表示してはならない。派生データの遅れ又は破損で、存在しない記録を比較対象へ渡さないためである。
2. 候補の詳細、根拠、関係、現在版又は指定改訂版は正本から取得する。索引に保存した要約又は順位値を、根拠原文、来歴、現在の状態の代わりにしてはならない。索引は探索を速くするためのものであり、検証可能な事実を保持する責任を持たないためである。
3. 正本の主張、根拠、関係、改訂、適用範囲、時点・製品版、来歴のいずれかが候補選択又は詳細取得に影響する場合、その変更は索引が追跡可能な正本変更境界に含める。本文だけを追跡すると、関係・根拠・時点の変更後に古い候補経路を返すためである。
4. 検索結果が正本と照合できない場合、照合できない候補を成功結果へ混ぜない。要求の成否と回復方法は公開エラー契約及び後続の詳細設計が定めるが、候補不足を意味上の空集合として偽装してはならない。空集合と索引・正本の不整合を区別するためである。

### 4.2 更新の可観測性と鮮度

更新操作は、正本変更と、変更後に必要な索引反映を一つの整合単位として扱う。ここで「即時反映」は、特定の同期方式又は時間上限を先取りする言葉ではない。少なくとも次の状態を区別し、読取り側と運用側が正本との対応を判断できることを要求する。

| 状態 | 意味 | 許可すること | 禁止することと必要な理由 |
| --- | --- | --- | --- |
| `current`（現行） | 読取りに使う索引世代が、対象検索で必要な正本変更境界まで反映済みである。 | 正本との対応範囲を明示して候補検索を行う。 | 反映範囲を示さず「最新」と表示しない。正本時点を判断できなくなるため。 |
| `lagging`（遅れ） | 正本変更は確定したが、読取りに使う索引世代が必要な変更境界へまだ追随していない。 | 後続設計が定める安全な待機、再試行、又は鮮度情報付きの読取りを行う。 | 遅れを正常な空集合又は正本不存在として返さない。候補の欠落理由を隠すため。 |
| `building`（構築中） | 新しい索引世代を正本から作成しているが、読取りに公開していない。 | 既存の検証済み世代を継続利用するか、後続設計が定める回復経路へ移る。 | 未完成世代を混在させて候補集合を返さない。ページ境界と候補の再現性を壊すため。 |
| `unavailable`（利用不可） | 正本との対応を確認できず、安全な候補検索を提供できない。 | 障害として報告し、再構築又は復旧の対象にする。 | 索引内容を正本確認なしに候補として返さない。古い又は壊れた情報を結論へ渡すため。 |

状態は派生索引の利用可否と正本反映範囲を表す。利用者の知識状態、主張の真偽、更新操作の成否、CLIの終了コードを表す列挙ではない。異なる分類軸を一つの状態値へ混ぜると、復旧の必要性と意味判断を区別できなくなる。

検索応答又はその内部の読取り記録は、少なくとも使用した索引世代を識別でき、正本変更境界との対応を検証可能にしなければならない。外部JSONの項目名・型・公開有無はL1のSchemaと後続のCLI詳細設計が定める。本書が意味上の追跡を要求するのは、継続取得、障害診断、再構築後の検証で、どの正本を基準に候補が選ばれたかを失わないためである。

## 5. 索引ライフサイクルと再構築

### 5.1 作成・切替・廃止の不変条件

1. 索引世代は、作成対象の正本変更境界、索引定義の識別、作成結果を追跡できなければならない。索引定義には、候補選択の意味へ影響する方式又はモデルの版を含める。これがなければ、同じ検索要求で候補が変わった理由を、正本変更と索引定義変更から区別できない。
2. 新しい世代は、必要な正本範囲を読み終え、整合確認に通過するまで読取りに公開してはならない。構築途中の一部データを公開すると、同じ検索条件でも実行順序により候補が欠落するためである。
3. 世代の切替は、読取り単位で旧世代又は新世代のいずれか一方を使う。単一の集合検索又はその継続ページで両世代を混ぜてはならない。候補の順序、重複排除、継続トークンの意味を維持するためである。
4. 旧世代は、新世代の公開と必要な確認が終わるまで廃棄しない。失敗した構築や切替から、安全な既知状態へ戻る選択肢を残すためである。ただし、旧世代が正本を代替する保存先になることは許可しない。
5. 再構築は正本だけを入力として完了できなければならない。既存索引、検索ログ、順位値、利用者の一時的判断を必須入力にしてはならない。派生データの障害そのものから回復できなくなるためである。

### 5.2 再構築で検証する内容

再構築後は、少なくとも次の確認を行う。具体的な件数、ハッシュ、比較アルゴリズム、運用の実行手順は後続Taskが技術に応じて定める。

| 確認対象 | 確認する事実 | 必要な理由 |
| --- | --- | --- |
| 入力範囲 | 新世代が対象とする正本変更境界と、読み取った主張・根拠・関係・改訂の範囲が一致する。 | 途中までの正本から「現行」索引を作らないため。 |
| 参照整合 | 索引から候補として参照する識別子が正本に存在し、対象種別と改訂・関係の対応が崩れていない。 | 壊れた参照又は別種別の記録を候補として返さないため。 |
| 検索意味 | 八つの検索・取得能力が必要とする、文字列、意味、概念、関係、矛盾候補、時点候補、主張、根拠への到達を失わない。 | 再構築を高速化だけの成功とせず、後続の比較・評価が必要な入口を保つため。 |
| 適用範囲の保持 | 正本にある技術分野、プログラミング言語、対象製品の適用範囲を、再構築後も`scope`公開条件の同じ絞込み意味で使える。 | 同じ検索要求でも候補母集団が変わり、範囲外の候補混入又は範囲内候補の欠落を検出できなくなるため。 |
| 集合の安定性 | 同じ正規化済み条件と検索結果時点で、重複しない候補、安定順序、継続取得の規則を維持する。 | 世代切替・再構築でページの重複又は欠落を生まないため。 |
| 正本照合 | 候補詳細と根拠取得が正本から検証でき、索引の要約だけへ依存しない。 | 索引の古さや破損を意味判断の根拠へ持ち込まないため。 |
| 失敗時の安全性 | 検証不能な新世代を公開せず、既存の安全な世代又は利用不可状態へ戻せる。 | 不完全な再構築を成功結果や空集合として見せないため。 |

### 5.3 障害回復の境界

索引の生成・更新・検証に失敗した場合、正本に確定済みの記録、改訂履歴、根拠、操作履歴を削除・巻戻し・推測補完してはならない。索引障害は派生データの障害であり、正本の事実を消す理由にはならないためである。反対に、正本変更が確定していない段階で索引だけを現行として公開してもならない。索引が指す事実を正本から検証できないためである。

復旧処理は、失敗した世代、対象正本変更境界、失敗分類、最後に安全と確認できた世代を追跡できるようにする。これにより、後続の運用実装が再試行、再構築、世代切替、利用不可の通知を区別できる。再試行回数、待機時間、再起動、利用者への表示、公開コマンド名は本書で定めない。これらはCLIのエラー契約、ワークフロー、Index Lifecycle詳細設計の責務である。

## 6. 正本永続化設計の確認基準（Review Gate）

この確認基準は、永続化技術の採否又は物理Schemaの具体形を決めるものではない。L2-M1-S1からS3が、選んだ正本設計が検索・再構築・障害回復を可能にすることを、技術に依存しない問いで確認するための入力である。各項目を満たせない設計は、検索製品を後から追加しても正本から正しく復元できないため、Gateを通過させない。

| 確認基準 | 合格に必要な証拠 | 不合格となる例 | 必要な理由 |
| --- | --- | --- | --- |
| 正本の網羅性 | 主張、根拠、関係、改訂、適用範囲、時点・製品版、来歴、更新操作の確定事実を、索引外の正本として取得できる設計。 | 索引にしか本文・根拠・関係がなく、正本だけから候補詳細を復元できない。 | 索引障害後も検証可能な記録を失わずに再構築するため。 |
| 安定した識別と参照 | 主張、根拠、関係、改訂、操作を一意に識別し、索引参照を正本へ照合できる設計。 | 表示順又は検索順位を記録識別子として使い、再構築後に同じ対象へ戻れない。 | 候補、根拠、履歴、関係を別の記録へ取り違えないため。 |
| 改訂・来歴の保持 | 現在版だけでなく、必要な過去改訂と置換・訂正の関係を取得できる設計。 | 更新で旧内容を物理削除し、時点検索又は根拠比較ができない。 | 時点差、訂正、置換を矛盾又は同一性と誤判定しないため。 |
| 原子的な正本変更境界 | 一更新操作について、競合確認済みの正本変更と、それが索引へ反映されるべき範囲を追跡できる設計。 | 途中変更の一部だけを成功とし、どこまで索引が追随すべきか分からない。 | 鮮度・再試行・復旧を、要求受付時刻ではなく確定事実に結び付けるため。 |
| 正本の列挙と差分取得 | 指定した正本変更境界までの全対象を列挙でき、二つの境界間の追加・改訂・関係・根拠の差分を取得できる設計。 | 全件を不安定な順序でしか読めず、更新後に何を索引へ反映すべきか判定できない。 | 初回構築と増分反映を同じ正本根拠で実現し、再構築との差を検証するため。 |
| 検索に必要な意味の保持 | 文字列、意味入力、概念、関係、矛盾候補、時点候補、主張・根拠取得に必要な正本情報を失わない設計。 | 主張本文だけを保存し、概念、関係の向き、適用範囲、時点、根拠へ到達できない。 | L3の既存知識比較とL4の知識探索が必要とする候補・比較材料を提供するため。 |
| 適用範囲による候補選択 | `search-text`、`search-semantic`、`search-concept`、`search-contradictions`、`search-temporal`に対応する五つの候補検索で、任意の`scope`公開条件を正本の技術分野、プログラミング言語、対象製品の適用範囲へ同じ意味で適用し、再構築後も同じ条件から候補母集団を再現できる設計。関係候補検索は`relation_kinds`と`direction`だけで範囲を選び、`scope`を追加しない。 | `scope`を索引だけの補助値として保存し、正本から復元できない、又はページ継続時に適用範囲が変わる。関係候補検索へ未承認の`scope`を追加する。 | 範囲を絞った検索で候補の混入・欠落を防ぎ、L1の公開検索条件と派生索引の再構築を一致させるため。検索ごとに承認済みの入力だけを保つため。 |
| 派生データからの独立 | 索引を消去又は隔離しても、正本と正本変更境界から新しい索引世代を作れる設計。 | 現行索引、検索ログ、キャッシュがなければ再構築入力を取得できない。 | 索引の障害を正本の障害へ拡大しないため。 |
| 安全な公開と復旧 | 構築途中又は検証失敗の索引世代を読取りへ公開せず、安全な世代又は利用不可を識別できる設計。 | 新旧世代を同一ページへ混ぜ、失敗時に空集合として成功応答を返す。 | 候補の重複・欠落と、検索失敗の意味上の誤分類を防ぐため。 |
| 版の追跡 | 索引定義、検索意味に影響するモデル又は変換、正本変更境界、索引世代の対応を追跡できる設計。 | 正本が同じなのに候補が変わった理由を、方式変更とデータ変更から区別できない。 | 再構築結果の説明、互換性判断、障害切り分けを可能にするため。 |
| 公開境界の維持 | 索引作成、再構築、世代切替、ID発行、履歴削除を、L1の12公開業務コマンドへ追加しない設計。 | 利用者が単独で再構築又は索引切替を呼び、不整合な途中状態を作れる。 | 既存の公開契約と内部整合責務を保ち、運用制御を後続Ownerへ残すため。 |

Gateを通過するためには、各基準に対し「採用した設計箇所」「満たす事実」「検証方法又は未解決点」を対応付ける。単に利用する製品名、性能値、又は将来実装予定を記すだけでは証拠にならない。特に、差分取得、構築途中の非公開、世代切替、再構築入力、正本照合は、技術選定後に初めて具体化できても、この段階で満たすべき意味として確認する。

## 8. 入力・範囲外・完全性確認

本書は、L1の公開コマンド・集合取得・正本論理モデル、L3-M2-S2の既存知識比較要求、L4-M2-S1の技術非依存探索要求を入力としている。L3入力からは、文字列・意味・概念・関係・矛盾候補・時点候補と、主張・根拠取得、検索結果が結論ではない境界を採用した。L4入力からは、探索範囲・段階・局所停止理由を失わず候補と取得事実を渡す必要を採用した。

次は本書の範囲外であり、未決定の漏れではない。

- 検索製品、データベース、埋め込みモデル、類似度計算、順位しきい値、上位件数、物理索引構造はL2-M2-S2以降が決める。技術非依存要件へ製品選定を混ぜないためである。
- 正本の物理Schema、Transaction、Repository、差分取得Portの具体APIはL2-M1-S1からS3が決める。本書はそれらが満たすべき意味上の確認基準だけを定めるためである。
- 索引世代の具体状態機械、同期順序、障害回復手順、CLIへの接続、運用実装はL2-M2-S4、L2-M2-S10、L2-M3-S7が決める。本書で具体手順を固定すると、技術選定前に実装設計を重複させるためである。
- 再試行回数、待機時間、予算、ワークフロー全体の停止・再開はL5の責務である。検索の遅れ又は利用不可を、利用者本人の知識状態や意味比較の結果へ変換しないためである。

完全性確認として、八つの公開検索・取得操作に必要な候補・取得能力を第3章へ一件ずつ対応付けた。第4章では正本照合と鮮度を、第五章では世代、再構築、障害時の安全性を、第6章ではL2-M1が確認すべき正本設計の基準を定めた。これにより、検索を高速化する派生データと、根拠・履歴を保持する正本の責務を混同せず、正本だけから再構築できることを後続が検証できる。
