# CLI公開コマンド台帳

## 1. この文書の目的と適用範囲

この文書は、知識基盤を操作するCLI（コマンドライン・インターフェース。端末から文字列で命令を渡す操作窓口）について、外部の呼出し元が直接使える**公開コマンド**を定める台帳である。台帳を先に固定する理由は、後続のJSON Schema（JSONで渡すデータの形式）、エラーと終了コード、集合取得規則、永続化実装が、別々の名前や責務を前提にしてしまうことを防ぐためである。

本書の対象は、Issue #1 が必要とする8個の検索・取得操作と4個の更新操作の、コマンド名、呼出し経路、論理的な入力項目、操作の意味、公開処理と内部処理の境界である。本書はJSONの厳密な構造、エラー番号、終了コード、複数件の並び順・ページ分割、互換性番号を決めない。それらは、それぞれ `L1-M2-S4`、`L1-M2-S3`、`L1-M2-S2`、`L1-M2-S5` が決める必要があるためである。

「論理的な入力項目」とは、呼出し元が何を指定しなければならないかを表す意味上の項目であり、JSON上のキー名や型の表現そのものではない。後続Taskは本書の項目名と条件を変更せず、機械可読な表現だけを具体化する。

## 2. 用語

| 用語 | 意味 | 必要な理由 |
| --- | --- | --- |
| CLI | 端末から実行するプログラムの操作窓口。 | Codexが判断した検索条件や更新内容を、決定的に保存・取得する境界を明確にするため。 |
| 公開コマンド | Codexまたは利用者が直接指定して実行できる操作。 | 利用者が呼ぶ操作と、実装が自動で行う処理を区別するため。 |
| 内部処理 | 公開コマンドの実行中にCLIまたは永続化層が自動で行う処理。 | インデックス更新や識別子採番を、操作のたびに手動で呼ばせないため。 |
| assertion（主張） | 根拠と来歴を伴って保存する、検証可能な知識内容。 | 検索・取得・更新の主対象を一貫して示すため。 |
| evidence（根拠） | 主張を支える出典、観測、引用などの記録。 | 主張だけを保存して根拠を失わないようにするため。 |
| relation（関係） | 主張同士の関連、矛盾候補、後継関係などを表す記録。 | 関連検索と置換履歴を追跡可能にするため。 |
| 識別子 | assertion、evidence、relation、revisionを一意に指す値。 | 既存記録を誤らず取得・更新するため。 |
| revision（改訂版） | 同じ記録の特定時点の保存済み内容。 | 更新後にも以前の内容を参照・検証できるようにするため。 |
| operation_id（操作識別子） | 更新要求を呼出し元が一意に識別する値。 | 通信失敗後の再送を重複更新にせず、同じ要求として判定するため。 |
| expected revision（期待改訂版） | 更新時に「この版を読んだ上で変更する」と指定する改訂版。 | 他者の変更を見落として上書きする競合を防ぐため。 |

## 3. 共通の呼出し契約

### 3.1 構文と入出力経路

すべての業務コマンドは、次の構文で呼び出す。

```text
knowledge <command> --input -
```

- `knowledge` は知識基盤CLIの論理的な実行名である。実際の配布方法や実行ファイル名を固定するものではないが、後続設計が同じ呼出し対象を参照するために用いる。
- `<command>` は第4章に列挙する公開操作名である。表にない文字列を公開操作として追加してはならない。Issue #1の操作集合とCLIの責務を一致させるためである。
- `--input -` は、標準入力（呼出し元からCLIへ渡すバイト列の経路）から、ちょうど1件の構造化要求を受け取ることを示す。検索語、根拠、更新内容をシェルの位置引数へ分散させず、一つの要求として検証するために必須とする。
- 構造化要求の表現はJSONとする。ただし、JSONオブジェクトの外形、各値の厳密な型、出力の外形は `L1-M2-S4` が定義する。本書で示す項目は、そのSchemaに必ず対応させる論理契約である。
- 正常な業務結果は標準出力へ出す。診断メッセージは標準エラー出力を使う。成功・失敗のJSON表現、終了コード、診断文の契約は `L1-M2-S3` が定める。この分担により、呼出し方を先に確定しつつ、失敗時の機械判定を一貫させる。

本書が許可するのは上記の業務要求経路だけである。位置引数、未定義のフラグ、要求JSONを直接コマンド行へ埋め込む経路、任意ファイルを入力として読む経路は公開契約に含めない。引用符、文字コード、ファイルの読取権限による環境差を業務意味へ持ち込まないためである。ヘルプ表示、バージョン表示、配布時の起動補助は、業務コマンドの追加ではなくランタイム境界を扱う後続設計で定める。

### 3.2 共通の値の条件

「空でない文字列」は、空文字列と空白だけの文字列を受け付けない値をいう。条件や根拠が未指定のまま検索・更新されたように見えることを防ぐためである。「既存識別子」は、保存済みの対象を一意に指す識別子をいう。見つからない場合や対象種別が異なる場合の扱いはエラー契約に委ねるが、別の記録へ読み替えてはならない。

`scope` は、Scope（命題またはrelationが成立する意味的な適用範囲）による任意フィルターである。Scopeは `facets`（適用範囲を一件ずつ表す要素）からなり、各要素は技術分野、プログラミング言語、対象製品のいずれかとその値を表す。異なる種類の要素はすべて満たす条件、同じ種類の複数値はそのいずれかを満たす条件として解釈する。同じ文字列でも対象製品や言語が違えば別の意味になり得るため、この規則で検索の文脈を限定する。

`scope` を省略した場合は、認可済みの記録を意味的な適用範囲で追加フィルターしない。空のScopeは「全範囲に成立する」ではなく「追加の適用範囲を観測していない」を表す。この二つを区別しないと、検索条件を指定しないことと、保存済み主張が全ての技術分野・言語・製品に当てはまるという強い結論を混同するためである。認可は、呼出し主体が記録を閲覧できるかを決める別の実行時境界であり、本Taskが定める`scope`入力値ではない。

複数値の項目は、同じ意味の値を重複させず、空の要素を含めない。これにより、同じ根拠や関係を二重に登録する要求を検出できる。時刻は比較可能な時点、製品版は比較対象として意味を持つ版を表す値である。具体的な文字列表現はSchemaの責務である。

### 3.3 取得結果と集合結果

単一の対象を取得するコマンドは、対象が存在する場合にその内容、識別子、改訂版、来歴を返す必要がある。複数候補を返すコマンドは集合結果を返すが、並び順、件数上限、継続取得用のカーソル、総数の表現は `L1-M2-S2` が決定する。本書でそれらを仮決めしないのは、各検索コマンドが異なるページ操作を持つことを防ぎ、利用者が同じ集合操作として扱えるようにするためである。

どの検索結果も「候補」であって、CLIが真偽、既知性、矛盾の成立、時点上の正しさを判定したものではない。意味判断はCodexまたは利用者の責務であり、CLIは指定条件に対応する保存済み記録を決定的に取得する。類似している、矛盾しそうである、時点が異なるという取得条件を、真であるという結論にすり替えないためである。

## 4. 公開コマンド一覧

| 分類 | コマンド | 操作の要点 | 結果の種類 |
| --- | --- | --- | --- |
| 検索・取得 | `search-text` | 文字列、API名、識別子を含む主張を探す。 | 主張候補の集合 |
| 検索・取得 | `search-semantic` | 入力文に意味的に近い主張を候補として探す。 | 主張候補の集合 |
| 検索・取得 | `search-concept` | 指定した概念を含む主張を探す。 | 主張候補の集合 |
| 検索・取得 | `search-related` | 指定主張と関係記録で結ばれた主張を探す。 | 関係付き主張候補の集合 |
| 検索・取得 | `get` | 主張の現在内容または指定改訂版を得る。 | 単一主張 |
| 検索・取得 | `get-evidence` | 主張に結び付く根拠を得る。 | 根拠の集合または単一根拠 |
| 検索・取得 | `search-contradictions` | 指定主張と矛盾する可能性がある主張を探す。 | 矛盾候補の集合 |
| 検索・取得 | `search-temporal` | 指定主張と時点・製品版が異なる候補を探す。 | 時間・版の候補集合 |
| 更新 | `create` | 新しい主張、根拠、必要な関係を保存する。 | 作成済み記録と改訂版 |
| 更新 | `attach-evidence` | 既存主張へ新しい根拠を追加する。 | 更新済み主張と根拠 |
| 更新 | `revise` | 既存記録の内容を改訂し、旧版を保持する。 | 改訂済み記録と改訂版 |
| 更新 | `supersede` | 旧主張を新主張で置換し、後継関係を残す。 | 新旧主張と後継関係 |

この12個以外の公開コマンドは定義しない。とくに、`recalculate`、インデックスの作成・再構築、識別子の発行、履歴の削除・整理を公開コマンドにしてはならない。これらは第6章の内部処理であり、公開すると利用者が途中状態を作ったり、来歴を失ったりするためである。

## 5. コマンドごとの契約

### 5.0 更新コマンドに共通する判断・競合防止の入力

`create`、`attach-evidence`、`revise`、`supersede` は、各節の固有項目に加えて、次の項目を要求へ含める。更新は単なる文字列保存ではなく、どの知識を採用し、どの範囲へ影響すると判断したかを後から検証できる必要があるためである。

- `operation_id`: 必須。要求全体を一意に結び付ける操作識別子。同じ識別子で同じ内容を再送したときは、同じ論理要求として扱い、二重変更を作らない。異なる内容を同じ識別子で送ってはならない。
- `decided_by`: 必須。操作の選択、主張の同一性、根拠の採否、影響範囲を判断した主体。Codexが判断した場合に、CLIの実行主体へ置き換えてはならない。判断責任と保存処理の責任を区別するためである。
- `decision_rationale`: 必須。操作選択、同一性、根拠の採否、影響範囲を検証できる空でない説明。操作名だけ、定型文だけ、処理障害だけ、秘密値や根拠原文の無目的な複写は許可しない。CLIが未決の意味判断を推測して保存しないために必要である。
- `expected_revisions`: 項目自体は必須。今回の判断で読んだ既存記録について、記録種別、業務識別子、期待する現在改訂版を重複なく示す一覧である。`create` が既存記録を参照しない場合だけ空配列を許可する。既存記録を参照または更新する要求では空配列を許可せず、更新対象と状態公開に影響する記録を漏らしてはならない。現在値が一致しないときは古い前提の更新を成功扱いにしない。
- `affected_assertion_ids`: 必須。状態再計算または現在状態の利用停止を検討した主張識別子の重複なし一覧。影響がないと判断した場合だけ空一覧を許可する。関連主張の古い状態を見落とさないためである。

`operation_kind` はコマンド名から、`requested_at` はCLIが要求を受理した時点から、`executed_by` は確定処理を実行した主体から決定する内部記録であり、呼出し元が指定してはならない。これらを入力にすると、時点や実行者を遡及して書き換えられるためである。新規記録の業務識別子と初版はCLIが内部で割り当て、その未使用性を検証する。したがって、呼出し元は新規recordやrevisionの識別子を指定せず、`expected_revisions` には既存記録だけを入れる。

同じ `operation_id` と同じ正規化要求（順序や表記揺れを同じ意味としてそろえた要求内容）を再送した場合、CLIは初回成功時と同じ確定結果を返し、保存、索引更新、状態再計算を再実行しない。同じ操作を通信失敗後に安全に再試行できるようにするためである。同じ `operation_id` に異なる正規化要求を結び付けることは許可せず、失敗として扱う。失敗時のJSON表現、診断文、終了コードなどの詳細は `L1-M2-S3` が定める。

### 5.1 `search-text`

**目的**: 文字列、API名、識別子など、保存内容に含まれる文字列を手掛かりに主張候補を取得する。

**入力項目**:

- `text`: 必須。空でない検索文字列。検索意図のない全件取得を防ぐため、空値は許可しない。
- `scope`: 任意。Scopeによる意味的適用範囲フィルター。省略時は認可済み記録を意味的範囲で追加限定しない。空Scopeの意味と認可との違いは第3.2節に従う。

**動作と結果**: `text` に対応する主張候補の集合を返す。文字列の一致方式、順位、ページ操作は集合取得規則の責務である。候補が存在しないことは「知識が存在しない」という判断ではなく、この検索条件で取得できなかったことだけを表す。

### 5.2 `search-semantic`

**目的**: 入力文と意味が近い可能性がある主張を候補として取得し、Codexが表現の揺れを越えて調査できるようにする。

**入力項目**:

- `statement`: 必須。空でない入力文。類似性を測る対象が必要である。
- `scope`: 任意。`search-text` と同じScopeによる意味的適用範囲フィルター。

**動作と結果**: 意味的に近い主張候補の集合を返す。近さは検索の手掛かりであり、CLIは候補を既知、真、採用済みと判定しない。類似度の計算方法や閾値の表現は、本書の公開項目を増やさずに実装・Schema側で具体化する。

### 5.3 `search-concept`

**目的**: 同じ概念を扱う主張を探し、別表現で記録された知識を調査可能にする。

**入力項目**:

- `concept`: 必須。空でない概念名または概念を表す文字列。
- `scope`: 任意。Scopeによる意味的適用範囲フィルター。

**動作と結果**: `concept` に対応する主張候補の集合を返す。概念の同一性は検索上の対応であり、CLIは概念の正しさや主張の真偽を決めない。

### 5.4 `search-related`

**目的**: 指定した主張から、保存済みのrelationをたどって関連主張を取得する。

**入力項目**:

- `assertion_id`: 必須。探索の起点となる既存主張の識別子。起点なしに関連を判定しないため必須である。
- `relation_kinds`: 任意。取得する関係種別の重複なしリスト。省略時は保存済みの全関係種別を対象にする。
- `direction`: 任意。起点から出る関係、起点へ入る関係、または両方のいずれかを示す。省略時は両方とする。関係の向きを明示できなければ、原因と結果、置換元と置換先を取り違えるためである。

**動作と結果**: 指定条件に一致するrelationと、その相手側の主張候補を返す。到達可能な関係を返すだけであり、関係の妥当性を新たに推論しない。

### 5.5 `get`

**目的**: 一つの主張について、現在版または保存済みの特定改訂版を取得する。

**入力項目**:

- `assertion_id`: 必須。取得対象の既存主張の識別子。
- `revision_id`: 任意。取得する保存済み改訂版の識別子。省略時は現在版を取得する。指定時は、その主張に属する改訂版だけを許可する。
- `include_history`: 任意。主張に保持された改訂履歴の参照情報を結果に含めるかを示す真偽値。省略時は含めない。過去版への到達経路を提供しながら、通常の単一取得を不必要に大きくしないためである。

**動作と結果**: 選択された一つの主張内容、識別子、改訂版、来歴を返す。`include_history` は履歴の削除・変更を許すものではなく、保存済み履歴を参照するためだけの項目である。履歴参照情報が複数件になる場合の並び順や分割は集合取得規則に従う。

### 5.6 `get-evidence`

**目的**: 主張を支える根拠を、主張との結び付きとともに取得する。

**入力項目**:

- `assertion_id`: 必須。根拠を求める既存主張の識別子。
- `evidence_id`: 任意。特定の根拠だけを取得する既存根拠の識別子。省略時は当該主張に結び付く根拠の集合を対象にする。
- `revision_id`: 任意。`evidence_id` を指定した場合に、その根拠の保存済み改訂版を選択する。根拠と無関係な改訂版を読まないため、`evidence_id` を省略した場合は指定してはならない。

**動作と結果**: 指定根拠または根拠候補の集合を、出典・観測内容・主張との結び付き・改訂版とともに返す。根拠がないことをCLIが主張の偽と判断する根拠にはしない。

### 5.7 `search-contradictions`

**目的**: 指定主張と両立しない可能性がある主張を候補として取得し、Codexが根拠と文脈を比較できるようにする。

**入力項目**:

- `assertion_id`: 必須。比較の基準となる既存主張の識別子。
- `scope`: 任意。Scopeによる意味的適用範囲フィルター。

**動作と結果**: 矛盾する可能性がある主張候補の集合を返す。結果は矛盾候補であり、矛盾の成立、採用する主張、解決方法はCodexまたは利用者が判断する。CLIが候補検索と最終判断を混同しないためである。

### 5.8 `search-temporal`

**目的**: 指定主張と時点または製品版が異なる主張候補を取得し、古い情報と新しい情報を比較できるようにする。

**入力項目**:

- `assertion_id`: 必須。比較の基準となる既存主張の識別子。
- `as_of`: 任意。比較対象とする時点。省略時は基準主張に記録された時点を用いる。
- `product_version`: 任意。比較対象とする製品版。省略時は基準主張に記録された製品版を用いる。
- `scope`: 任意。Scopeによる意味的適用範囲フィルター。

**動作と結果**: 時点または製品版が異なる候補の集合を返す。`as_of` と `product_version` は両方指定してよく、両方省略しても基準主張の記録を比較基準にするため要求は成立する。CLIは新旧や正誤を確定せず、比較に必要な候補と記録済みの時間・版情報を返す。

### 5.9 `create`

**目的**: 新しい主張を、少なくとも一つの根拠とともに保存する。

**入力項目**:

- `operation_id`: 必須。今回の作成要求を一意に表す操作識別子。同じ値で同一内容の要求を再送した場合に、二重作成を避けるために必要である。
- `assertion`: 必須。保存する主張内容。空の主張を知識として作らないため、内容を持たなければならない。
- `evidence`: 必須。主張を支える一件以上の根拠の重複なしリスト。根拠のない主張を確定知識のように保存しないためである。
- `relations`: 任意。新主張と既存主張を結ぶ関係の重複なしリスト。関連がない場合は省略できる。

**動作と結果**: 新しい主張、根拠、指定された関係を原子的に保存し、作成された各記録の識別子と改訂版を返す。原子的とは、成功時は必要な記録がそろって保存され、失敗時は一部だけを確定保存しない性質である。識別子と初版の割当て、索引更新、状態再計算は内部処理である。

### 5.10 `attach-evidence`

**目的**: 既存主張へ追加根拠を結び付け、主張を支える証拠を増やす。

**入力項目**:

- `assertion_id`: 必須。追加先となる既存主張の識別子。
- `evidence`: 必須。追加する一件以上の根拠の重複なしリスト。

**動作と結果**: 指定主張へ根拠を追加し、必要な記録を同じ更新単位で改訂して、更新済みの主張・根拠・改訂版を返す。期待改訂版が現在値と異なる場合、CLIは古い前提での更新を成功扱いにしない。

### 5.11 `revise`

**目的**: 既存のassertion、evidence、relationの内容を改訂し、以前の版を失わずに新しい版を保存する。

**入力項目**:

- `target_kind`: 必須。`assertion`、`evidence`、`relation` のいずれか。異なる記録種別を同じ項目で曖昧に更新しないために必要である。
- `target_id`: 必須。`target_kind` に一致する既存記録の識別子。
- `replacement`: 必須。対象記録へ適用する置換後の内容。変更箇所を省略せず、改訂後の意味を明確にするために必要である。

**動作と結果**: 対象の新しい改訂版を保存し、旧版を履歴として保持して、更新済み記録と改訂版を返す。対象種別や関連整合性により必要な状態再計算・索引更新は内部処理であり、個別公開コマンドとして呼び出さない。

### 5.12 `supersede`

**目的**: 旧主張を新主張で置換し、どの新主張がどの旧主張を置き換えたかを明示的な後継relationとして保存する。

**入力項目**:

- `old_assertion_ids`: 必須。置換対象となる一件以上の既存主張識別子の重複なしリスト。
- `new_assertions`: 必須。新たに作成する一件以上の主張と、それぞれを支える一件以上の根拠の重複なしリスト。
- `supersedes_links`: 必須。`new_assertions` の各新主張と `old_assertion_ids` の旧主張を結ぶ、一件以上の後継relation指定の重複なしリスト。多対多の置換でも対応関係を失わないために必要である。

**動作と結果**: 新主張と根拠を保存し、指定対応の後継relationを作成し、旧主張を置換済みとして扱うための必要な改訂を一つの更新単位で行う。旧主張とその根拠・改訂履歴は削除しない。置換の根拠と過去の判断を後から検証できるようにするためである。

## 6. 公開処理と内部処理の境界

| 対象 | 公開か内部か | 契約 | この境界が必要な理由 |
| --- | --- | --- | --- |
| Index management（検索用索引の管理） | 内部処理 | 公開更新が正常に確定した後、必要な索引更新または再計算を自動で行う。索引を作る・削除する・再構築する公開コマンドは設けない。 | 主データだけが更新されて検索結果が古い途中状態を、利用者に作らせないため。 |
| ID management（記録識別子の管理） | 内部処理 | CLIが新規recordとrevisionの識別子を割り当て、既存記録を参照する識別子を検証する。公開の識別子発行コマンドは設けない。`operation_id` は再送識別のために呼出し元が渡す値であり、record識別子ではない。 | 未保存の識別子や衝突した識別子を、呼出し元が生成して記録の整合性を壊すことを防ぐため。 |
| history retention（履歴保持） | 内部不変条件 | `revise` と `supersede` は旧版を保持し、`get` と `get-evidence` は保存済み版を参照できる。履歴を削除・整理・改変する公開コマンドは設けない。 | 判断の根拠、更新時点、置換前の内容を失わず、後から検証可能にするため。 |
| state recalculation（状態再計算） | 内部処理 | 更新に伴う状態の再計算は、`create`、`attach-evidence`、`revise`、`supersede` の内部段階として実行する。 | 状態更新だけを切り離して呼ぶと、内容・根拠・状態の不整合を生むため。 |
| 真偽・既知性・矛盾・時間的正しさの判断 | CLIの責務外 | CLIは保存済み記録を条件に従って取得・保存・検証する。Codexまたは利用者が文脈と根拠を読んで判断する。 | 機械的な検索候補を、根拠を比較しない結論として扱わないため。 |

## 7. 後続Taskへの引継ぎ

この台帳は、後続Taskが次の範囲だけを具体化するための入力である。後続Taskはコマンド名、ここで必須・任意・条件付き必須とした論理項目、公開／内部境界を変更してはならない。変更が必要になった場合は、台帳Ownerである本Taskを起点に契約を再調整する必要がある。

| 後続Task | 受け取る内容 | 後続Taskが決める内容 |
| --- | --- | --- |
| `L1-M2-S2` | `search-text`、`search-semantic`、`search-concept`、`search-related`、`search-contradictions`、`search-temporal` の6個の `search-*` コマンドが返す候補集合、`get` が `include_history` 指定時に返す複数の履歴参照情報、`get-evidence` が根拠識別子を省略した場合に返す複数根拠。この3種類は、検索・取得8操作のうち複数要素を返し得る全ての結果である。 | 候補・履歴参照・根拠を、同じcollection（複数要素の結果）の契約として扱うための並び順、ページ分割、継続取得、件数表現。各コマンドの取得意味や入力条件は本書のままとしないと、ページ操作の違いで検索・取得結果の意味が変わるため。 |
| `L1-M2-S3` | 未入力、条件違反、対象未発見、期待改訂版不一致などの失敗条件。 | エラー分類、診断、終了コード。 |
| `L1-M2-S4` | 12コマンド、標準入力の要求経路、論理項目、結果の種類。 | JSON Schema、JSONの具体的なキー・型・成功/失敗包み。 |
| `L1-M2-S6` | Issue #1 の12操作へ対応する公開コマンドと責務境界。 | 要件からCLI契約への追跡表。 |
| `L2-M1-S3` | 更新コマンドの原子性、期待改訂版、索引・ID・状態処理が内部であること。 | Repository（永続化操作を抽象化する窓口）とTransaction（複数の永続化変更を一体として確定または取消す単位）の境界。 |

## 8. 受入条件の対応

| 受入条件 | 本書での対応 |
| --- | --- |
| CLIの全公開コマンド一覧 | 第4章に検索・取得8個、更新4個を漏れなく列挙する。 |
| コマンドごとの動作・呼出し・引数契約 | 第3章で共通呼出しを、第5章で目的、入力、条件、結果を定める。 |

| JSON Schema、エラー、集合規則との分担 | 第1章、第3章、第7章で後続Taskの決定範囲を分離する。 |
| CodexとCLIの責務分離 | 第3.3節と第6章で、CLIは候補取得・決定的保存、判断はCodexまたは利用者と定める。 |
