# 知識基盤CLI JSON Schema一覧

このディレクトリは、Codex（文章の意味を判断するAI）と知識基盤CLI（保存・取得を決定的に実行する端末プログラム）の間で、標準入力と標準出力に渡すJSONの形を機械検証する規則である。JSON Schemaは項目名、値の型、必須性、禁止する組合せを一つに固定し、呼出し側と実装側が別の形式を想定することを防ぐために必要である。

共通定義は[`cli-contract.schema.json`](./cli-contract.schema.json)に置く。各コマンドのSchemaは、この共通定義を参照して、要求、成功応答、失敗応答を定める。成功時は標準出力へJSONを1件、失敗時も可能な限り同じ経路へ失敗JSONを1件返す。失敗の終了コードと標準エラー出力の診断規則は、Schema外の[エラー契約](../errors-and-exit-codes.md)が定める。

| 公開コマンド | Schema | 必要な理由 |
| --- | --- | --- |
| `search-text`、`search-semantic`、`search-concept` | `search-*.schema.json` | 文字列・意味・概念という異なる検索起点を、同じページ取得契約で検証する。 |
| `search-related`、`search-contradictions`、`search-temporal` | `search-*.schema.json` | 既存主張を起点とする関係・矛盾候補・時間差候補の条件を曖昧にしない。 |
| `get`、`get-evidence` | `get*.schema.json` | 単一取得と、条件により複数になる履歴・根拠取得を区別する。 |
| `create`、`attach-evidence`、`revise`、`supersede` | `*.schema.json` | 更新の判断根拠、競合防止、非破壊履歴の入力を必須化する。 |

`additionalProperties: false` は、文書化されていない入力を黙って受理しない指定である。公開操作では未定義の検索条件・内部時刻・実行者を呼出し元が注入できないようにするために使用する。新規の記録・改訂版識別子、要求受理時点、実行主体はCLI内部が決めるため、要求Schemaに含めない。

## 要求・成功・失敗を別々に検証する入口

各コマンドのSchemaの最上位には、`request`、`success`、`error` の三つの入口がある。これは一つのJSONに三者を同時に入れる形式ではない。標準入力の要求、標準出力の成功、標準出力の失敗は異なる時点に発生するため、最上位の `oneOf`（複数候補のうち一つだけを許可する規則）で、三つのうち一つだけを含むJSONを検証する。要求と成功、または成功と失敗を同時に渡すことは禁止する。

* 要求を検証するときは、`{ "request": ... }` を各コマンドSchemaへ渡す。要求は検索条件又は更新判断を表し、成功結果や失敗診断を含めない。
* 成功を検証するときは、`{ "success": { "ok": true, "result": ... } }` を同じSchemaへ渡す。`result` はコマンド固有であり、検索は順位値を持つ集合、取得は単一記録又は根拠集合、更新は操作ID・確定状態・作成又は改訂記録を返す。単なる任意objectは許可しない。
* 失敗を検証するときは、`{ "error": { "ok": false, "error": ... } }` を同じSchemaへ渡す。失敗コード、再試行可否、安全な診断を必須にし、成功結果を混在させない。

各Schemaの `$ref` は、同じディレクトリの `cli-contract.schema.json#/$defs/名前` を参照する。`$defs` は共通部品を置く領域であり、個別コマンドの入力と出力で同じID、改訂版、来歴、ページ、エラー規則を別実装にせず使い回すために必要である。検証器にはこのディレクトリを同じ基底URIで読ませ、外部参照先として `cli-contract.schema.json` を解決可能にする。`$ref` の名前が `$defs` に存在しない場合は、Schemaを有効な契約として扱ってはならない。

検索集合の各要素には、保存記録ID、改訂版ID、記録種別、具体内容、由来に加えて順位値 `score` を必須にする。`search-related` だけは、候補を返した関係を単数項目にせず、関係ID・種別・方向を持つ重複なしの `relations`（関係対応一覧）へ入れる。これは、同じ候補主張に複数関係で到達しても候補を重複返却せず、各到達理由を失わないためである。`relations` は関係IDの昇順で返す。JSON Schemaの標準機能だけでは、オブジェクト配列の特定キーの重複禁止・並び順、または可変配列 `items` と `returned_count` の実際の長さの比較を表現できないため、CLI実装の追加検証でそれぞれ必須にする。この比較を省くと、同じ関係の重複、再試行時の不安定な順序、機械的な件数表示と実際の結果の不一致が起きる。

単一取得と更新成功の `record` 又は `records` の各要素も、ID・改訂版・来歴だけではなく、`record_kind`（主張、根拠、関係、派生状態のどれか）と対応する具体内容 `content` を必須にする。主張は本文、根拠は種別・内容・出典、関係は種別・接続先、派生状態は計算種別・値・計算元記録を持つ。これにより、取得・更新した対象を後続の呼出し側が内容まで機械検証でき、識別子だけから別取得を強制されない。
