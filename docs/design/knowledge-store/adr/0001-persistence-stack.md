# ADR 0001: 知識記録の正本を SQLite の関係データベースへ保存する

## 状態

採用。ここで「正本」とは、検索用の索引、キャッシュ、計算済み状態を失っても、利用者本人が示した根拠、命題、関係、改訂、操作の確定事実を復元できる基準記録をいう。この決定は `L2-M1-S1` が所有する技術選定であり、物理表の列、更新手順、移行実行器、検索索引製品、CLI の実装言語は後続Taskが決める。

## 1. 背景と決める対象

知識記録領域は、利用者本人が示した発言・コード等を採用した `Evidence`（根拠）、知識を一件ずつ判定する `KnowledgeAssertion`（命題）、検索用索引語 `Concept`、命題間の `KnowledgeRelation`（関係）、改訂履歴、根拠から計算した `DerivedKnowledgeState`（計算済み知識状態）を扱う。これらは似ていても役割が違う。とくに根拠と改訂履歴は、検索結果や計算済み状態の根拠を後から確認・再計算するために消してはならない。

このADRが選ぶ「永続化技術スタック」は、正本をどの保存方式と問合せ言語で保つか、その方式が後続の物理設計・更新設計・検索基盤に約束する制約をいう。具体的な表名・列名・索引名、個々のSQL文、接続プール、ドライバ製品名は、この段階で推測して固定しない。前者をここで固定すると、後続Taskが持つ設計責任を奪い、後者を固定しないと、正本の復元可能性と更新整合性を後から検証できないためである。

## 2. 決定

正本の保存方式として **SQLite 3 を埋込み型の関係データベースとして採用し、SQLite が実装するSQL、トランザクション、制約、版付きSQL移行ファイルを正本側の共通基盤とする。**

- SQLite はアプリケーションと同じ実行環境で一つのデータベースファイルを開く関係データベースである。常時稼働する別のデータベースサーバーを必須にしないため、ローカルCLIから正本を一貫して保存・持ち運ぶ要件に適する。
- 関係データベースは、表、行、列と、外部キー・一意制約・検査制約を使って記録間の関係を表す方式である。根拠、命題、改訂、関係、操作を別々に識別しつつ参照整合性を機械的に検査するために選ぶ。
- SQL は表の定義、制約、読取り、更新を記述する言語である。正本の物理構造、差分取得、移行を同じ保存方式の上で検証可能にするために使う。SQLを検索索引製品の問合せ言語やCLIの公開JSON形式と混同しない。
- トランザクションは、複数の変更を「すべて確定」又は「一つも確定しない」として扱う保存単位である。更新操作ID、主変更、改訂・来歴、影響する再計算待ち記録を途中で分断しないために必要である。各更新にどの行を含めるかは `L2-M1-S3` が定める。
- 物理スキーマの変更は、順序番号と内容を固定したSQL移行ファイルとして追加する。既適用の移行ファイルを編集せず、新しい移行で変更履歴を残す。これはSQLiteを採用しても、異なる版のデータベースを同じ構造だと誤認しないために必要である。適用履歴の表現と実行器は `L2-M1-S5` が所有する。

SQLiteを採用するのは、SQLite内の全文検索、ベクトル検索、埋め込みモデル、索引世代管理を採用する決定ではない。それらは正本から再構築できる派生索引の責務であり、`L2-M2-S2`以降が別に比較・決定する。SQLiteの補助機能を正本の唯一の復元経路にしてはならない。

## 3. 採用理由と満たす条件

`L2-M2-S1`の確認基準は、製品名を選ぶ基準ではなく、検索・再構築・障害回復のために正本が失ってはならない意味を定める。本決定がその基準へ与える土台を次に示す。ここでの「可能」はSQLiteだけで完了するという意味ではなく、後続の物理スキーマと保存境界が守るべき、SQLite上で実現可能な制約である。

| 確認基準 | SQLiteを選ぶ理由と、このADRの制約 | 後続で具体化する担当 | このADRだけで保証しないこと |
| --- | --- | --- | --- |
| 正本の網羅性 | 根拠、命題、関係、改訂、時点・製品版、来歴、操作を、索引とは別の表へ保存できる。索引を削除しても正本ファイルから読める形にする。 | `L2-M1-S2` | 各表・列の定義と実際の網羅性。 |
| 安定した識別と参照 | 表示順や検索順位ではなく、保存した識別子を主キー又は一意制約として保持し、外部キーで参照先を検査できる。 | `L2-M1-S2`、`L2-M1-S4` | 識別子の形式・発行方式、個々の参照制約。 |
| 改訂・来歴の保持 | 更新で旧行を単純上書き・物理削除するのではなく、現行記録と改訂・置換関係を別に保持できる。 | `L2-M1-S2`、`L2-M1-S3`、`L2-M1-S9` | 改訂表現、系譜の循環禁止、更新API。 |
| 原子的な正本変更境界 | SQLiteのトランザクションで、競合確認済みの更新、操作ID、影響範囲の記録を同じ確定単位にできる。 | `L2-M1-S3`、`L2-M1-S6`〜`S9` | 競合検出、再試行、状態再計算を含む実際の境界。 |
| 正本の列挙と差分取得 | 確定順序と更新境界を保存する表を設計すれば、指定境界までの安定列挙と二境界間の差分問合せをSQLで実装できる。 | `L2-M1-S2`、`L2-M1-S3`、`L2-M1-S10` | 境界を表す列・順序規則・Port（内部操作窓口）。 |
| 検索に必要な意味の保持 | 検索で候補を見つけた後、その候補が何の命題で、どの根拠・改訂・関係・時点・製品版に基づくかを正本から確認できるよう、意味を表す記録を索引とは別の表に保存できる。関係には、起点から相手へ向かうか、相手から起点へ戻るかを区別する**向き**も保存する。向きを失うと、前提・原因・置換など、一方向だけに意味を持つつながりを逆向きに辿ってしまう。検索順位や埋め込み値だけでは候補の正しさを説明・再評価できず、関係の向きも復元できないため、この保持が必要である。**推奨方針は、起点、相手、向きを別々の情報として保存・復元し、検索時にも同じ三要素を混同しないことである。** これにより、保存時の向きと検索時の到達方向を照合できる。表、列、値の形式、対称な関係をどのように正規化するかは物理設計であり、`L2-M1-S2` Ownerへ委ねる。 | `L2-M1-S2`、`L2-M1-S10`、`L2-M2-S3`、`L2-M2-S5` | 推奨方針を満たす関係種別・起点・相手・向きの物理表現、候補への対応付け、候補の照合方法、検索結果に出す説明。 |
| 適用範囲による候補選択 | 「適用範囲（`scope`）」とは、主張がどの技術分野、プログラミング言語、対象製品について成り立つかを絞る公開条件である。`scope`を任意で使えるのは、原典が定めた `search-text`（文字列）、`search-semantic`（意味）、`search-concept`（概念）、`search-contradictions`（矛盾候補）、`search-temporal`（時点・製品版候補）の五つだけである。SQLiteの列・制約・SQL問合せとして範囲情報を正本へ保存・絞込みできるため、この五検索では候補母集団の選択、順位付け前の絞込み、継続取得、再試行で同じ`scope`を維持できる。語句が似ていても別製品・別版にだけ当てはまる知識を返さず、再構築後も同じ候補集合を説明するために必要である。**推奨方針は、五検索で受け取った同一の`scope`条件を、候補選択の入力、継続取得、再試行へ引き渡し続けること、関係候補検索は `relation_kinds`（関係種別）と `direction`（関係の向き）だけに固定することである。** 関係候補検索には`scope`を**追加してはならない**。これを足すと固定済みの公開入力と候補範囲契約を変更し、同じ検索を再現できなくなる。`scope`の物理表現、正規化、公開CLIの値形式、候補との照合順序は、このADRでは固定せず後続Ownerへ委ねる。 | `L2-M1-S2`、`L2-M1-S10`、`L2-M2-S3`、`L2-M2-S5` | 推奨方針を満たす範囲の物理表現、五検索へ渡す条件と継続時の保持、候補と正本を照合する順序、公開CLIの指定形式。関係検索に`scope`を追加する設計は後続でも禁止する。 |
| 版の追跡 | 「版」は、同じ名称でも内容が異なり得る製品・データベース構造・検索索引・埋め込みモデル・CLI実行環境の世代を区別する情報である。正本変更境界（競合確認を通過して一更新操作が確定した範囲）、索引定義（候補の作り方を定める識別）、検索意味に影響するモデル又は変換（入力を検索可能な表現へ変える処理）、索引世代（同じ定義・入力範囲から作った一まとまりの索引）の対応を追跡しなければならない。SQLiteでは、正本が扱う製品版・時点と物理スキーマの適用状態を別々に記録し、上記対応を保存する基盤にできる。**推奨方針は、正本変更境界、索引定義、意味に影響するモデル又は変換、索引世代を、一組の対応記録として追跡することである。** これにより候補が変わった理由を、正本データの変更、検索方式の変更、索引の作り直しから区別でき、再構築結果の説明・互換性判断・障害切り分けができる。対応記録の表構造、識別子、保存時点、互換性判定の規則は、このADRでは固定せず、物理・索引・CLI設計の後続Ownerへ委ねる。 | `L2-M1-S2`、`L2-M1-S5`、`L2-M2-S4`、`L2-M3-S1` | 推奨方針を満たす各版と正本変更境界の識別形式、索引定義・モデル・変換・索引世代の対応表、互換性判定と組合せ検証。 |
| 派生データからの独立 | SQLite内外を問わず派生索引を正本とは別に管理し、索引の消去・隔離後に正本から再構築する。 | `L2-M2-S2`〜`S4`、`S10` | 索引製品、世代切替、同期・復旧手順。 |
| 安全な公開と復旧 | 正本のトランザクション確定と、派生索引の公開を別の責務に保てる。構築途中の索引を正本の代替として返さない。 | `L2-M1-S3`、`L2-M2-S4`、`S10` | 索引の公開状態機械、再試行、障害通知。 |
| 公開境界の維持 | SQLiteの接続、移行、ID発行、索引再構築は公開CLIコマンドにせず、内部の保存・運用処理に閉じ込められる。 | `L2-M1-S3`、`L2-M3` | CLIへの配線、設定、配布方法。 |

## 4. 選ばなかった方式

| 方式 | 採用しない理由 | 将来採用を検討する条件 |
| --- | --- | --- |
| PostgreSQLなどの常駐サーバー型関係データベース | 複数利用者・複数ホストの同時書込みには強いが、現時点のCLI基盤に常駐サーバー、接続資格情報、運用・バックアップ手順を必須化する。正本の論理要件だけからその運用負担を正当化できない。 | 単一ファイルでは満たせない、複数ホストからの同時更新又は集中運用が、要件として明示され、移行・運用Ownerが決まった場合。 |
| JSON、Markdown、CSVなどのファイル集合 | 人が直接読める利点はあるが、複数レコードの原子更新、参照整合性、一意性、安定した差分列挙をアプリケーション側で再実装する必要がある。正本の更新失敗で途中状態を残しやすい。 | 単なるエクスポート又は検証用Fixtureとして。正本の保存方式にはしない。 |
| 文書指向データベース | 可変形状の文書には適するが、根拠・命題・改訂・関係・操作間の参照整合性と、履歴を横断する差分取得を保存層で一貫して検査しにくい。 | 論理モデルが関係制約より独立文書の可変形状を主に要求し、同等の整合性・履歴・差分根拠を検証できる場合。 |
| 検索索引又はベクトルデータベースを正本にする | 候補検索には有用でも、検索順位・埋め込みモデル・索引世代が変わると同じ記録を安定して復元できない。索引障害後の再構築入力にもできない。 | 採用しない。検索基盤は常にSQLiteの正本から再構築できる派生物としてのみ扱う。 |

## 5. 実装へ渡す拘束条件

後続TaskはSQLiteを使うとき、次を満たさなければならない。これは詳細設計を先取りするためではなく、採用理由を実装で失わないための最低条件である。

1. **外部キー検査を接続ごとに有効にする。** 外部キーは、根拠が存在しない命題や存在しない改訂への参照を保存しない制約である。SQLiteでは接続単位の設定になり得るため、接続を作る側が常に有効化を検査する。どの表を参照するかは `L2-M1-S2` が決める。
2. **正本の整合性をアプリケーションの記憶だけに依存させない。** 一意性、参照、許可値、必要な検査は、SQLiteで表せるものを制約として定義する。文章の意味、同一性、根拠の採否はCodexが判断するため、SQLiteへ意味判断を委ねない。
3. **更新は明示的なトランザクションで確定する。** SQL文を一つずつ自動確定して、操作IDだけ、改訂だけ、再計算待ちだけが残る状態を作らない。読取りと書込みの具体的な隔離・競合処理は `L2-M1-S3` が定める。
4. **SQLiteの一書込み者という性質を前提にする。** 複数の書込みトランザクションを同時に完了できるサーバーではないため、書込み競合は競合エラー又は安全な再試行として扱い、無制限の並列更新で解決しない。待機時間、再試行回数、接続数は性能・実行基盤の設計であり、このADRでは固定しない。
5. **データベースファイルの世代と移行適用状態を検査可能にする。** アプリケーションの版、SQLiteの版、物理スキーマの版、派生索引・埋め込みモデルの版は別物である。後続は、少なくとも物理スキーマの適用状態を記録して互換性を確認する。索引・CLIの版との対応はそれぞれのOwnerが定める。
6. **正本をSQLite固有の検索拡張へ閉じ込めない。** 全文検索仮想表、ベクトル拡張、独自関数、キャッシュは採用しても派生物にとどめ、根拠本文、改訂、関係、時点・製品版、操作境界の唯一の保存先にしない。
7. **バックアップと破損検出を設計対象に含める。** 単一ファイルであることは、コピーすれば常に安全という意味ではない。稼働中のファイルを任意にコピーして整合性を仮定せず、SQLiteが整合した複製を作る手段、整合性検査、復元手順を、実行・運用を所有する後続設計で定める。

## 6. 影響とトレードオフ

SQLiteにより、正本の整合性、履歴、更新境界を一つのローカルな保存単位で扱える。一方で、分散した複数の書込み者を高頻度に受け入れる用途には適さない。その要求が現れた場合は、SQLiteを暗黙にサーバー用途へ拡張せず、正本の移行、運用、既存データの互換性、派生索引の再構築を含む新しいADRで再評価する。

実行言語のSQLiteドライバ、接続設定の詳細、ORM（表とプログラムの構造を自動対応付ける部品）の採否は未決定ではなく、本Taskの対象外である。CLI実行方式自体を `L2-M3-S1` が選定する前に特定言語やライブラリを固定すると、永続化の決定とCLI実行基盤のOwnerを混同するためである。ただし、後続の実装は第5章のSQLite互換条件を満たすドライバ又は接続部品を選ばなければならない。

## 8. 根拠、範囲外、確認結果

この決定の直接入力は、`docs/design/search-infrastructure/search-and-index-requirements.md` 第6章のReview Gate、`docs/design/knowledge-model/`の論理モデル・根拠由来状態・更新履歴の設計、`docs/design/cli-contract/errors-and-exit-codes.md`の競合・再試行・安全な途中状態の契約である。これらは、正本を索引から独立させ、改訂を消さず、更新の確定境界と差分取得を追跡することを要求する。

次はこのADRの範囲外であり、未決定の漏れではない。
