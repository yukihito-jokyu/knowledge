# Knowledge論理モデル要件トレーサビリティ

## 1. 目的

本書は、[原典Issue #1](https://github.com/yukihito-jokyu/knowledge/issues/1)のうちKnowledge論理モデルに関係する要求と、4つの設計成果物との対応を双方向に確認する。ここでいうトレーサビリティとは、要求から実現箇所へ進む「順方向」と、設計要素から根拠となる要求へ戻る「逆方向」の両方を追跡できる性質である。両方向が必要なのは、要求の実現漏れだけでなく、要求に根拠のない設計追加も検出するためである。

本書は新しいドメイン仕様、コマンド名、JSON（項目名と値で表すデータ交換形式）、データベース構造を決めない。先行4成果物が原典を満たすかを確認し、後続へ渡す論理上の条件を明示する検証成果物である。

固定入力は、計画を後から変わらない形で特定するCommit `9bf911b9122bf4ec51ec48312cc310de29bfcdff`の[固定版Task Map](https://github.com/yukihito-jokyu/knowledge/blob/9bf911b9122bf4ec51ec48312cc310de29bfcdff/docs/task-map.md)と[固定版接続台帳](https://github.com/yukihito-jokyu/knowledge/blob/9bf911b9122bf4ec51ec48312cc310de29bfcdff/docs/task-connections.md)、原典Issue #1、Issue #32が指定する設計判断記録の決定004、034から037、041である。これとは別に、直接の後続Issue #33へ渡す未確定事項の出所を照合するため、CLI公開契約の分割を承認した決定005も参照する。決定005はIssue #32の指定決定記録を追加・変更する入力ではなく、後続受渡しの根拠を再現するための読取り資料である。

SHA固定リンクとは、Branchの現在位置ではなく40文字のCommit識別値をURLに含め、後日の更新後も同じ内容を再現できる参照である。[現在のTask Map](../../task-map.md)と[現在の接続台帳](../../task-connections.md)は差異検出にだけ使い、固定入力を置き換えない。決定041は、従来の7状態へ`reported_unknown`（利用者本人が知らないと直接述べた状態）を追加し、既存7状態の意味を変えず8状態にした承認済み変更である。

## 2. 適用範囲、用語、判定方法

### 2.1 照合対象

| 略称 | 設計成果物 | 本書で照合する役割 | この役割が必要な理由 |
| --- | --- | --- | --- |
| LS | [Knowledge論理スキーマ](./logical-schema.md) | レコード、属性、許可値、必須性、レコード内不変条件 | 後続が保持すべき情報を推測しないため |
| RI | [Knowledge論理関連と参照整合性制約](./relations-and-integrity.md) | 関係種別、向き、件数、重複、循環、参照整合性 | 関連探索と根拠追跡を壊れた参照なしで行うため |
| ES | [Evidence由来Stateの整合性・導出契約](./evidence-derived-state.md) | 根拠の採用、8状態の導出、競合、再計算、論理的無効化 | 利用者の知識を推測ではなく根拠から一貫して評価するため |
| UL | [Knowledge更新操作の事前・事後条件と履歴系譜](./update-operations-and-lineage.md) | 4更新操作、再試行、不可分性、変更前後、系譜 | 訂正後も根拠と旧状態を失わず、安全に更新するため |

### 2.2 用語

| 用語 | 本書での意味 | 似た語との違いと必要な理由 |
| --- | --- | --- |
| 要求ID | 原典の一つまたは不可分な一組の要求へ、本書内で付けた安定した参照名 | GitHub Issue番号やレコードIDではない。表同士を短く確実に結ぶために必要である |
| 設計要素 | 先行成果物の章、表、属性、規則 | 実装コードや物理データベースではない。論理設計段階の充足箇所を示すために必要である |
| 完結 | 要求の意味、許可条件、禁止条件が先行4成果物で確定している | 実装済みという意味ではない。後続が意味を選び直さず実装できることを表す |
| 後続契約 | 論理モデルに必要な情報・制約は確定し、コマンド、JSON、索引等の具体表現は承認済みの後続Ownerが定義する状態 | 未決定の放置ではない。Taskの担当境界と要件漏れを区別するために必要である |
| 対象外 | 読書推奨等、論理モデルでは結果を保持・供給するだけで、最終判断を行わない要求 | 不要という意味ではない。別Ownerの要求を本Taskが上書きしないために必要である |
| 不変条件 | 作成、更新、検索の前後を問わず常に守る規則 | 通常時だけの手順と異なり、失敗・再試行時にも弱められない条件を示す |

判定は次の3種類だけを使う。

| 判定 | 許可条件 | 禁止する解釈 |
| --- | --- | --- |
| 完結 | 先行成果物内に必要な論理情報と許可・禁止条件がある | 実装やテストまで完了したとは扱わない |
| 後続契約 | 先行成果物が後続に必要な論理入力を定義し、後続Ownerが固定計画で特定されている | 具体表現が未作成という理由だけで要件欠落にしない |
| 対象外 | 原典要求は必要だが、L1-M1のKnowledge論理モデルが判断主体ではない | 原典から削除された要求とは扱わない |

「一部充足」や`TBD`（未決定）は使わない。意味上の不足があれば先行成果物Ownerへ戻す必要があり、本書だけで新仕様を補って完結扱いにしてはならないためである。今回の照合では、そのような不足は検出していない。

## 10. 後続Issue #33 `L1-M2-S1`への受渡し

Issue #33はCLIのコマンド一覧を定義する直接の後続leaf Taskである。本書を受け取れることと、Issue #33を着手できることは別である。受渡しは本成果物の確定後に可能だが、着手時には固定Task Mapと接続台帳にある全依存を改めて確認しなければならない。

公開操作とはCodexや利用者がCLIから直接呼び出せる操作、内部動作とは別の公開操作の実行中にCLI内部で自動的に行う処理である。決定005に従い、Issue #33はIndex管理（検索用索引の作成・更新・再構築）、ID管理（レコード識別値の発行・検証）、履歴保持（Revisionや変更前後を残す処理）を、公開操作にするか内部動作にするか個別に明示する必要がある。この区別が必要なのは、後続が未契約の公開入口を実装したり、必要な運用操作を内部に隠したりすることを防ぐためである。本Taskは新しいコマンドを決めない。

| 後続が本書から受け取るもの | 必要な理由 | 後続で決めてよいこと | 後続で変えてはならないこと |
| --- | --- | --- | --- |
| SR-01からSR-08の検索プリミティブと意味境界 | コマンド一覧から原典検索要件へ戻れるようにするため | コマンド名の最終表記、引数、終了状態の表現 | CLIが意味判断を行わないこと、根拠・関係・時点を取得できること |

| 8状態と`StatePublication`の区別 | 正式な知識評価と再計算中の利用不可を別応答にするため | JSON上の配置やエラー表現 | 状態の追加・統合、`reported_unknown`と`no_evidence`の混同 |
