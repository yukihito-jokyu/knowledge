# Evidence由来Stateの整合性・導出契約

## 1. 目的

本書は、[Knowledge論理スキーマ](./logical-schema.md)で定義した`Evidence`（利用者本人の知識を判断するために採用した根拠）から、`DerivedKnowledgeState`（根拠から計算した現在の知識状態）を一件導く規則を定義する。複数の根拠が一致、競合、訂正、または時点・製品版の違いを含む場合にも、8種類の`status`（知識状態の分類）を同じ意味で選び、判断に使った根拠へ戻れるようにする。

この契約が必要なのは、記事を利用者向けに調整するとき、利用者が実際に示した知識とCodexの推測を混同せず、根拠追加後に古くなった状態を再計算できるようにするためである。一般的な記事品質ではなく、利用者本人にとっての認識利得と注意コストを評価できる状態を作る。

本書の固定入力は、[原典Issue #1](https://github.com/yukihito-jokyu/knowledge/issues/1)、計画を固定したCommit（Gitによる変更履歴の保存単位）`9bf911b9122bf4ec51ec48312cc310de29bfcdff`の[作業構成表](../../task-map.md)と[作業間接続表](../../task-connections.md)、直接の先行成果物である[Knowledge論理スキーマ](./logical-schema.md)である。[設計判断記録](../../task-decomposition-decisions.md)のDecision 004、034から037も確認した。

Decision 004の承認時点では状態数が7種類だったが、Issue #1の2026年8月11日承認済み追記で`reported_unknown`（利用者本人が知らないと直接述べた状態）が追加され、既存7種類の意味を変えず8種類になった。本書はこの承認済み追記と先行スキーマに従う。この差は依存関係、Gate（後続作業を開始してよいかを判定する通過条件）、または成果物Owner（ファイルを変更する責任を持つ作業）の差ではなく、後から承認された状態数の置換である。

## 2. 適用範囲と確定状態

### 2.1 本書で確定すること

- 状態計算へ入れる根拠候補と、実際に採用する根拠の区別
- 一件または複数件の根拠から8種類の`status`を選ぶ条件
- 根拠の訂正、競合、強さ、適用範囲、時点、製品版を比較する順序
- `confidence`（選んだ状態分類の確かさ）、`evidence_ids`（実際に使った根拠の識別子）、`known_aspects`（確認できた既知部分）、`knowledge_gaps`（不足部分）、`rationale`（判断理由）へ入れる内容
- どの変更で状態を再計算し、古い計算結果を現在値として無効にするか
- Codexが文章の意味を判断する範囲と、CLI（コマンドラインから利用する機械処理）が形式を検証する範囲

### 2.2 本書で変えない確定事項

| 確定事項 | 本書で変えない理由 |
| --- | --- |
| `Evidence`が正本で、`DerivedKnowledgeState`が再計算可能な導出物であること | 原典Issue #1と先行スキーマの不変条件であり、導出結果から元の観測事実を復元する設計にはできないため |
| 8種類の`status`名と各状態の基本的な意味 | Issue #1の承認済み追記と先行スキーマで確定済みであり、本書は選択条件だけを詳細化するため |
| `stance`と`knowledge_report`が別の判断軸であること | 前者は命題の正しさへの向き、後者は利用者本人の知識についての自己申告であり、否定と「知らない」を混同しないため |
| 質問、AIの説明、情報を見た事実、根拠の不在だけでは利用者の未知または既知を決めないこと | 利用者本人の観測事実がない推測を知識状態へ混入させないため |
| Codexが意味を判断し、CLIは決められた値と不変条件を機械検証すること | 文章・コードの意味判断を、文字列一致や件数比較へ置き換えないため |
| 一つの`assertion_id`に現在状態は最大一件であること | 同じ命題へ複数の現在値を返して利用側の解釈を曖昧にしないため |

## 3. 用語と二つの責務

| 用語 | 本書での意味 | 必要な理由 |
| --- | --- | --- |
| 評価対象命題 | `DerivedKnowledgeState.assertion_id`が指す、一つの意味に分けた`KnowledgeAssertion` | 何について知っているかを、検索用語や記事全体ではなく真偽を判断できる単位へ固定するため |
| 評価文脈 | 計算時点、評価対象命題の`scope`（技術分野・プログラミング言語・対象製品などの適用範囲）と`temporal`（有効時点・適用製品版） | 同じ文でも製品版や時点が違えば知識の現在性が変わるため |
| 根拠候補集合 | 評価対象命題そのもの、または意味上関係する命題について、今回の状態を決める可能性がある全`Evidence` | 都合のよい一件だけを先に選び、反対の根拠や訂正を見落とさないため |
| 採用根拠集合 | 根拠候補集合のうち、最終状態、既知部分、不足部分、競合、または時点差を実際に判断するため使った根拠 | `evidence_ids`を、単なる検索結果一覧ではなく再評価できる追跡情報にするため |
| 直接根拠 | 評価対象命題そのもの、または意味が実質的に同じ命題について利用者本人が示した根拠 | 前提を知っていることと、対象命題自体を知っていることを区別するため |
| 関連根拠 | 構成要素、前提、矛盾する理解、過去版など、評価対象命題とは別の命題を対象にした根拠 | `partially_known`、`inferable`、`contradicted`、`outdated`を直接根拠だけでは表せないため |
| 適用可能 | 根拠の意味、適用範囲、有効時点、製品版が評価文脈と両立すること | 過去には正しかった知識や別製品の知識を現在の`known`へ混入させないため |
| 競合 | 同じ評価文脈で両立しない複数の根拠があり、訂正や適用条件によって一方を解消できない状態 | 単純な多数決で誤った状態を選ばず、`uncertain`を正しく使うため |
| 論理的無効化 | 古い`DerivedKnowledgeState`を現在値として取得させないこと | 正本の根拠を削除する物理削除や、`uncertain`への状態変更と区別するため |
| 再計算 | 根拠候補を最初から集め直し、本書の全手順で新しい状態を導くこと | 既存状態へ差分だけを足して、過去の判断ミスや競合を残さないため |

本書では次の責務を分離する。

- **Codexによる意味判断**: 命題同士が同じ意味か、根拠が構成要素・前提・矛盾・旧版のどれに当たるか、訂正が何を置き換えるか、文章やコードが状態条件を満たすかを判断する。意味を読む必要があるためである。
- **CLIによる機械検証**: 必須属性、論理型、許可された固定値、参照先の存在、配列件数、時点の前後関係、一命題一現在状態などを検証する。文章の意味を推測せず同じ入力へ同じ形式判定を返すためである。

CLIは、根拠件数、最新日時、`strength`の名前だけから`status`を自動決定しない。Codexも、CLIが検証できる参照存在や許可値の違反を意味判断で許可しない。

## 4. 根拠候補の収集と採用

### 4.1 計算開始時の入力

状態計算は少なくとも次の入力を一組として受け取る。

1. 評価対象の`KnowledgeAssertion`
2. `evaluated_at`に使う計算時点
3. 評価対象命題へ直接結び付く全`Evidence`
4. 構成要素、前提、矛盾する理解、過去版などとして今回参照する関連命題と、その全`Evidence`
5. 適用範囲、時点、製品版を比較するために必要な各レコードの`scope`と`temporal`

「全」とする理由は、新しい根拠だけ、または既存状態の`evidence_ids`だけを読むと、後から追加された反対根拠を発見できないためである。関連命題を使うのは、Codexが評価対象命題との意味上の接続を説明できる場合だけとする。単に同じ単語を含む、検索結果に近く表示された、または索引語が一致しただけでは関連根拠にしない。

### 4.2 根拠候補の分類

Codexは各候補を次のいずれか一つ以上の役割へ分類する。複数の役割を持つ場合は、どの役割で最終判断に使ったかを`rationale`へ記す。

| 役割 | 意味 | 主に導ける状態 | 採用条件 |
| --- | --- | --- | --- |
| 対象全体の直接根拠 | 評価対象命題そのもの、または実質的に同じ知識についての説明、推論、コード、判断 | `known`、`contradicted`、`uncertain` | 命題の意味と評価文脈が一致し、原文から利用者本人の理解を確認できる |
| 既知の構成要素 | 評価対象命題の真部分集合についての知識 | `partially_known` | 対象全体ではなく、どの部分を示すかを具体的に書ける |
| 導出に必要な前提 | 対象命題を導くために不足なく必要な前提知識 | `inferable` | 前提から対象へ至る意味上の導出過程を説明でき、対象自体の直接認識は観測されていない |
| 矛盾する理解 | 同じ評価文脈で評価対象命題と同時に正しいとできない理解 | `contradicted`、`uncertain` | 単なる疑問や未確認ではなく、利用者本人が反例、否定、または両立しない説明を示している |
| 本人による不知の明示申告 | `knowledge_self_report`かつ`knowledge_report=reports_unknown`で、原文にも「知らない」という直接の申告がある根拠 | `reported_unknown`、`uncertain` | 質問、説明依頼、AI出力、情報への露出、根拠不在ではない |
| 過去または別版の知識 | 主題は同じだが評価文脈と時点または製品版が一致しない知識 | `outdated`、`uncertain` | どの境界が異なるかを時点・製品版で説明できる |
| 判定力が不足する根拠 | 認識だけ、経験申告だけ、適用範囲不明、強さ不足などで他状態の十分条件を満たさない根拠 | `uncertain` | 根拠は存在するため`no_evidence`へ落とさず、不足内容を具体化する |
| 非関連 | 評価対象命題の状態を変えない根拠 | なし | 採用根拠集合と`evidence_ids`へ入れない |

`evidence_kind`は、利用者本人の何を観測した根拠かを表す。許可値は次の6種類だけであり、自由な文字列は許可しない。

| `evidence_kind` | 日本語での意味 | 似た値との違いと必要な理由 |
| --- | --- | --- |
| `explanation` | 利用者本人による仕組み、意味、条件の説明 | 前提から結論へ至る過程が主なら`reasoning`を使う。理解内容を直接確認するために必要である |
| `reasoning` | 利用者本人が示した前提から結論への推論 | 複数案から採否を決めた場合は`technical_decision`を使う。結論だけでなく導出能力を確認するために必要である |
| `code` | 利用者本人が作成・提示したコード | コードに添えた説明等を別根拠にする場合は出典範囲を分ける。知識を実際に適用した観測を残すために必要である |
| `correction` | 利用者本人による以前の説明・判断の明示的な訂正 | 単なる新しい説明ではなく、何を誤りとし何へ直したかを含む。本人との意味確認が済んだ場合は`strength=strong`とし、旧根拠を残したまま現在判断を更新するために必要である |
| `knowledge_self_report` | 知っている、知らない、認識した、経験したという本人申告 | 説明、推論、コードが主なら対応する別の値を使う。命題の正しさではなく本人の知識についての申告を分離するために必要である |
| `technical_decision` | 利用者本人が複数案を比較し、採用・却下と理由を示した技術判断 | 仕組みの説明だけなら`explanation`、選択を伴わない導出なら`reasoning`を使う。知識を意思決定へ適用した観測を残すために必要である |

`stance`は命題が正しいことへの向きであり、許可値は`supports`（支持する）、`challenges`（反証する）、`qualifies`（条件や例外で限定する）の3種類である。`knowledge_report`は利用者本人の知識に関する申告であり、許可値は`reports_known`（知っているという申告）、`reports_unknown`（知らないという申告）、`recognizes`（用語等を認識しただけ）、`reports_experience`（経験したという申告）の4種類である。

両者を分ける理由は、「この命題は誤りだ」と正しさを否定することと、「この命題を私は知らない」と知識を申告することが別の事実だからである。`knowledge_self_report`では`stance`を禁止し、それ以外の根拠では`knowledge_report`を禁止する先行スキーマの条件を変えない。

`strength`は一件の根拠が利用者本人の知識状態をどれほど明確に示すかであり、許可値は`strong`（正しい説明・推論・適用を確認できる強い根拠、または明示的で本人との意味確認が済んだ訂正）、`moderate`（知っている・知らない・経験したという明示申告等の中程度の根拠）、`weak`（用語認識等だけを確認できる弱い根拠）の3種類である。自由な数値や他の文字列は許可しない。「本人との意味確認が済んだ訂正」とは、利用者本人の原文または本人への確認結果から、以前の何を誤りとし、どの意味へ直したかを一意に説明できる訂正である。訂正らしい表現があるだけ、またはCodexが修正意図を推測しただけでは`strong`にしない。これは一件の観測の明確さを比較するために必要であり、利用者の熟達度や、最終状態分類の確かさである`confidence`とは異なる。

### 4.3 適用可能性の確認

根拠は次の順に確認する。

1. `raw_content`と出典の前後関係から、利用者本人の観測事実であることを再確認する。
2. 根拠が対象全体、構成要素、前提、矛盾、または旧版のどれに当たるかを確認する。
3. `scope`の各条件を比較する。異なる種類の条件はAND（すべて満たす）、同じ種類の複数値はOR（いずれかを満たす）として扱う。
4. `temporal.valid_from`を含み、`temporal.valid_until`を含まない有効期間と、`version_scope`を比較する。
5. 時点または製品版が異なるだけの根拠は捨てず、`outdated`候補として分離する。
6. 適用範囲または時点を観測しておらず両立を確認できない根拠は、現在有効と推定せず、判定力が不足する根拠として扱う。

空の`scope`や省略された時点情報は「すべての範囲・時点で有効」という意味ではない。情報を観測していないという意味である。ただし、時点・製品版に依存しない命題だと原文と対象命題からCodexが説明できる場合は、その理由を`rationale`へ記して適用可能と判断できる。

### 4.4 訂正、重複、件数の扱い

- `evidence_kind=correction`として採用するのは、利用者本人の原文または本人への確認結果から、何を誤りとし何へ直したかを一意に説明できる場合に限る。この明示的で本人との意味確認が済んだ訂正は、必ず`strength=strong`にする。意味が曖昧な訂正候補は`correction`の`Evidence`として採用せず、追加確認が得られるまで以前の判断を置き換えない。強い訂正と弱い推測を区別し、誤った現在状態への更新を防ぐためである。
- 一つの発言またはファイル内の同じ出典に、過去の説明・判断を直す行為と「対象命題を知らない」という本人申告が両方ある場合は、一件の`Evidence`へ混在させない。訂正部分は`evidence_kind=correction`、`strength=strong`とし、命題の正しさへの向きに応じた`stance`を持たせ、`knowledge_report`は持たせない。不知申告部分は別の`Evidence`として`evidence_kind=knowledge_self_report`、`knowledge_report=reports_unknown`、`strength=moderate`とし、`stance`は持たせない。先行スキーマの`fragment_locator`（大きな出典内で該当箇所を示す発言番号・行番号・文字範囲などの位置情報）で二つの該当範囲を分け、それぞれの`raw_content`（利用者本人が示した加工前の内容）に対応する部分を保持する。
- 訂正と不知申告を二件へ分ける理由は、前者が以前の説明・判断の内容を直す観測行為であり、後者が利用者本人の知識についての自己申告という別の観測行為だからである。`correction`の`strong`は訂正内容が明確であることを示し、自己申告の強さや対象命題を知っていることは示さない。そのため`strong`を自己申告側へ伝播させず、不知申告側は先行スキーマどおり`moderate`を保つ。
- 強い訂正が置き換えられる旧`Evidence`は、旧根拠が指す命題と訂正根拠が指す命題が同じ意味であり、両命題の`scope`（技術分野・プログラミング言語・対象製品などの適用範囲）が同一であるものに限る。文字列が似ているだけ、同じ主題だが別の構成要素である、または適用範囲が異なる旧根拠は置き換えない。同じ意味・同じ適用範囲という境界が必要なのは、別製品や別言語について正しい過去の観測を誤って無効にしないためである。
- 同じ意味・同じ`scope`でも、時点または製品版が異なる場合は、その差が訂正対象そのものかを確認する。新しい製品版についての説明というだけでは旧製品版の根拠を誤りとして置き換えず、評価文脈と異なる知識として`outdated`（同じ主題を知っているが時点・製品版が合わない状態）の判定へ残す。
- 訂正前の`Evidence`は削除、上書き、または非存在扱いにしない。訂正の判断で旧根拠を確認した場合は、旧根拠と訂正根拠の両方を採用根拠集合へ入れ、変更経緯を追跡できるようにする。
- `observed_at`が新しい、または`strength=strong`であるというだけでは古い根拠に優先しない。新しい根拠が同じ意味・同じ`scope`についての明示的な訂正または更新かを確認する。`strong`は一件の観測の明確さであって、意味・適用範囲が異なる無関係な根拠へ機械的に勝つ優先順位ではない。これは、別製品や別の構成要素の新しい根拠で過去の正しい観測を消さないためである。
- 同じ出典断片と同じ意味上の観測からできた重複候補は、一つの論理的な効力として扱う。件数を増やして`strong`へ格上げしたり、多数決の票を増やしたりしない。重複の保存・再試行方法は`L1-M1-S4`が定義する。
- 独立した複数根拠も、件数だけで強さを決めない。内容の直接性、適用範囲、時点、出典の独立性をCodexが評価する。

## 5. 競合解決と状態決定の共通手順

状態は次の順で一件に決める。途中の順序は、8状態に機械的な優先順位を付けるものではなく、見落としを防ぐ評価手順である。

1. 評価対象命題と評価文脈を固定する。
2. 第4章の根拠候補を全件集め、重複候補を一つの論理的効力へまとめる。
3. 訂正、適用範囲、時点、製品版によって解消できる見かけ上の競合を分離する。
4. 解消後も同じ評価文脈で両立しない根拠が残るか確認する。
5. 第6章の十分条件と禁止条件を満たす状態を一件選ぶ。
6. 採用根拠集合、既知部分、不足部分、判断理由を作る。
7. 状態を先に確定した後、第7章の要因から`confidence`を決める。
8. CLIが先行スキーマと本書の機械規則を検証し、違反があれば保存しない。

競合は次の規則で解決する。

- 同じ意味・同じ`scope`への明示的で本人との意味確認が済んだ`strong`な訂正は、訂正前と訂正後を追跡したうえで現在判断へ反映する。訂正後の内容が評価対象命題を支持し現在の評価文脈に合えば`known`、評価対象命題と両立しない理解を明示し未解消の支持根拠がなければ`contradicted`を検討する。訂正が別の時点・製品版にだけ当てはまる場合は、旧根拠へ機械的に勝たせず`outdated`を含む時点差の判定へ残す。これにより、訂正の強さと3状態の意味を混同しない。
- 適用範囲、時点、製品版が異なり両立できる根拠は競合ではない。現在文脈へ合わない知識は`outdated`候補にする。
- `strong`一件が常に複数の`moderate`または`weak`へ勝つとは限らず、意味または`scope`が異なる根拠には勝敗自体を付けない。`strength`は一件の明確さであり、内容の正しさ、現在性、他の主題への優先順位、または状態分類の確かさではない。
- 直接根拠は対象命題自体の認識を示す点で関連根拠より直接的だが、古い直接根拠を現在の関連根拠より無条件に優先しない。
- 両立しない現在の根拠が残り、どちらかを正当に除外できない場合は`uncertain`とする。都合のよい側だけを`evidence_ids`へ残さない。

## 6. 8種類の状態を選ぶ契約

### 6.1 状態選択表

| `status` | 日本語での意味 | 必要な十分条件 | この状態を禁止する条件 | 主な出力規則 |
| --- | --- | --- | --- | --- |
| `known` | 対象命題そのものを知っている | 現在の評価文脈に適用可能で、対象命題または実質的に同じ知識を利用者本人が正しく説明・推論・適用した`strong`な直接根拠が1件以上あり、未解消の競合がない | `reports_known`だけ、用語認識だけ、経験申告だけ、前提だけ、AI出力だけ、または適用範囲不明だけで選ばない | `evidence_ids`に直接根拠と解消に使った訂正を入れる。`known_aspects`に確認できた範囲を書き、残る不足がなければ`knowledge_gaps`は0件にできる |
| `partially_known` | 対象命題を構成する一部を知っている | 現在適用可能な根拠から、対象全体より狭い既知部分と、全体判断に足りない不足部分を各1件以上具体化できる | 既知部分または不足部分を空にする、前提を知るだけで構成部分を知ると扱う、対象全体の直接知識が十分な場合に選ぶ | `known_aspects`と`knowledge_gaps`を各1件以上にし、各項目を根拠IDと対応付けて`rationale`で説明する |
| `inferable` | 前提から導けるが対象自体を知っているとは確認していない | 現在適用可能な根拠から必要な前提が不足なく確認でき、前提から対象命題までの導出過程を説明でき、対象自体の直接認識がない | 対象自体の直接根拠がある、必要な前提が不足する、単なる関連や語句一致だけ、または自動的に`known`へ変換することを禁止する | `evidence_ids`に各前提の正本根拠を入れる。`known_aspects`に確認済み前提、`knowledge_gaps`に対象命題を直接認識・適用した観測がないことを書く |
| `contradicted` | 対象命題と両立しない理解を持っている | 現在の同じ評価文脈で、利用者本人が対象命題を反証するか、両立しない理解を持つと判断できる根拠があり、対象を支持する競合根拠が残らない | 単なる質問、不知の申告、古い版との差だけ、または支持・反証の双方が未解消の場合に選ばない | `evidence_ids`に反証または両立しない理解の根拠を入れ、何と何が両立しないかを`rationale`へ書く |
| `outdated` | 同じ主題の知識はあるが現在の時点・製品版に合わない | 利用者本人の知識を示す根拠はあるが、評価対象との相違が時点または製品版で説明でき、現在文脈に適用可能な全体知識の根拠がない | 主題自体が無関係、時点差を観測していないだけ、現在の適用可能な根拠で全体を十分に判断できる場合に選ばない | `evidence_ids`に旧知識の根拠を入れ、`known_aspects`に旧文脈で知っている内容、`knowledge_gaps`に現在文脈との差を明記する |
| `reported_unknown` | 利用者本人が対象命題を知らないと直接述べた | 採用根拠に`knowledge_self_report`かつ`knowledge_report=reports_unknown`が1件以上あり、原文が対象命題についての直接の不知申告で、これと両立しない現在の直接根拠が残らない | 質問、確認依頼、説明依頼、AI出力、情報への露出、根拠不在、`stance=challenges`だけから選ばない | `evidence_ids`に明示申告を必ず入れ、`knowledge_gaps`に申告対象を具体化する。前提や一部知識が別に確認できる場合は`known_aspects`へ残せる |
| `no_evidence` | 必要な探索後も採用できる根拠がない | 直接根拠と意味上必要な関連根拠を探索し、状態判断へ使える`Evidence`が0件である | 根拠があるが弱い、競合する、適用範囲不明、または不知申告がある場合に選ばない。レコード不在だけで探索完了とみなさない | `evidence_ids`は0件。`known_aspects`は0件にし、`knowledge_gaps`には観測不足の対象を必要に応じて書く。利用者が知らないとは書かない |
| `uncertain` | 根拠はあるが他の7状態へ確定できない | 未解消の競合、強さ不足、意味・適用範囲・時点の不明、直接根拠の不足など、採用根拠が1件以上あり確定を妨げる理由を説明できる | 根拠が0件なら`no_evidence`、明示的不知だけで競合がなければ`reported_unknown`とする | `evidence_ids`に競合する両側または不足判断へ使った全根拠を入れ、`knowledge_gaps`に確定へ必要な確認を書く |

### 6.2 同時に複数条件が見える場合

状態選択表の複数行が候補になる場合は、次の比較で一件へ絞る。

1. **未解消の競合を先に扱う**: 同じ文脈の直接根拠が両立しない場合は`uncertain`とする。例として、現在の強い説明と現在の明示的不知申告が同時に残る場合、どちらかを推測で消さない。
2. **対象全体の直接観測を区別する**: 十分な`strong`の直接根拠があれば`known`、両立しない理解だけがあれば`contradicted`とする。前提や一部だけで`known`へ上げない。
3. **明示的不知を独立して保つ**: 対象全体の知識と競合しない`reports_unknown`があれば`reported_unknown`とする。前提を知っていることや一部を認識していることは、対象全体を知らないという申告と両立し得るため、それだけで申告を消さない。
4. **現在の一部知識と旧知識を分ける**: 現在文脈で構成部分を知る根拠があれば`partially_known`を検討し、知識を示す根拠が旧時点・別版にしかない場合は`outdated`とする。
5. **構成部分と前提を分ける**: 対象命題の一部を知る場合は`partially_known`、対象とは別の前提から導けるだけなら`inferable`とする。
6. **根拠の有無を最後に確認する**: 採用可能な根拠が0件なら`no_evidence`、1件以上あるが十分条件を満たさなければ`uncertain`とする。

この比較は単純な状態の優先順位ではない。訂正、時点差、適用範囲差を解消した後の同じ評価文脈へ適用する。たとえば、新しい訂正で古い誤解が明確に解消され、現在の強い直接根拠だけが残る場合は、古い`contradicted`を維持せず`known`へ再計算する。

### 6.3 自己申告だけの場合

自己申告の許可値ごとの扱いを次に固定する。

| `knowledge_report` | 申告単体から選べる状態 | 選べない状態と理由 |
| --- | --- | --- |
| `reports_known` | 原則`uncertain`。申告以外の内容に正しい適用・判断があり、別の強い根拠として採用できれば`known`等を選べる | 申告単体は`moderate`であり、対象を実際に説明・適用できる強い直接根拠ではないため`known`にしない |
| `reports_unknown` | 競合がなければ`reported_unknown` | 命題を否定する理解ではないので`contradicted`にせず、根拠が存在するので`no_evidence`にしない |
| `recognizes` | 原則`uncertain` | 用語認識だけでは対象命題の構成部分、前提、または全体理解を特定できないため`known`や`partially_known`にしない |
| `reports_experience` | 原則`uncertain`。原文から具体的な既知部分を別に観測できる場合は、対応する根拠を分けて`partially_known`等を検討できる | 経験した事実だけでは、対象命題を理解していることを意味しないため`known`にしない |

同じ出典から訂正Evidenceと不知申告Evidenceを二件作った場合でも、`reported_unknown`の採用根拠には、`evidence_kind=knowledge_self_report`、`knowledge_report=reports_unknown`、`strength=moderate`である不知申告側の`evidence_id`を必ず含める。`evidence_kind=correction`、`strength=strong`である訂正側だけから`reported_unknown`を導いてはならない。訂正は以前の説明・判断を直したこと、不知申告は対象命題を知らないと本人が述べたことを表し、証明する事実が異なるためである。

訂正部分そのものが対象命題を正しく説明・適用する強い直接根拠になり、同じ評価文脈の不知申告と両立しない場合は、訂正の`strong`を自己申告へ移さず、二つの根拠を未解消の競合として`uncertain`を選ぶ。訂正が別の説明・判断だけを直しており、対象命題を知っている直接根拠にはならない場合は、不知申告と競合させず`reported_unknown`を選べる。この区別により、`known`、`reported_unknown`、`uncertain`の条件を、根拠強度の単純比較で崩さない。

## 7. `DerivedKnowledgeState`各属性の作成規則

### 7.1 `evidence_ids`

`evidence_ids`には、状態を計算するとき実際に意味を読んだ全根拠ではなく、最終状態、既知部分、不足部分、競合解消、訂正、または時点差の説明に実際に使った根拠だけを入れる。検索したが非関連と判断した根拠は入れない。

- `no_evidence`では必ず0件、それ以外では1件以上とする。
- 同じIDを重複させない。
- 関連命題の根拠を入れる場合は、その根拠から評価対象命題へ至る役割を`rationale`へ明記する。
- `uncertain`では一方だけを選ばず、競合判断に使った両側を入れる。
- 訂正で旧判断を置き換えた場合は、実際に比較した訂正前と訂正後の根拠を入れる。
- 一覧の順序へ優先度や時間順の意味を持たせない。表示順が必要なら後続の物理設計で決める。

### 7.2 `known_aspects`と`knowledge_gaps`

両属性は自由な感想ではなく、評価対象命題のどの部分を記事で省略または補足できるか判断するための具体的な短文一覧である。空文字列と同一内容の重複を禁止する。

| 状態 | `known_aspects` | `knowledge_gaps` |
| --- | --- | --- |
| `known` | 強い直接根拠で確認した範囲。対象全体を一項目で表してもよい | 観測された不足がなければ0件。別の未確認事項を推測して追加しない |
| `partially_known` | 1件以上。根拠で確認した構成部分 | 1件以上。対象全体へ足りない構成部分 |
| `inferable` | 導出に使えると確認した前提 | 対象命題自体の直接認識・適用をまだ観測していないこと |
| `contradicted` | 利用者が実際に示した関連知識があれば記す | 対象命題と両立しない理解の具体的な差 |
| `outdated` | 旧時点・旧製品版で確認した知識 | 現在の時点・対象製品版との差 |
| `reported_unknown` | 別に確認できた前提や一部があれば記せる | 利用者本人が知らないと申告した対象範囲 |
| `no_evidence` | 0件 | 観測できていない対象を必要に応じて記す。ただし「利用者は知らない」とは書かない |
| `uncertain` | 競合せず確認できる部分があれば記す | 競合解消または状態確定に必要な追加確認 |

### 7.3 `rationale`

`rationale`は、少なくとも次を人が読み取れる`NonEmptyText`（前後の空白を除き1文字以上ある文章）にする。

1. 選んだ状態と、その十分条件を満たした理由
2. 各`evidence_id`の役割
3. 直接根拠ではないIDを使った場合、その命題と評価対象命題の意味上の接続
4. 適用範囲、時点、製品版の比較結果
5. 競合または訂正がある場合、その解消方法または未解消理由
6. `confidence`を決めた要因

根拠原文の全文を複写して`rationale`の代わりにしない。`rationale`は判断過程、`Evidence.raw_content`は加工前の正本であり、必要な役割が異なるためである。

### 7.4 `confidence`

`confidence`は`0.0`以上`1.0`以下で、選んだ`status`の分類がどれだけ確かかを表す。利用者本人の熟達度、命題そのものが正しい確率、根拠の件数、または「知らなさ」の大きさではない。

Codexは状態を先に選び、次の要因を総合して値を決める。

- 根拠原文が明示的か
- 評価対象命題との意味的一致が直接的か
- 適用範囲、時点、製品版が十分に確認できるか
- 対象全体、構成部分、または前提の必要範囲を覆っているか
- 未解消の競合があるか
- 出典と採用根拠への追跡が完全か

状態を変える数値しきい値は設けない。たとえば`0.8`以上なら`known`という扱いは禁止する。十分条件で状態を選んだ後に確信度を付けるためである。`uncertain`でも「競合して確定不能である」という分類自体には高い`confidence`を付けられ、`no_evidence`でも必要な探索が完全なら高い値を付けられる。数値だけでは理由を説明できないため、主要因を必ず`rationale`へ書く。

### 7.5 時点と監査属性

- `evaluated_at`は今回の計算時点とする。
- `temporal.observed_at`は`evaluated_at`と同じ値にする。
- `temporal`の他の属性は、計算結果自体に適用時点・製品版の限定がある場合だけ設定する。未観測を空文字列や`unknown`で代用しない。
- `audit`は状態内容を誰がいつ決めたかを記録する。保存処理を実行したCLIではなく、意味内容を決めた主体を記録する先行スキーマの規則を守る。

同じ根拠候補、同じ評価文脈、同じ導出規則で再計算した場合、`status`、`evidence_ids`の集合、`known_aspects`、`knowledge_gaps`の意味、`confidence`は恣意的に変えない。再計算時刻、監査時刻、理由文の表記だけは変わり得る。この意味上の冪等性（同じ入力で繰り返しても結果の意味が変わらない性質）が必要なのは、再試行で利用者向けの判定が揺れないようにするためである。

## 8. 再計算と論理的無効化

### 8.1 再計算を必要とする変更

次のいずれかが成立した時点で、影響する現在状態を古い結果として扱い、再計算する。

| 変更 | 影響する範囲 | 必要な理由 |
| --- | --- | --- |
| `Evidence`の追加、内容・分類・強さ・適用条件・出典の修正、または履歴上の失効 | その根拠の対象命題と、その根拠を構成要素・前提・矛盾・旧版として使い得る命題 | 新しい根拠が既存状態の支持、競合、または現在性を変えるため |
| 評価対象`KnowledgeAssertion`の本文、`scope`、`temporal`の変更 | 当該命題の状態と、それを関連根拠として使い得る状態 | 同じ根拠でも評価対象の意味や文脈が変わるため |
| 関連命題の意味、または命題間の意味上の接続の変更 | その接続を構成要素、前提、矛盾、旧版の判断に使う状態 | `partially_known`、`inferable`、`contradicted`、`outdated`の導出経路が変わるため |
| 計算時点が有効期間の境界を越える、または対象製品版が変わる | 境界・製品版に依存する状態 | 追加更新がなくても現在適用可能な根拠集合が変わるため |
| 本書の導出規則または状態の意味が承認済み変更で変わる | 変更規則の影響を受ける全状態。影響を限定できない場合は全状態 | 同じ根拠でも新規則による結果が変わり得るため |

「使い得る命題」には、既存状態の`evidence_ids`へ既に含まれる命題だけでなく、新しい根拠によって初めて構成要素・前提・矛盾・旧版になった命題も含む。既存の逆参照だけに限定すると、新規競合を見落とすためである。影響範囲を索引や走査のどちらで求めるかは物理設計で決める。

### 8.2 無効化の不変条件

1. 無効化は`Evidence`の削除、上書き、または採用事実の抹消ではない。
2. 無効化された`DerivedKnowledgeState`を現在状態として検索結果へ返さない。
3. 無効化中を`no_evidence`または`uncertain`という8状態へ読み替えない。前者は探索後の根拠0件、後者は根拠を評価した結果であり、未再計算とは意味が違う。
4. 無効化と再計算を一つの不可分な変更として完了できる場合は、古い現在値を新しい現在値へ置き換える。分けて行う場合は、その間「現在状態は再計算が必要」として利用不可にする。
5. 再計算に失敗した場合、古い状態を暗黙に現在有効へ戻さない。失敗と再計算必要を返し、正本の根拠を保持する。
6. 同一命題へ外部から見える現在状態は最大一件とし、再計算途中の部分結果を公開しない。

無効化済み結果をどの履歴レコードで残すか、利用不可をどの値や保存場所で表すか、変更を一括適用する方法は`L1-M1-S4`が定義する。本書は新しい`status`や論理スキーマ属性を追加しない。

### 8.3 再計算の事後条件

再計算の完了後は次をすべて満たす。

- 第4章に従って根拠候補を再収集している。
- 第5章と第6章に従い8状態の一件を選んでいる。
- 第7章に従い全属性を作成している。
- 新しい現在状態だけが取得可能である。
- 旧状態と正本の根拠を、履歴契約に従って追跡できる。
- 同じ入力による再試行で二重の現在状態を作らない。

## 9. 保存・更新処理へ渡す契約

### 9.1 事前条件

CLIは状態を保存する前に、少なくとも次を検証する。

1. `assertion_id`と全`evidence_ids`の参照先が同じ知識記録領域に存在する。
2. 全属性が先行スキーマの必須性、論理型、許可値を満たす。
3. `status=no_evidence`なら`evidence_ids`が0件、それ以外なら1件以上で、ID重複がない。
4. `status=partially_known`なら`known_aspects`と`knowledge_gaps`が各1件以上ある。
5. `status=reported_unknown`なら、少なくとも一つの根拠が明示的不知申告の条件を満たす。
6. `temporal.observed_at=evaluated_at`である。
7. 同一`assertion_id`の現在状態を二件公開しない変更になっている。

CLIが機械判定できない命題の同一性、前提の十分性、矛盾、訂正、旧版の意味は、Codexが`rationale`と採用根拠を揃えて決定済みでなければならない。未決定の候補をCLIが推測して保存しない。

### 9.2 事後条件

- 保存した状態から、評価対象命題と実際に使った全根拠へ遡れる。
- 保存処理は`Evidence`を変更、削除、または`rationale`で置き換えない。
- 旧状態を現在値として返さず、現在値は最大一件である。
- 再試行しても同じ論理変更を重複適用せず、失敗時に一部だけを利用可能にしない。
- 履歴には、状態変更前後、変更理由、決定主体、時点を後続契約に従って残せる。

## 10. 具体例

| 観測した根拠 | 結果 | 理由 |
| --- | --- | --- |
| 利用者本人が対象命題を自分の言葉で正しく説明し、現在の適用範囲にも合う`strong`な根拠がある | `known` | 対象全体の直接知識を示し、未解消の競合がない |
| 対象を構成する二つの条件の一方だけを正しく説明し、もう一方は観測できない | `partially_known` | 既知部分と不足部分をそれぞれ具体化できる。両一覧を1件以上にする |
| 必要な前提AとBの理解は強い根拠で確認できるが、AとBから導く対象命題自体の認識はない | `inferable` | 導出経路はあるが、対象自体の直接根拠がないため`known`へ上げない |
| 利用者本人が対象命題と同じ文脈で両立しない説明を一貫して示す | `contradicted` | 質問や不知申告ではなく、矛盾する理解の根拠がある |
| 利用者本人は旧製品版の挙動を正しく説明するが、対象は変更後の現行版である | `outdated` | 知識の不在ではなく、製品版の差で現在適用できない |
| 利用者本人が「この仕組みは知りません」と直接述べた自己申告がある | `reported_unknown` | 明示的不知申告が正本として存在する。質問だけの場合とは異なる |
| 利用者本人が「なぜこの仕組みが必要ですか」と質問しただけで、他の根拠もない | `no_evidence` | 質問を不知申告へ変換せず、必要な探索後も採用根拠が0件である |
| AIが説明し、利用者本人の応答や作成物がまだない | `no_evidence` | 情報への露出は利用者本人の知識獲得を示さない |
| 利用者本人が「知っている」とだけ申告し、説明や適用は確認できない | `uncertain` | 根拠はあるので`no_evidence`ではないが、申告単体では`known`の強い直接根拠にならない |
| 現在の強い支持根拠と、同じ文脈の強い反証根拠が残り、訂正や時点差で解消できない | `uncertain` | 支持側だけを選ぶと競合を隠すため、両側を`evidence_ids`へ残す |
| 古い誤った説明の後、利用者本人が同じ主題を明示的に訂正し、現在の正しい説明を示す | 訂正後の内容で再計算 | 古い根拠を削除せず、旧根拠と訂正根拠を追跡して現在状態を更新する |
| 用語を認識する短い応答だけがある | `uncertain` | `recognizes`は`weak`であり、対象命題の理解範囲を確定できない |

## 11. 後続作業へ渡す確定事項

### 11.1 `L1-M1-S4`への引継ぎ

- 第4章から第7章を、各更新操作が状態を作る際の意味上の入力・出力契約にする。
- 第8章の変更を検出したら、古い状態を現在値として返さず、再計算完了後だけ新状態を公開する。
- 無効化を8状態のいずれかで代用せず、履歴と再計算必要状態の物理表現を定義する。
- 正本の`Evidence`を物理削除せず、訂正前、訂正後、旧状態、新状態を追跡できる履歴を定義する。
- 再試行で現在状態を二重作成せず、一部だけ成功した状態を公開しない。

本書の成果物を引き渡せることと、`L1-M1-S4`を直ちに着手できることは同じではない。固定作業構成表では、同作業は`L1-M1-S2`と本作業`L1-M1-S3`の両方が完了していることを開始条件とする。

### 11.2 `L1-M1-S5`への引継ぎ

- 第6章で8状態がすべて定義され、`reported_unknown`と`no_evidence`、`contradicted`、`uncertain`が区別されていることを要件へ対応付ける。
- `stance`と`knowledge_report`の意味・許可値・条件付き存在が第4.2節で分離されていることを確認する。
- 質問、AI説明、情報への露出、根拠不在から既知・未知を推定しない規則を第4章、第6章、第10章から追跡する。
- `Evidence`を正本として保持し、状態の根拠ID、判断理由、訂正、競合、再計算、無効化を第7章から第9章へ対応付ける。
- Codexの意味判断とCLIの機械検証の境界を、第3章と第9章から追跡する。

本書は`L1-M1-S5`へ直接渡せる入力であるが、同作業の着手には`L1-M1-S1`から`L1-M1-S4`までの全成果物が必要である。本書単独の完了を、全依存が揃った状態とは扱わない。
