# Knowledge論理スキーマ（保持する情報の設計）

## 1. 目的

`KnowledgeStore`（利用者本人が示した知識の根拠と、その評価結果を保存する領域）が保持する情報を定義する。具体的には、情報のまとまり、各項目、値の種類、必須かどうか、許可する値、重複の扱い、同じまとまりの内部で守る規則を定める。本書は、特定のデータベース製品、ファイル形式、検索高速化方法、既存データの移行方法、コマンドラインの引数、JSON形式には依存しない。

本書では、`KnowledgeAssertion`のようにバッククォートで囲んだ英語を、プログラムや保存データで使う識別名として残す。これは実装時に同じ項目を正確に指すためであり、概念の説明を英語へ任せるためではない。初出箇所と定義箇所には日本語の役割名と必要な理由を併記する。

本書の固定入力は[原典Issue #1](https://github.com/yukihito-jokyu/knowledge/issues/1)と、計画内容を後から変わらない形で特定するCommit `9bf911b9122bf4ec51ec48312cc310de29bfcdff`にある[作業構成表](../../task-map.md)である。加えて、本書の設計について利用者へ確認したQ1からQ3までとQ5の回答を設計判断として使用する。Q5は、Issue #1に不足していた「利用者本人が知らないと明示した場合」を表す状態を追加する判断であり、Issue #1の7状態という個数だけを8状態へ変更する。次の原則は、このQ5による変更を除いて選び直さない。

- 利用者本人が知っているかを一つずつ判定できる具体的な命題を、`KnowledgeAssertion`として中心単位にする。
- `Concept`は知識そのものではなく、語句から関連する命題を探すための検索用索引語とする。
- 利用者本人が実際に示した未加工の発言・コードと、そこから整理した命題を別々に保持する。
- 利用者本人が実際に示した根拠を`Evidence`として正本にし、その根拠から計算した現在の知識状態を別に保持する。
- 根拠の強さは`strong`（強い）、`moderate`（中程度）、`weak`（弱い）の3分類とする。
- 記事から取り出した主張についての知識状態は、`known`（知っている）、`partially_known`（一部を知っている）、`inferable`（直接の根拠はないが推論可能）、`contradicted`（記事の主張と矛盾する理解がある）、`outdated`（同じ主題の知識に製品版・時点の差がある）、`reported_unknown`（本人が知らないと明示した）、`no_evidence`（根拠を観測していない）、`uncertain`（根拠同士の競合などにより確定できない）の8状態とする。
- AIが説明した事実、情報を見た事実、質問した事実だけでは、利用者本人が知っていると判定しない。
- 意味判断はCodex、保存・取得・機械的検証はCLIが担う。

## 2. 適用範囲と後続設計との境界

本書が定義するのは、各レコードの内部構造と、各属性へ値を入れる際に守る規則である。規則には、CLIが型や値を見て機械的に検証できるものと、Codexが文章やコードの意味を読んで判断するものがある。両者を混同するとCLIへ意味判断を持ち込むため、本書では規則ごとに判断担当を明記する。

| 項目 | 本書で定義する範囲 | 後続の担当作業 |
| --- | --- | --- |
| 論理レコード | レコード種別、属性、論理型、必須性、列挙値、一意キー | 本書 |
| レコード間のつながり | 参照に必要なID属性と`KnowledgeRelation`レコードの形状 | つながりの種別、向き、接続できる件数、重複可否、参照先の存在確認は`L1-M1-S2` |
| 採用済みの根拠から計算した知識状態 | 保存可能な計算結果の形状 | 根拠の採用、根拠同士が矛盾した場合の解決、再計算、古い計算結果を無効にする規則は`L1-M1-S3` |
| 更新・履歴 | 現在レコードに必要な作成・更新の記録 | `create`（新規作成）、`attach-evidence`（根拠追加）、`revise`（訂正）、`supersede`（新しい内容による置換）の実行前後に守る条件、同一性、変更のつながり、履歴保持は`L1-M1-S4` |
| 要件充足 | 後続が参照できる完全なデータ辞書 | 要件と検索・更新・不変条件が相互に対応していることの確認は`L1-M1-S5` |
| 外部との入出力・実際の保存方法 | 論理型と制約 | JSONでの入出力形式は`L1-M2`、Database上の保存構造・検索高速化・既存データ移行は`L2` |

つながりの種別と、採用済みの根拠から知識状態を計算する規則は、この担当作業の未決事項として放置するのではなく、承認済みの担当分担に従って後続作業で定義する。

### 2.1 このシステム固有のドメイン用語

ここでいうドメイン用語とは、このKnowledgeシステムが情報を区別するために定めた固有概念である。一般的なIT用語や単なる言い換えではない。ここでの「ドメイン」は「このシステムが扱う問題領域」という意味であり、インターネット上の住所を表すドメイン名とは別である。

「ドメイン用語」と「ドメイン知識」も別である。ドメイン用語は、システム内の情報を分類するための名前である。ドメイン知識は、Goやデータベース設計など、対象分野について利用者本人が知っている具体的な内容である。`KnowledgeAssertion`と`Concept`はドメイン用語だが、`KnowledgeAssertion`レコードや`Concept`レコードが存在するだけでは利用者本人のドメイン知識とは判定しない。

| 識別名 | 日本語での意味 | 何と区別するために必要か |
| --- | --- | --- |
| Knowledge（知識） | 本書では、利用者本人がある具体的な命題を知っているという、採用済みの根拠に基づいて評価される状態 | 一般的な情報、記事本文、Codexの説明、保存済みの語句をすべて「知識」と呼ぶ曖昧さを避ける |
| `KnowledgeStore`（知識記録領域） | 利用者本人が示した知識の根拠、整理した命題、現在の評価結果、検索用の語句、相互関係を保存する領域 | 一時的な会話履歴や、記事本文そのものと区別する |
| `KnowledgeAssertion`（知識判定用の命題） | 利用者本人が知っているかを、一つの単位として判定できる具体的な文。例:「Goのスライスは参照先の配列を共有する場合がある」 | 「Goに詳しい」のような粗い能力評価や、単なる語句と区別する |
| `Concept`（検索用索引語） | 記事や会話に現れた語句から、関連する知識判定用の命題を探すための語。例:「slice」「スライス」 | 利用者本人が知っていると判定する命題そのものと区別する |
| `Evidence`（採用済みの根拠） | 利用者本人が命題を知っているかを判断する根拠として採用した、本人の発言、説明、推論、コード、訂正、判断 | まだ評価していない出典データや、Codexが説明しただけの内容と区別する |
| `KnowledgeEpisode`（評価対象の会話・作業範囲） | 複数の発言や作業を、まとめて根拠候補として評価する完了済みの会話または作業の範囲 | 一つの発言や一行のコードと、評価に必要な前後の文脈を区別する |
| `DerivedKnowledgeState`（計算済みの知識状態） | 採用済みの根拠を基に計算した、ある知識判定用の命題についての利用者本人の現在の知識状態 | 根拠そのものと、根拠から計算した結果を区別する |
| `KnowledgeRelation`（命題・索引語のつながり） | 命題や検索用索引語の間にある、前提、因果、矛盾、置換などの明示的なつながり | 語句が似ているだけの関係や、利用者本人がその関係を知っているという根拠と区別する |
| `ArticleClaim`（記事から取り出した主張） | 読む価値を判定する既存の記事から、利用者本人の知識と比較できる一単位として取り出した具体的な主張。本書が定義する知識記録領域の保存レコードではなく、後続の記事分析・知識検索処理が扱う評価入力である | 記事の要約全体ではなく、利用者本人が既に知っている命題と比較する側の情報を明示し、保存済みの`KnowledgeAssertion`と取り違えないため |
| `PrimaryUser`（利用者本人） | この知識記録領域が知識を記録・評価する唯一の利用者 | 出典を作ったCodexや自動処理と区別する |
| 根拠候補 | 未評価の出典データのうち、Codexが確認して根拠として採用する可能性がある部分。候補になっただけでは採用済みの根拠でも`known`（知っている）でもない | 読み込んだ全データ、採用済みの根拠、計算済み知識状態を区別する |
| 未評価の出典データ | 根拠として使えるかまだ判断していない発言、コード、文書、訂正、技術判断 | 採用済みの根拠や、利用者本人の知識として評価した状態と区別する |
| `ActorReference`（行為主体への参照） | 出典を作成・提示した主体、または論理レコードの内容を作成・更新すると決めた主体への参照 | 内容そのもの、出典場所、保存を実行しただけの処理、データを読み込む操作と区別する |
| `SourceReference`（出典への参照） | 採用済みの根拠の原文がある会話、ファイル、発言、行番号などへの参照 | 原文そのものや、原文を作った主体と区別する |
| `Alias`（別名） | 同じ検索用索引語を指す略称、API名、綴り違い | 代表表記や、別の意味を持つ語と区別する |
| `Scope`（適用範囲） | 命題や検索用索引語が成り立つ技術分野、プログラミング言語、対象製品などの適用範囲 | 同じ文章・語句でも意味が異なる前後関係を区別する |
| `TemporalMetadata`（時点・製品版情報） | 有効期間、適用製品版、観測時点、最終確認時点 | 本文の意味と、いつ有効かという条件を区別する |
| `AuditMetadata`（作成・更新の記録） | 論理レコードの内容を誰がいつ成立させ、最後に誰がいつ変更すると決めたかの記録 | 根拠の出典作成者や、決定済みの内容を保存しただけの処理と区別する |
| `EntityReference`（つながりの接続先） | 命題・索引語のつながりの始点・終点となる命題または検索用索引語への参照 | 接続先の内容や、つながりの種類と区別する |
| Codex | 文章の意味、同一性、根拠として妥当か、どの命題に対応するかを判断するAI | 規則どおり保存するだけのコマンドライン処理・自動処理と区別する |
| CLI（コマンドライン処理） | 文字による命令で実行し、Codexが決めた内容を規則どおり検証・保存・取得するプログラム | 意味を判断するCodexと区別する |
| System（自動処理） | 利用者本人でもCodexでもない自動処理。例: 決められた規則で保存するコマンドライン処理 | 利用者本人の意思表示やCodexの意味判断と区別する |
| `import`（外部データの読込み） | 現在の会話の外にあるファイルや会話履歴を、未評価の出典データとして読み込む操作 | 人や処理主体を表す`ActorReference`と区別する |
| Artifact（外部成果物） | 現在評価している会話・作業の外で作成された文書、コード、設計書などの成果物 | 現在の会話内の発言や、その成果物を読み込む操作と区別する |

「検索アンカー」という表現は使用しない。意味が定義されていない比喩だったため、以後は「検索用索引語」と記載する。

#### 具体例: 一つの発言をどう扱うか

利用者本人が「Goでは、スライスへ要素を追加すると、容量が足りない場合に新しい配列が確保される」と説明した場合は、次のように区別する。

| 段階 | 保存・判断する内容 | この時点では何ではないか |
| --- | --- | --- |
| 未評価の出典データ | 利用者本人の発言を、加工せず取得したもの | 取得しただけでは採用済みの根拠でも知識でもない |
| `KnowledgeAssertion`（知識判定用の命題） | 「Goのスライスへの追加は、容量不足時に新しい配列を確保する」という、知っているかを判定する一文 | 利用者本人の発言原文ではなく、知識状態そのものでもない |
| `Evidence`（採用済みの根拠） | 上記命題の根拠として採用した、利用者本人の実際の説明 | Codexの説明や、検索用の語句ではない |
| `DerivedKnowledgeState`（計算済みの知識状態） | 採用済みの根拠から計算した「知っている」「一部を知っている」などの結果 | 根拠原文ではなく、根拠が変われば再計算する |
| `Concept`（検索用索引語） | 「Go」「slice」「スライス」「append」など、関連する命題を探すための語 | 命題でも、根拠でも、知識状態でもない |

したがって、`KnowledgeAssertion`は「知識かどうかを判定する一文」、`Concept`は「その一文を探すための索引語」である。どちらのレコードも、存在するだけでは利用者本人が知っていることを意味しない。

### 2.2 一般的な設計用語

以下はKnowledgeドメイン固有ではなく、データ設計で一般に使う用語である。本書内での意味を次のように固定する。

| 前提知識 | 本書での意味 |
| --- | --- |
| ドメイン | システムが扱う問題領域。本書では、利用者本人の知識を記録・評価する領域を指す |
| ドメイン用語 | 対象システム内の情報を一貫して区別するために定義した専門語 |
| ドメイン知識 | Go、データベース設計など、ある対象分野について利用者本人が知っている具体的内容 |
| Schema（スキーマ、情報構造の設計） | 保存する情報の種類、項目、値の種類、必須条件、相互関係を定めた設計。本書では以後「スキーマ」と記載する |
| 論理スキーマと物理スキーマ | 論理スキーマは「何を保持するか」を定義する。物理スキーマはデータベースの表、列、文書、索引などを使って「どう保持するか」を定義する |
| レコード | 独立した識別番号を持ち、個別に作成・更新・参照する情報のまとまり |
| 属性 | レコード内の一項目。例: 命題本文を入れる`statement` |
| 論理型 | 項目へ入れられる値の性質を表す分類。例: 文字列、時点、識別子。特定のデータベース製品で使う型名ではない |
| プログラム上の基礎型 | 論理型を実装するときに使う値の基本分類。本書では`string`（文字列）、`int`（整数）、`float`（小数）、`datetime`（日時）、`object`（複数属性のまとまり）、`list<T>`（同じ型`T`の複数値）を使う |
| 値オブジェクト | 親レコードの一部としてだけ意味を持つ、複数属性のまとまり。独立した識別番号や単独の更新単位を持たない |
| 正本と導出物 | 正本は判断をやり直す際の基準として残す元記録。導出物は正本から再計算できる結果。`Evidence`（採用済みの根拠）が正本、`DerivedKnowledgeState`（計算済みの知識状態）が導出物 |
| 識別子（ID） | 表示名や本文が変わっても同じレコードを指し続けるための値 |
| 参照属性と参照整合性 | 参照属性は別レコードのIDを保持する項目。参照整合性は参照先が実在することや、削除時に参照を壊さないための規則 |
| 列挙値 | 自由文ではなく、事前に許可した候補から一つを選ぶ値。例: `actor_kind`の`user`、`codex`、`system` |
| 一意性 | 同じ値または値の組合せを、複数レコードへ重複登録できないという規則 |
| 不変条件 | 作成・更新の前後を問わず、常に守らなければならない規則 |
| 未観測と否定 | 値や採用済みの根拠が存在しないことは、否定、未知、理解不足を意味しない |
| 文字列一致と意味的同一性 | 文字列の一致・不一致だけでは、2つの知識判定用の命題や検索用索引語が同じ意味か判定できない |
| 正規化 | 意味を変えず、表記揺れを抑えて検索・比較しやすい形に整えること。原文の削除や要約を意味しない |
| `Scope`（適用範囲） | 命題や語句が、どの技術分野・プログラミング言語・対象製品について成り立つかを示す条件。本文が日本語か英語かは含めない |
| `TemporalMetadata`（時点情報） | 内容がいつ有効か、どの製品版に適用できるか、いつ観測・確認したかを示す情報 |
| CodexとCLI（コマンドライン処理）の責務 | Codexが文章の意味、同一性、根拠として妥当かを判断する。コマンドライン処理はCodexから指定された内容を、追加の意味判断をせず規則どおり検証・保存・取得する |
| AI（人工知能） | 本書では文章の生成や意味判断を行う仕組み。Codexはこの役割を担う |
| API（プログラム向けの操作窓口） | 別のプログラムから機能を呼び出すために公開された名前や規則 |
| JSON（項目名と値で表すデータ形式） | プログラム間で情報を受け渡すための文字形式。この論理スキーマを実際にどうJSONへ表すかは後続設計で決める |
| Runtime（実行する仕組み） | プログラムを実際に動かし、処理手順を進める側。原典の`AI Runtime: Codex`は、AIとして意味を判断し、処理を進行する役割をCodexが担うという意味 |
| URI（参照先識別子） | 会話、発言、ファイルなどの参照先を一意に指す文字列。ウェブ上のURLだけに限定しない |
| SHA-256（内容照合値の計算方法） | 元データから固定長の値を計算する標準方式。同じ元データからは同じ値が得られ、内容変更の検出に使う。暗号化して元データを隠す方式ではない |
| BCP 47（自然言語の識別形式） | 日本語を`ja`、英語を`en`のように表す、インターネット技術の標準形式。GoやJavaなどのプログラミング言語は表さない |
| GitとCommit（変更履歴とその保存単位） | Gitはファイル変更の履歴を管理する仕組み。Commitは複数の変更を一つの履歴単位としてGitへ保存したもの。本書の固定Commitは、参照する計画内容が後から変わらないよう版を特定するために使う |
| GitHub Issue（作業・要件の記録） | GitHub上で、要件、担当作業、完了条件、議論を一件にまとめた記録。本書ではIssue #1を原典の要件、Issue #28を本書作成の担当作業として扱う |
| 作業ID | 承認済みの作業構成表で担当範囲を一意に示す番号。例: `L1-M1-S2`。本書が決めず後続作業へ渡す事項の担当先を明示するために使う |
| データベース | 複数のレコードを保存し、条件に応じて取得・更新する仕組み |
| コマンドライン | 画面上のボタンではなく、文字で命令を入力してプログラムを実行する方法 |

特に、`no_evidence`は「利用者本人が知らない」ではなく「採用済みの根拠がない」、`inferable`は「利用者本人が知っている」ではなく「他の知識から推論できる」という不変条件を前提とする。

### 2.3 利用者の回答と確認項目

#### Q3への回答. 利用者本人が過去に作成した外部成果物を、知識の根拠候補にする

用語と前提知識:

- `PrimaryUser`（利用者本人）は、この知識記録領域が知識を記録・評価する唯一の利用者である。Q1の回答により、複数利用者の登録や切替は扱わない。
- 未評価の出典データは、知識そのものではない。根拠として採用する前の発言、コード断片、文書、訂正、技術判断などである。
- `import`（外部データの読込み）は、現在の会話の外にあるファイルや会話履歴を、未評価の出典データとして読み込む操作である。出典を作成した人や自動処理を指す語ではない。ファイルのアップロード、コマンドによる読込み、ファイル走査など、具体的な読込み手段はこの論理スキーマでは区別しない。
- Artifact（外部成果物）は、現在評価している会話・作業の外で作成された文書、コード、設計記録などである。
- `KnowledgeEpisode`（評価対象の会話・作業範囲）は、一つの発言だけでなく、後続の訂正や関連する作業も含めて根拠候補を評価する、完了済みのまとまりである。`conversation`は会話のまとまり、`task`はファイル編集やコマンド実行を含む作業のまとまりを表す。
- `System`（自動処理）は、利用者本人でも、意味判断を行うCodexでもない処理である。たとえば、決められた規則で出典を収集したり、知識レコードを保存したりするコマンドライン処理が該当する。内容を運んだ自動処理を、その内容の作成者とは扱わない。
- `ActorReference`（行為主体への参照）は、人または処理を指す再利用可能な項目群である。`SourceReference.originator`に置かれた場合は出典を実際に作成・提示した主体を表す。`AuditMetadata.created_by`または`updated_by`に置かれた場合は、知識レコードの内容を作成・更新すると決めた主体を表す。CLIがCodexの決定をそのまま保存しただけなら、CLIはこの属性へ記録しない。
- `SourceReference`（出典への参照）は、未評価の出典データをどこから、どの前後関係で取得したかを表す。出典の種類、元データへの参照先、評価対象の会話・作業範囲、行番号や発言番号などを保持する。
- たとえば、利用者本人が過去に作ったコードファイルをCodexが読み込む場合、`originator.actor_kind`（出典作成者の種類）は`user`、`source_kind`（出典を取得する形式）は`file`（ファイル）、`source_locator`（元データへの参照先）はそのファイルを指す。同じコードを現在の会話へ貼り、その発言を根拠原文として採用した場合、作成者は同じ`user`だが、出典を取得する形式は`message`（会話内の発言）となる。
- `KnowledgeAssertion`（知識判定用の命題）は、「利用者本人がこれを知っているか」を一件ずつ判定する具体的な一文である。
- `Evidence`（採用済みの根拠）は、利用者本人が知識判定用の命題を知っているかを判断するために採用した、本人の発言・説明・コード・訂正・判断である。資料を読み込んだことや本人が資料を見たことだけでは、理解している根拠にならない。
- `known`（知っている）は、採用済みの根拠から、利用者本人がその命題を知っていると評価できる状態である。資料が存在するだけでは設定しない。
- 「直接、根拠候補にする」とは、現在の会話で追加説明を求める前から、過去の成果物そのものを評価対象へ含めることを意味する。候補になっただけでは、採用済みの根拠にも「知っている」という状態にもならない。

回答前に確定していなかった点: `import`は行為主体ではないため、`ActorReference.actor_kind`から除外することは確定済みだった。一方、外部成果物が利用者本人の知識を示す直接の根拠候補になり得る条件は、原典だけでは確定していなかった。

質問する理由: 外部成果物の作成者を確認せず根拠にすると、第三者資料やAI生成物を利用者本人の知識として誤登録する。一方、外部成果物をすべて対象外にすると、利用者本人が過去に作成したコードや設計書から知識の根拠を得られない。

選択肢と影響:

- A. 作成者が利用者本人だと出典情報から確認できる外部成果物は、その内容自体を直接、根拠候補にする。作成者不明、第三者作成、Codex・AI生成の成果物は、利用者本人による説明・訂正・技術判断などを別に観測できた場合だけ候補にする。
- B. 現在の会話・作業範囲内で利用者本人が示した内容だけを、直接の根拠候補にする。利用者本人が作成したと確認できる外部成果物も、現在の会話・作業で本人が説明・確認するまでは候補にしない。

判断してほしい基準: 過去に自分で作ったコード・文書も知識判定へ積極的に利用したい場合はAを選ぶ。知識判定を、現在のCodexとの会話・作業内で本人に確認できた内容だけへ限定したい場合はBを選ぶ。どちらでも、作成者不明、第三者作成、AI生成の成果物は、読み込んだだけでは採用済みの根拠にしない。

現在の推奨: A。利用者本人の過去の成果物は知識を示す観測になり得て、作成者を確認できない内容は除外できるためである。`actor_kind`（行為主体の種類）は選択肢にかかわらず`user`、`codex`、`system`に限定する。

質問: 利用者本人が過去に作成したと確認できる外部のコード・文書を、現在の会話で再確認しなくても直接、根拠候補にするAを採用してよいでしょうか。それとも、現在の会話・作業内で本人が説明・確認した内容だけへ限定するBが必要でしょうか。

利用者の回答: A。

この回答から採用する設計:

- 出典情報から利用者本人が作成したと確認できる外部成果物は、現在の会話で再確認しなくても、その内容自体を知識の根拠候補にできる。
- 作成者不明、第三者作成、Codex・AI生成の外部成果物は、読み込んだだけでは利用者本人の知識の根拠候補にしない。
- それらの外部成果物について利用者本人による説明、訂正、技術判断などを別に観測できた場合は、その本人の行為を根拠候補にできる。
- 根拠候補になったことだけでは、`Evidence`（採用済みの根拠）にも`known`（知っている状態）にもならない。内容を命題と対応付け、根拠として妥当かを評価した後に採用する。

必要な理由: 利用者本人が過去に作ったコードや文書を知識判定に利用しながら、第三者やAIが作成した内容を利用者本人の知識として誤登録することを防ぐためである。

#### Q5（回答済み）. 利用者本人が「知らない」と明示した場合の知識状態

用語と前提知識:

- 「知らないという明示申告」は、利用者本人が特定の命題について「それは知らない」と直接述べた事実である。質問しただけ、説明を受けただけ、保存済みの根拠が見つからないだけの場合は含めない。

質問する理由: この場合を決めないと、採用可能な根拠が存在するのに7状態のどれにも定義どおり分類できず、`DerivedKnowledgeState.status`（計算済み知識状態の分類）を必須値として保存できないためである。

選択肢と影響:

- A. `reported_unknown`（本人が知らないと明示した）を8番目の状態として追加する。根拠の不在や質問からは設定せず、利用者本人の明示申告だけを条件にする。意味は最も正確になるが、原典Issue #1の「7状態」を変更し、後続設計も8状態へ合わせる必要がある。
- B. 「知らない」という明示申告がある場合も`no_evidence`へ含める。7状態は維持できるが、「知っているとも知らないとも判断できる根拠がない」という現在の意味を「知っている根拠がない」へ変更するため、未観測と明示的な不知を区別できなくなる。
- C. 「知らない」という明示申告を`uncertain`へ含める。7状態と`no_evidence`の意味は維持できるが、明確な本人申告と、矛盾・情報不足による判定不能を同じ状態へまとめることになる。

判断してほしい基準: 未観測と本人による明示的な「知らない」を区別し、後から根拠まで正確に説明できることを優先するならAを選ぶ。原典の7状態を変更しないことを最優先するならBまたはCになるが、どちらも意味の異なる状況を一つへまとめる。

現在の推奨: A。Issue #1の不変条件である「根拠がないことは、知らないことではない」を守りながら、本人が明示した不知だけを別に表せるためである。

質問: 利用者本人が特定の命題について「知らない」と明示した場合を表すため、Aの`reported_unknown`を8番目の知識状態として追加してよいでしょうか。それとも、7状態を維持してBの`no_evidence`またはCの`uncertain`へ含めますか。

利用者の回答: Aを採用して問題ない。

この回答から採用する設計:

## 3. 記法と共通規則

### 3.1 必須性

| 表記 | 意味 |
| --- | --- |
| 必須 | レコード生成時から値が存在する |
| 条件付き | 記載した条件を満たす場合に値が存在する |
| 任意 | 値を観測または適用できる場合だけ存在する |

任意値の未観測は「値なし」であり、空文字列、空の識別子、`unknown`という推定値で代用しない。配列は、属性自体が任意なら省略可能、必須なら0件を許容する場合でも存在する。

### 3.2 論理型

論理型に付ける`T[]`は「論理型`T`の値を0件以上並べたもの」を表す記法であり、プログラム上の基礎型`list<T>`と同じ複数値を表す。例えば`Alias[]`は、基礎型では`list<object>`である。`T`は実際の型名ではなく、「ここへ任意の型名が入る」という記号である。

| 論理型 | プログラム上の基礎型 | 定義とレコード内制約 | 必要な理由 |
| --- | --- | --- | --- |
| `Identifier<T>` | `string` | 種別`T`のレコード一件を区別するID。ID自体へ名前や日時などの意味を持たせず、空値を許さない。具体的な生成方法は後続設計で決める | 表示名や内容が変わっても、同じレコードを参照し続けるため |
| `NonEmptyText` | `string` | 前後の空白を除いて1文字以上ある文字列。日本語、英語、記号などを扱える | 意味を持たない空値を有効な本文や表示値として保存しないため |
| `NormalizedText` | `string` | 原文の意味を変えず、大文字小文字や空白などの表記差を一定の規則で整え、正規化後も1文字以上ある文字列。原文の代わりには使わない | 空文字列を検索・比較用の値として登録せず、表記揺れを抑えた検索・比較と原文保持を両立するため |
| `Token`（許可値を限定した短い文字列） | `string` | 状態や種別をプログラムが判定するための短い固定文字列。大文字小文字を区別し、属性ごとに許可値を列挙する。ただし、作業分担上、許可値の決定を後続作業へ明記して委ねた属性は、後続作業で許可値が確定するまで実装入力に使わない | 状態や種別を自由文にせず、入力誤りを検出し、処理を確実に分岐するため |
| `Instant`（時差を含む一時点） | `datetime` | 「2026年8月11日10時00分（日本時間）」のように、時差を含めて世界上の一時点へ確定できる日時値。保存時の文字列表現は後続設計で決める | 観測・有効期間・作成更新の前後関係を、文字列ではなく日時として比較するため |
| `Decimal01` | `float` | `0.0`以上`1.0`以下の小数。`0.0`は確信なし、`1.0`は最大の確信を表す尺度として使う | 知識状態をどれだけ確かに分類できたかを同じ範囲で比較するため |
| `Digest`（内容照合値） | `string` | `sha256:`の直後へ、SHA-256（元データから固定長の照合値を計算する標準方式）で得た64文字を続ける。64文字には数字`0`〜`9`と小文字`a`〜`f`だけを使う。つまり形式は`sha256:`と64文字の計算結果であり、省略表記は保存しない。計算方法の詳細は[米国国立標準技術研究所の標準文書 FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)を参照する | 後から取得した出典が、根拠作成時と同じ内容かを機械的に確認し、異なる計算方法の結果を取り違えないため |
| `URI`（参照先を示す文字列） | `string` | ファイル、会話、発言などの参照先を一意に示す文字列。ウェブ上の参照先だけでなく、システム内部の参照形式も含む | 保存方式が変わっても、根拠の出典や評価対象の会話・作業範囲へ戻れるようにするため |
| `LanguageTag`（自然言語を示す値） | `string` | 本文が日本語、英語などのどの自然言語で書かれているかを、[BCP 47](https://www.rfc-editor.org/info/rfc5646/)（自然言語を識別するための標準形式）に従って表す。例: `ja`（日本語）、`en`（英語）、`en-US`（米国で使われる英語）。プログラミング言語は表さず、判定できない場合は省略する | 言語に合った検索・表示・表記正規化を選び、同じ自然言語を独自表記で重複させないため |

現在のレコードには整数を保持する属性がないため、プログラム上の基礎型`int`を使う属性はない。将来、件数や順序を属性として追加する場合は、その時点で許可範囲を持つ論理型を定義する。

### 3.3 全レコード共通規則

- 主識別子はレコード種別内で一意であり、業務上の意味を埋め込まない。
- `NormalizedText`同士の文字列一致は意味的同一性を保証しない。意味的な重複判定はCodexの責務である。
- 監査時点は事実を記録するだけで、履歴レコードや更新操作の意味を兼ねない。
- レコードの不在からユーザーの未知、理解不足、熟達度を推定しない。

本書の規則は、次の二種類を明記して区別する。

- CLIによる機械検証: 基礎型、必須性、列挙値、日時の前後関係、完全一致による重複など、文章の意味を理解せず判定できる規則。
- Codexによる意味判断: 命題が一つの意味へ分けられているか、根拠として妥当か、二つの表現が同じ意味かなど、文章やコードの意味を読む必要がある規則。

CLIはCodexによる意味判断を代行しない。Codexが決めた値に対し、CLIによる機械検証だけを行う。

## 4. 論理レコード一覧

論理レコードは複数の属性を一件へまとめるため、レコード全体のプログラム上の基礎型は`object`である。`string`や`int`はレコード全体ではなく、レコードを構成する各属性の基礎型として使う。各属性の基礎型は第5章と第6章の属性表へ直接記載する。

| 論理レコード | レコード全体の基礎型 | 役割 | `object`が必要な理由 | 正本性 |
| --- | --- | --- | --- | --- |
| `KnowledgeAssertion` | `object` | 独立評価可能な正規化済み命題 | ID、命題本文、本文の自然言語、適用範囲、時点、作成・更新情報を一件へまとめるため | 正本 |
| `Concept` | `object` | 語句から関連する命題へ到達する検索用索引語 | ID、代表表記、検索比較用表記、別名、適用範囲、作成・更新情報を一件へまとめるため | 正本 |
| `KnowledgeEpisode` | `object` | 根拠候補をまとめて評価する会話・作業の範囲 | ID、範囲種別、参照先、開始・終了時点、説明、作成・更新情報を一件へまとめるため | 正本 |
| `Evidence` | `object` | 命題について利用者本人が実際に示した、加工前の根拠 | ID、対象命題、根拠種別、原文、出典、時点、作成・更新情報を一件へまとめるため | 正本 |
| `DerivedKnowledgeState` | `object` | 採用済みの根拠から算出した利用者本人の知識状態 | ID、対象命題、実際に使った根拠ID、状態、確信度、既知部分、不足部分、計算時点を一件へまとめるため | 導出物。採用済みの根拠を上書きしない |
| `KnowledgeRelation` | `object` | 命題と検索用索引語の間にある明示的なつながり | ID、始点、終点、つながり種別、適用範囲、時点を一件へまとめるため | 正本。ただし利用者本人がそのつながりを知っている証明ではない |

`ActorReference`（行為主体への参照）、`AuditMetadata`（作成・更新の記録）、`Alias`（別名）、`Scope`（意味の適用範囲）、`TemporalMetadata`（時点情報）、`SourceReference`（出典への参照）、`EntityReference`（つながりの接続先）も、複数属性をまとめるため基礎型は`object`である。ただし、上記レコードの一部としてだけ使い、単独のIDや、単独で作成・更新・削除される期間を持たない。

## 5. 複数のレコード内で共通利用する項目群

### 5.1 `ActorReference`（行為主体への参照）

「誰が行ったか」を表す。どこに配置されるかによって、出典データを作成・提示した人または処理、知識レコードを作成・更新した人または処理を指す。Codexが作った説明を利用者本人の知識根拠へ誤登録しないために必要である。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `actor_kind` | `Token` | `string` | 必須 | `user`、`codex`、`system`のいずれか | 利用者本人が示した内容とAI・自動処理が作った情報を機械的に区別するため。`import`は読込み操作であり行為主体ではない |
| `actor_id` | `NonEmptyText` | `string` | 条件付き | `actor_kind=user`では省略する。`actor_kind=codex`または`system`では必須とし、設定で固定したプログラム・処理名を入れる | 一人専用の利用者へ不要な識別子を設けず、Codexや自動処理は具体的にどの処理が内容を決めたかを追跡するため |

`actor_kind`の値:

- `user`: 知識を評価される唯一の利用者本人が、発言、コード、訂正、判断を提示した場合。利用者は一人に固定されるため`actor_id`を付けない。
- `codex`: Codexが文章の意味を読み、根拠の採用や知識レコードの内容を決めた場合。`actor_id`には設定で固定したCodexの処理名を入れる。
- `system`: CLIなどの自動処理が、文章の意味を判断せず、決められた規則だけで内容を決めた場合。`actor_id`には設定で固定したプログラムまたは処理名を入れる。Codexが決めた内容をCLIがそのまま保存しただけの場合、レコード内容の決定者は`codex`であり`system`ではない。

`import`は外部データを読み込む操作であり、誰が行ったかを表す主体ではないため含めない。

### 5.2 `AuditMetadata`（作成・更新の記録）

現在のレコード内容を、誰がいつ成立させ、最後に誰がいつ変更すると決めたかを記録する。内容に誤りが見つかったときに、変更時点と内容の決定者を確認するために必要である。ここでは保存処理を実行したプログラムではなく、論理レコードの内容を決めた主体を記録する。CLIへの保存要求や再試行など、処理自体の履歴は`L1-M1-S4`で定義する。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `created_at` | `Instant` | `datetime` | 必須 | 当該論理レコードが最初に作成された時点 | レコードの発生時点と、その後の更新時点を区別するため |
| `created_by` | `ActorReference` | `object` | 必須 | 初期のレコード内容を決めた主体。Codexが内容を決め、CLIが保存した場合は`codex` | 初期表現を誰の意思または意味判断で成立させたかを監査できるようにするため |
| `updated_at` | `Instant` | `datetime` | 必須 | 現在表現が最後に更新された時点。`created_at`以後 | 現在値の鮮度と変更順序を判定するため |
| `updated_by` | `ActorReference` | `object` | 必須 | 現在のレコード内容へ最後に変更すると決めた主体。作成後に未更新なら`created_by`と同じ | 現在表現へ最後に責任を持つ行為主体を追跡するため |

監査メタデータは全6レコードで必須とする。作成後に一度も更新していない場合は、`updated_at=created_at`かつ`updated_by=created_by`とする。更新前の値、保存を実行したプログラム、操作ID、系譜は`L1-M1-S4`の履歴契約で定義する。

### 5.3 `Alias`（別名）

同じ検索用索引語を指す別の表記である。正式名だけでなく、略称、API名、綴り違いからも同じ検索用索引語へ到達するために必要である。別名自体を、利用者本人が知っているか判定する命題として扱わない。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `text` | `NonEmptyText` | `string` | 必須 | 別名の原表記 | 利用者本人の発言や出典に現れた表記を失わず、検索結果へ表示するため |
| `normalized_text` | `NormalizedText` | `string` | 必須 | 照合用表記 | 大小文字や表記形式の差を抑えて字句照合するため |
| `alias_kind` | `Token` | `string` | 必須 | `synonym`、`abbreviation`、`identifier`、`api_name`、`spelling_variant`のいずれか | 別名が一致する理由を区別し、検索時の扱いを選べるようにするため |
| `language` | `LanguageTag` | `string` | 任意 | 自然言語に依存する別名の場合に設定 | 同じ表記でも言語によって意味が異なる場合の誤照合を抑えるため |

同じ`Concept`内では、検索比較用の別名、言語、別名種別の組を重複させない。代表表記`canonical_label`と、表記を整えた後に同じになる別名は登録しない。

`alias_kind`の値:

- `synonym`: 意味が同じ別の語。例:「削除」と「消去」。
- `abbreviation`: 略称。例:「Application Programming Interface」に対する「API」。
- `identifier`: プログラム内の型名や変数名などの識別名。
- `api_name`: APIで外部へ公開されている関数名、メソッド名、接続先名。公開API名にもプログラム上の識別名という性質はあるが、外部利用者が呼び出す契約名である場合はこちらを選び、公開されていない型名・変数名は`identifier`を選ぶ。
- `spelling_variant`: 大文字小文字、送り仮名、綴りなどの表記違い。

### 5.4 `ScopeFacet`と`Scope`（意味の適用範囲）

`Scope`は、命題や検索用索引語がどの分野、プログラミング言語、対象について成り立つかを表す。同じ語句でも分野や対象によって意味が異なるものを混同しないために必要である。`ScopeFacet`は、「分野」「プログラミング言語」「対象」のような適用範囲一件分である。命題本文が日本語か英語かは`LanguageTag`で表し、ここへは入れない。

`ScopeFacet`:

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `dimension` | `Token` | `string` | 必須 | `domain`、`language`、`subject`のいずれか。この版ではそれ以外を許可しない | `value`が何の適用範囲を示すかを機械的に解釈し、未定義の分類を保存しないため |
| `value` | `NonEmptyText` | `string` | 必須 | 適用範囲の種類に対応する値 | 人間が適用範囲を確認できる原表記を保持するため |
| `normalized_value` | `NormalizedText` | `string` | 必須 | 検索・比較用表記 | 表記揺れを抑えて同じ適用範囲の候補を検索・比較するため |

`Scope`:

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `facets` | `ScopeFacet[]` | `list<object>` | 必須 | 0件以上。同じ適用範囲種別と検索比較用の値の組を重複させない | 技術分野、プログラミング言語、対象製品など複数種類の適用範囲を、種類ごとに固定項目を増やさず組み合わせて表すため |

空の`Scope`は「全範囲に有効」ではなく「追加の適用範囲を観測していない」を表す。適用範囲を限定しないと判断した場合は、知識判定用の命題本文と時点情報を根拠に扱う。

複数の`ScopeFacet`を持つ場合、異なる`dimension`（適用範囲の種類）同士はAND条件、同じ`dimension`内の複数値はOR条件として扱う。たとえば`domain=software-engineering`と`language=Go`を持つ場合は「ソフトウェア工学の分野であり、かつGoに関する内容」を表す。`language=Go`と`language=Rust`を持つ場合は「GoまたはRustのいずれかに関する内容」を表す。この規則は、保存した適用範囲を検索処理ごとに異なる意味で解釈しないために必要である。比較時は`facets`の並び順を意味の違いとして扱わない。

`dimension`の現在の値:

- `domain`: 技術分野や業務分野。例: ソフトウェア工学、データベース設計、会計。プログラミング言語名は、専用の`language`へ入れ、`domain`へ重複して入れない。
- `language`: プログラミング言語。例: Go、Java、Rust。命題本文や根拠原文の自然言語を表す`LanguageTag`とは別である。Goのように技術分野名としても読める名称であっても、プログラミング言語を指す場合はこちらを選ぶ。
- `subject`: 命題が対象にしている製品、ライブラリ、機能など。利用者本人を表す語ではない。

### 5.5 `TemporalMetadata`（有効時点・適用製品版の情報）

命題や採用済みの根拠が、いつからいつまで有効か、どの製品版に当てはまるか、いつ観測・確認したかを表す。過去には正しかったが現在は古い内容や、製品版によって異なる内容を、現在も正しいものとして扱わないために必要である。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `valid_from` | `Instant` | `datetime` | 任意 | 内容が有効となる開始時点 | 将来有効になる内容や、過去のどの時点から成立したかを判定するため |
| `valid_until` | `Instant` | `datetime` | 任意 | 内容が有効でなくなる境界時点。この時点そのものは有効期間へ含めない | 境界時点で有効かどうかを処理ごとに違う解釈にせず、失効済みの知識を現在も有効だと扱わないため |
| `version_scope` | `NonEmptyText[]` | `list<string>` | 任意 | 製品、仕様、API等の適用製品版。空配列は使わない | 製品版ごとに真偽が変わる内容を混同しないため |
| `observed_at` | `Instant` | `datetime` | 任意 | 内容または状態を観測した時点 | 採用済みの根拠や計算済みの知識状態を、作成時点ではなく実際の観測時点へ結び付けるため |
| `last_verified` | `Instant` | `datetime` | 任意 | 内容を最後に検証した時点 | 再確認からの経過時間を基に、再検証の必要性を判断するため |

`valid_from`と`valid_until`が両方存在する場合は`valid_from < valid_until`とする。`version_scope`の要素は同一値を重複させない。製品版に依存しない場合、または時点情報を観測していない場合は、該当属性を省略する。

### 5.6 `SourceReference`（出典への参照）

採用済みの根拠となった発言・コード・判断が、どの会話、ファイル、位置から得られたかを記録する。命題への整理や知識状態の計算に誤りがあった場合、加工前の出典と前後の文脈へ戻って評価し直すために必要である。採用した原文そのものは`Evidence.raw_content`（根拠の原文）に保持する。`source_kind`は元データを会話の発言として取得したか、ファイルとして取得したかだけを表し、コード、自己申告、訂正など内容の意味は`Evidence.evidence_kind`へ記録する。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `source_kind` | `Token` | `string` | 必須 | `message`または`file`。内容の意味ではなく、元データを取得する形式で分類する | 会話履歴とファイルで異なる再取得・表示・位置指定方法を選ぶため |
| `source_locator` | `URI` | `string` | 必須 | 元データへ再び到達するための参照先 | 根拠の要約だけでなく、元データそのものへ遡るため |
| `episode_id` | `Identifier<KnowledgeEpisode>` | `string` | 必須 | 根拠を解釈した会話・作業のまとまりを指すID | 単一断片を、それが評価された会話・作業の前後関係へ結び付けるため |
| `originator` | `ActorReference` | `object` | 必須 | 原文、元コード、判断を提示した主体 | 利用者本人が示した根拠か、AI・自動処理が作った情報への露出かを判定するため |
| `captured_at` | `Instant` | `datetime` | 必須 | 出典を取得した時点 | 出典取得と内容観測の時間関係を検証するため |
| `content_digest` | `Digest` | `string` | 任意 | 元データの内容が同じか機械確認できる場合に設定 | 参照先の内容変更や取り違えを検出するため |
| `fragment_locator` | `NonEmptyText` | `string` | 任意 | 発言番号、行番号、範囲など、出典内の具体的位置 | 大きな出典から採用済みの根拠に該当する箇所を一意に見つけるため |

`originator.actor_kind`（出典作成者の種類）が`codex`または`system`の出典参照だけから、採用済みの根拠を生成してはならない。`Evidence.source`へ設定する出典参照は、利用者本人が示した部分を指し、`originator.actor_kind=user`でなければならない。AI発言を前後関係として確認する場合は、新しい出典参照を`Evidence`へ追加するのではなく、`episode_id`が指す会話・作業全体から確認する。これにより、単数の`Evidence.source`を利用者本人の根拠箇所へ固定しながら、AI発言を含む前後関係も失わずに辿れる。

`source_kind`の値:

- `message`: 会話履歴内の一発言を参照する場合。発言内容がコード、自己申告、訂正、技術判断でも、置き場所が会話ならこの値を選ぶ。
- `file`: ファイルとして保存された文書、コード、設計書などを参照する場合。現在の作業中に作ったか、過去に作ったかは問わない。ファイル内の具体的位置は`fragment_locator`で示す。`artifact`（外部成果物）は「現在の会話・作業の外で作成されたもの」という意味を持つため、取得形式だけを表すこの列挙値には使わない。

同じ出典へ`message`と`file`を同時に設定しない。会話へファイル内容を貼り付けた場合、会話上の発言を根拠原文として採用するなら`message`、元ファイルを根拠原文として採用するなら`file`を選び、それぞれ別の出典参照として扱う。

### 5.7 `EntityReference`（つながりの接続先への参照）

`KnowledgeRelation`が接続する始点または終点が、知識判定用の命題と検索用索引語のどちらなのかを示す。同じ形式のIDだけではレコード種別を判別できないために必要である。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `entity_kind` | `Token` | `string` | 必須 | `assertion`または`concept` | 同じ識別子表現でも参照先のレコード種別を判別するため |
| `entity_id` | `Identifier<KnowledgeAssertion>`または`Identifier<Concept>` | `string` | 必須 | `entity_kind`と対応する識別子型 | つながりの具体的な始点・終点レコードへ到達するため |

参照先の存在と許可される組合せは`L1-M1-S2`で定義する。

## 6. レコード別データ辞書

### 6.1 `KnowledgeAssertion`（知識判定用の命題）

読む価値を判定する既存の記事から取り出した主張と、利用者本人が既に知っている可能性がある内容を同じ単位で比較するための命題である。一つの`KnowledgeAssertion`には、他の命題と分けて「利用者本人がこれを知っているか」を判定できる一つの具体的な内容だけを入れる。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `assertion_id` | `Identifier<KnowledgeAssertion>` | `string` | 必須 | この命題を一意に区別するID | 採用済みの根拠、知識状態、他の命題とのつながりから、本文変更後も同じ命題を参照するため |
| `statement` | `NormalizedText` | `string` | 必須 | 利用者本人が知っているかを単独で判定できる一つの命題。根拠の原文をそのまま複写しない | 既存の記事から取り出した主張との比較と、根拠評価の単位を固定するため |
| `language` | `LanguageTag` | `string` | 任意 | `statement`の自然言語 | 言語に応じた検索・表示・意味比較を選ぶため |
| `scope` | `Scope` | `object` | 必須 | 0件以上の適用範囲要素 | 同じ命題表現でも、技術分野、プログラミング言語、対象製品が異なる場合を分離するため |
| `temporal` | `TemporalMetadata` | `object` | 必須 | 時点や製品版に依存しない場合は、内部属性をすべて省略する | 製品版の変更や時間経過で命題の有効性が変わる場合を表すため |
| `audit` | `AuditMetadata` | `object` | 必須 | 監査情報 | 正規化済み命題が誰によりいつ作成・更新されたかを追跡するため |

レコード内規則:

- Codexによる意味判断: `statement`は複数の独立命題を箇条書きや接続詞で束ねない。
- Codexによる意味判断: `statement`は「Goを理解している」のような粗い能力ラベルではなく、真偽・適用範囲を独立評価できる表現とする。
- CLIによる機械検証は`statement`の完全一致を重複候補として返せるが、一意制約にはしない。候補が同じ意味かはCodexが判断する。
- 共通不変条件: 知識判定用の命題が存在するだけでは、その利用者本人が`known`（知っている）であることを意味しない。

### 6.2 `Concept`（検索用の索引語）

記事の主張と知識判定用の命題の文章が直接一致しない場合でも、記事や会話に現れた用語、略称、API名、識別名から関連する命題を探せるようにする索引語である。`Concept`自体は「利用者本人が何かを知っている」という命題ではなく、検索を始めるための語句である。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `concept_id` | `Identifier<Concept>` | `string` | 必須 | この検索用索引語を一意に区別するID | 代表表記が変わっても、つながりや検索機能から同じ索引語を参照するため |
| `canonical_label` | `NonEmptyText` | `string` | 必須 | 複数の表記から代表として選んだ、人が読める名称 | 検索結果で検索用索引語を人間が識別できるようにするため |
| `normalized_label` | `NormalizedText` | `string` | 必須 | 検索・比較用の代表表記 | 表記揺れを抑えた字句検索と重複候補検出を行うため |
| `aliases` | `Alias[]` | `list<object>` | 必須 | 0件以上の別名 | 略称、API名、綴り違いから同じ代表索引語へ到達するため |
| `scope` | `Scope` | `object` | 必須 | 同名の索引語が何を意味するか限定する適用範囲 | 同じ名前で意味が異なる索引語を、技術分野や対象製品ごとに区別するため |
| `audit` | `AuditMetadata` | `object` | 必須 | 監査情報 | 検索用索引語が誰によりいつ作成・更新されたかを追跡するため |

レコード内規則:

- CLIによる機械検証: `(normalized_label, scope)`が完全一致するものを重複候補として返すが、自動一意制約にはしない。候補が同じ意味かはCodexが判断する。
- CLIによる機械検証: `Concept`（検索用索引語）へ命題本文、根拠の強さ、知識状態の属性を持たせない。
- CLIによる機械検証: 別名だけが存在し、代表表記`canonical_label`がない`Concept`を許可しない。

### 6.3 `KnowledgeEpisode`（評価対象となる会話・作業のまとまり）

一つの発言だけで判断せず、前後の発言、コード変更、コマンド実行結果などを共通の前後関係でまとめて、根拠候補として評価するための範囲である。会話や作業が完了し、後続発言による訂正も含めて評価できる境界を記録するために必要である。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `episode_id` | `Identifier<KnowledgeEpisode>` | `string` | 必須 | この会話・作業範囲を一意に区別するID | 複数の根拠を同じ評価上の前後関係へ安定して関連付けるため |
| `episode_kind` | `Token` | `string` | 必須 | `conversation`または`task` | 発言だけを扱う会話と、ファイル編集等を含む作業で、出典の解釈・取得方法を切り替えるため |
| `source_locator` | `URI` | `string` | 必須 | 会話・作業全体の元データへ戻るための参照先 | 根拠断片だけで判断できない場合に、会話・作業全体へ戻るため |
| `started_at` | `Instant` | `datetime` | 必須 | 会話・作業の開始時点 | 評価範囲と出来事の順序を確定するため |
| `ended_at` | `Instant` | `datetime` | 必須 | 根拠候補を一括評価できる終了時点 | 後続の訂正を待たずに評価を開始してよい完了境界を判定するため |
| `summary` | `NonEmptyText` | `string` | 任意 | 出典そのものの代用ではない、人間向けの短い説明 | 参照先だけでは判別しにくい会話・作業を一覧上で識別するため |
| `audit` | `AuditMetadata` | `object` | 必須 | 作成・更新の記録 | 会話・作業範囲の記録が誰によりいつ作成・更新されたかを追跡するため |

レコード内規則:

- CLIによる機械検証: `started_at <= ended_at`とする。
- CLIによる機械検証: `source_locator`は一意とする。
- CLIによる機械検証: 会話・作業範囲が存在しても、根拠の保存を必須としない。保存価値があるかはCodexが判断し、保存価値のある根拠がない範囲を許容する。

`episode_kind`の値:

- `conversation`: 利用者本人とCodexの一連の発言を評価する会話のまとまり。
- `task`: 発言だけでなく、ファイル編集、コマンド実行、設計判断なども含めて評価する作業のまとまり。

### 6.4 `Evidence`（利用者本人の知識を判断する根拠）

利用者本人が命題を知っているかを判断するために採用した観測事実である。本人の発言、説明、推論、コード、訂正、判断を加工前の形で残し、Codexの推測や説明だけで本人の知識を決めないために必要である。現在の知識状態を計算し直す際の正本になる。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `evidence_id` | `Identifier<Evidence>` | `string` | 必須 | この根拠を一意に区別するID | 個々の観測を、知識状態の計算、訂正、履歴から安定して参照するため |
| `assertion_id` | `Identifier<KnowledgeAssertion>` | `string` | 必須 | この根拠が評価対象とする命題のID | 加工前の利用者表現が、どの命題を支持・反証・限定するかを明示するため |
| `evidence_kind` | `Token` | `string` | 必須 | `explanation`、`reasoning`、`code`、`correction`、`knowledge_self_report`、`technical_decision`のいずれか | 観測形式に応じて根拠の解釈と強さを評価するため |
| `stance` | `Token` | `string` | 条件付き | `evidence_kind=knowledge_self_report`以外では必須とし、命題の正しさに対して`supports`、`challenges`、`qualifies`のいずれか。`knowledge_self_report`では省略する | 利用者本人が示した内容が命題を支持・反証・限定するどの向きかを表し、本人が知っているかという申告とは別の判断軸にするため |
| `knowledge_report` | `Token` | `string` | 条件付き | `evidence_kind=knowledge_self_report`では必須とし、`reports_known`、`reports_unknown`、`recognizes`、`reports_experience`のいずれか。それ以外では省略する | 命題の正しさへの向きと混同せず、利用者本人が自分の知識について何を申告したかを区別するため |
| `strength` | `Token` | `string` | 必須 | `strong`（強い）、`moderate`（中程度）、`weak`（弱い）のいずれか | 知識状態を計算するとき、各根拠が対象命題についての利用者本人の知識状態をどの程度明確に示すかを同じ尺度で比較するため |
| `raw_content` | `NonEmptyText` | `string` | 必須 | 利用者本人が示した加工前の発言、コード、訂正、判断。整理済みの命題で置き換えない | 命題への整理に誤りがあった場合や根拠同士が矛盾した場合に、加工前の利用者表現から再評価するため |
| `content_language` | `LanguageTag` | `string` | 任意 | `raw_content`の自然言語 | 原文の検索・表示・意味解析に適切な言語処理を選ぶため |
| `source` | `SourceReference` | `object` | 必須 | 出典と、評価対象となった会話・作業への参照 | 加工前の内容を提示した主体、出典内の位置、前後関係、取得時点まで遡るため |
| `temporal` | `TemporalMetadata` | `object` | 必須 | `observed_at`を必須とし、必要に応じて有効期間・製品版を持つ | 観測時点と適用製品版を基に、根拠の鮮度・有効性を再評価するため |
| `audit` | `AuditMetadata` | `object` | 必須 | 作成・更新の記録 | 根拠レコード自体が誰によりいつ登録・更新されたかを追跡するため |

レコード内規則:

- CLIによる機械検証: `temporal.observed_at`は必須であり、`source.captured_at`以前でなければならない。
- Codexによる意味判断: `source.originator.actor_kind=user`（出典の作成・提示者が利用者本人）であり、出典情報から利用者本人が作成したと確認できる内容は根拠候補になり得る。`source_kind=file`で現在の会話・作業の外にある外部成果物を指す場合でも、現在の会話で再確認することを必須としない。
- Codexによる意味判断: 作成者不明、第三者作成、Codex・AI生成の内容は、読み込んだだけでは利用者本人の知識の根拠候補にしない。利用者本人による説明、訂正、技術判断などを別に観測できた場合は、その本人の行為を根拠候補にできる。
- Codexによる意味判断: 質問文であることだけを`stance=challenges`または`knowledge_report=reports_unknown`に対応付けない。
- Codexによる意味判断: 利用者本人が対象命題を「知らない」と明示した根拠は、`evidence_kind=knowledge_self_report`、`knowledge_report=reports_unknown`、`strength=moderate`とし、`stance`は設定しない。`strength`は申告が明確であることを示し、知識を持っていることを示す値ではない。
- Codexによる意味判断: 利用者本人が命題の正しさを否定した場合は`stance=challenges`、その命題を知らないと申告した場合は`knowledge_report=reports_unknown`として別の属性へ記録する。`reported_unknown`の根拠に使えるのは、`raw_content`に知識がないという本人の明示申告がある場合だけである。
- Codexによる意味判断: AIの説明を`raw_content`として登録しない。利用者本人による承認、否定、説明、コード、訂正などを分離して記録する。
- Codexによる意味判断: `strength`は一件の根拠が、対象命題についての利用者本人の知識状態をどれほど明確に示すかである。知識がある方向だけを測る値ではなく、利用者本人の熟達度や、知識状態分類の確かさを示す`confidence`でもない。
- CLIによる機械検証は、同一出典断片から同一命題へ同じ`evidence_kind`、`stance`、`knowledge_report`で作られた根拠を重複候補として返す。省略された条件付き属性は空値として比較する。最終的な重複防止・再試行規則は`L1-M1-S4`で定義する。

`evidence_kind`の値:

- `correction`: 利用者本人が以前の説明・判断の誤りを明示し、正しい内容へ直した場合。訂正の中に説明や推論が含まれていても、訂正行為を記録するためこの値を優先する。
- `technical_decision`: 利用者本人が技術上の複数案を比較し、採用案または却下案と理由を示した場合。単なる仕組みの説明は`explanation`、前提から結論を導くだけで選択を行わない場合は`reasoning`とする。
- `reasoning`: 利用者本人が前提から結論へ至る考え方を示した場合。明示的な訂正または技術上の選択を行っている場合は、それぞれ`correction`または`technical_decision`を選ぶ。
- `explanation`: 利用者本人が仕組み、意味、条件を自分の言葉で説明した場合。前提から結論までの推論過程が主な観測対象なら`reasoning`を選ぶ。
- `code`: 利用者本人が作成・提示したコードそのものを主な観測対象にする場合。コードに添えた訂正・判断・推論も別々に根拠とする必要がある場合は、出典内の対象範囲を分けて別の`Evidence`として記録する。
- `knowledge_self_report`: 利用者本人が「知っている」「知らない」「経験がある」と明示的に申告した場合、または「goroutine leakですよね」のように用語・概念を認識していることだけを短く示した場合。説明・推論・コード・訂正・技術判断を示している場合は、それぞれ対応する分類を選ぶ。

一つの出典断片が複数の分類条件を満たす場合は、上記の説明に従って主な観測行為を一つ選ぶ。異なる行為をそれぞれ根拠として残す必要がある場合は、`fragment_locator`で対象範囲を分け、複数の`Evidence`として記録する。この分類は文章やコードの意味を読む必要があるためCodexが行い、CLIは許可値かどうかだけを検証する。

`stance`（根拠が命題へ与える向き）は、採用済みの根拠が命題の正しさを支持・反証・限定するかだけを表す。利用者本人がその命題を知っているかという申告には使わない:

- `supports`: 利用者本人が示した説明、推論、コード、判断などが、対象命題が正しいことを支持する場合。
- `challenges`: 利用者本人が対象命題への反例、否定、矛盾を示す場合。対象命題を「知らない」と申告した場合には使わない。
- `qualifies`: 条件、例外、適用範囲を加え、命題を限定する。

`knowledge_report`（知識に関する本人申告の内容）は、`evidence_kind=knowledge_self_report`の場合だけ使用する:

- `reports_known`: 利用者本人が対象命題を知っている、または理解していると明示した場合。短い用語認識だけの場合は使わない。
- `reports_unknown`: 利用者本人が対象命題を知らないと明示した場合。単なる質問、確認依頼、説明依頼には使わない。
- `recognizes`: 「goroutine leakですよね」のように、用語や概念を認識していることだけを短く示した場合。理解しているという明示申告や説明がある場合には使わない。
- `reports_experience`: 利用者本人が対象技術・事象を使った、実施した、遭遇した経験を明示したが、対象命題の理解までは説明していない場合。経験から何を理解しているかは`L1-M1-S3`で根拠内容を評価する。

単なる質問は、いずれの`knowledge_report`にも分類して採用済みの根拠にしない。本人申告と同じ断片に説明、推論、コード、訂正、技術判断が含まれ、そちらを主な観測対象にできる場合は、対応する`evidence_kind`と`stance`を使用する。

`knowledge_report=reports_known`、`reports_unknown`、`reports_experience`は明示的な本人申告なので、申告単体の`strength`は`moderate`とする。`knowledge_report=recognizes`は理解の深さを確認できないため`weak`とする。経験の申告が`moderate`であっても、対象命題を理解していることや`known`を直接意味しない。どの状態へ導くかは、申告内容と他の根拠を合わせて`L1-M1-S3`で定義する。

`strength`（根拠の強さ）は、一件の採用済みの根拠が、対象命題についての利用者本人の知識状態をどれほど明確に示すかを表す。知っているという根拠だけでなく、知らないという明示申告にも同じ尺度を使う:

- `strong`: 利用者本人が対象知識を使って正しく説明・推論した場合、またはその知識を前提に妥当なコード等を提示した場合。理由や適用条件を示していれば判断材料になるが、両方を必須条件にはしない。
- `moderate`: 利用者本人が「それは知っています」または「それは知りません」など、対象知識の有無を明示的に自己申告した場合。知っているという申告について正しい適用・判断を確認できる場合は、内容に応じて`strong`を選べる。
- `weak`: 用語や概念を認識していることは分かるが、理解の深さを確認できない短い応答の場合。例:「goroutine leakですよね」。明示的な知識の自己申告は`moderate`であり、ここへ含めない。

具体的な分類規則と、複数の根拠を組み合わせる規則は`L1-M1-S3`で定義する。

### 6.5 `DerivedKnowledgeState`（採用済みの根拠から計算した現在の知識状態）

知識記録領域に保存した一つの`KnowledgeAssertion`（知識判定用の命題）について、集めた根拠から計算した利用者本人の現在の知識状態である。検索のたびに同じ根拠を読み直して評価しなくても結果を取得できるようにするために必要である。根拠から再計算できるため正本ではなく、計算結果を一時保存または永続保存してよい。既存の記事から取り出した`ArticleClaim`（記事から取り出した主張）自体をこのレコードへ保存するのではない。後続の知識検索処理がArticleClaimと保存済み命題を比較し、同じ8状態の言葉を使って評価結果を作る。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `state_id` | `Identifier<DerivedKnowledgeState>` | `string` | 必須 | 保存した計算結果を一意に区別するID | 現在の知識状態を更新・参照したり、根拠追加後に古い結果として無効にしたりする対象を識別するため |
| `assertion_id` | `Identifier<KnowledgeAssertion>` | `string` | 必須 | 状態を評価した命題のID | どの具体的な命題についての知識状態かを一意に特定するため |
| `status` | `Token` | `string` | 必須 | `known`、`partially_known`、`inferable`、`contradicted`、`outdated`、`reported_unknown`、`no_evidence`、`uncertain`のいずれか。各意味は直後に定義する | 保存済み命題について、既知・部分既知・推論可能・矛盾・製品版や時点の差・本人による不知の申告・未観測・判定不能を区別し、記事から取り出した主張との比較に再利用するため |
| `confidence` | `Decimal01` | `float` | 必須 | 選んだ`status`（知識状態の分類）がどれだけ確かか。利用者本人の熟達度ではない | 同じ知識状態でも、再確認が必要な度合いが異なることを表すため |
| `evidence_ids` | `Identifier<Evidence>[]` | `list<string>` | 必須 | この状態の計算で実際に使用した採用済みの根拠ID。評価対象または関連する命題の根拠を指せる。`no_evidence`では0件、それ以外では1件以上とし、同じIDを重複させない | 計算結果の理由を文章だけにせず、判断をやり直す正本である具体的な根拠まで機械的に遡るため |
| `known_aspects` | `NonEmptyText[]` | `list<string>` | 必須 | 観測できた既知部分。0件以上、同一要素を重複させない | `partially_known`で既に説明不要な部分を特定するため |
| `knowledge_gaps` | `NonEmptyText[]` | `list<string>` | 必須 | 観測できない、または不足する部分。0件以上、同一要素を重複させない | 記事で補うべき具体的な不足部分を特定するため |
| `rationale` | `NonEmptyText` | `string` | 必須 | どの根拠から、なぜこの状態と既知・不足部分を導いたかの説明。根拠自体の代用ではない | 状態と既知・不足範囲の判断理由を、人が採用済みの根拠まで遡って検証できるようにするため |
| `evaluated_at` | `Instant` | `datetime` | 必須 | この知識状態を計算した時点 | 根拠追加後に計算結果が古くなっていないか判定するため |
| `temporal` | `TemporalMetadata` | `object` | 必須 | `observed_at=evaluated_at`とし、時点・製品版の差を保持可能にする | 時点・製品版ごとに異なる知識状態を混同しないため |
| `audit` | `AuditMetadata` | `object` | 必須 | 監査情報 | 導出結果が誰によりいつ保存・更新されたかを追跡するため |

レコード内規則:

- CLIによる機械検証: 同一`assertion_id`について現在状態は最大1件とする。履歴表現は`L1-M1-S4`で定義する。
- CLIによる機械検証: `status=partially_known`では`known_aspects`と`knowledge_gaps`を各1件以上必要とする。
- 共通不変条件: `status=inferable`を`known`へ自動変換しない。
- 共通不変条件: `status=no_evidence`は「unknown」を意味せず、`confidence`も未知度を意味しない。
- Codexによる意味判断: `status=reported_unknown`では、`evidence_ids`が指す根拠のうち1件以上を、`evidence_kind=knowledge_self_report`かつ`knowledge_report=reports_unknown`であり、利用者本人が対象命題を知らないと明示した根拠とする。質問、AIによる説明、情報への露出、根拠の不在からは設定しない。
- `evidence_ids`は計算時に実際に使用した根拠だけを指す。参照先の存在確認は`L1-M1-S2`、どの根拠を採用してこの一覧へ入れるかは`L1-M1-S3`で定義する。
- このレコードの保存・更新は採用済みの根拠を変更、削除、置換しない。根拠の競合解決、再計算、無効化の規則は`L1-M1-S3`で定義する。

`status`の値:

- `known`: 評価対象の命題そのもの、または意味が実質的に同じ知識を利用者本人が持っていると判断できる強い根拠がある。
- `partially_known`: 評価対象の命題を構成する一部の知識は根拠から確認できるが、命題全体を理解しているとは判断できない。
- `inferable`: 評価対象の命題を導くために必要な前提知識は根拠から確認できるが、その命題自体を利用者本人が明示的に認識している直接の根拠はない。
- `contradicted`: 評価対象の命題と矛盾する理解を、利用者本人が持っていると判断できる根拠がある。評価対象の命題を支持する根拠と否定する根拠が競合して状態を確定できない場合は`uncertain`とする。
- `outdated`: 評価対象の命題と同じ主題について利用者本人の知識を示す根拠はあるが、その知識と評価対象の命題に製品版または時点の差がある。
- `reported_unknown`: 利用者本人が評価対象の命題を知らないと直接述べ、その本人申告を採用済みの根拠にした。命題と矛盾する理解を持つ`contradicted`、根拠がない`no_evidence`、状態を確定できない`uncertain`とは区別する。
- `no_evidence`: 必要な探索を行っても、利用者本人が評価対象の命題を知っているとも知らないとも判断できる採用済みの根拠がない。利用者本人が知らないという意味ではない。
- `uncertain`: 根拠同士が矛盾する場合を含め、根拠の強さ、内容、適用範囲の不足や競合により他の状態へ確定できない。

### 6.6 `KnowledgeRelation`（命題・検索用索引語の間のつながり）

命題同士、検索用索引語同士、または命題と検索用索引語の間にある、前提、因果、矛盾、置換などのつながりを記録する。記事の語句と命題の文章が一致しなくても、つながりを辿って関連情報を探すために必要である。このつながりが保存されているだけでは、利用者本人がその関係を理解している証拠にはならない。

| 属性 | 論理型 | プログラム上の基礎型 | 必須性 | 制約・意味 | 必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `relation_id` | `Identifier<KnowledgeRelation>` | `string` | 必須 | このつながりを一意に区別するID | 個々のつながりを更新・参照・重複判定の対象として識別するため |
| `source` | `EntityReference` | `object` | 必須 | 向きを持つつながりの始点 | どの命題または検索用索引語から辿り始めるかを明示するため |
| `target` | `EntityReference` | `object` | 必須 | 向きを持つつながりの終点 | 始点からどの命題または検索用索引語へ到達するかを示すため |
| `relation_kind` | `Token` | `string` | 必須 | 前提、因果、矛盾、置換など、つながりの種類。正式な許可値は`L1-M1-S2`で定義する | 何を意味するつながりか、どちら向きに辿るかを選択するため |
| `scope` | `Scope` | `object` | 必須 | つながりが成立する技術分野・プログラミング言語・対象製品 | 文脈によって成立・不成立が変わるつながりを混同しないため |
| `temporal` | `TemporalMetadata` | `object` | 必須 | つながりが成立する時点・製品版の範囲 | 製品版の変更や置換で失効したつながりを現在も辿らないため |
| `audit` | `AuditMetadata` | `object` | 必須 | 作成・更新の記録 | つながりが誰によりいつ作成・更新されたかを追跡するため |

レコード内規則:

- CLIによる機械検証: `source`と`target`はそれぞれ完全な`EntityReference`でなければならない。
- 始点と終点が同じになるつながりを許可するか、左右を入れ替えても意味が同じつながりをどちら向きで保存するか、逆向きのつながりを別に保存するか、重複を許可するか、どのレコード種別同士を接続できるかは`L1-M1-S2`で確定する。
- Codexによる意味判断: 利用者本人がそのつながりを理解している事実を表す場合は、その内容を独立した知識判定用の命題と採用済みの根拠で表現する。

つながりの種別の候補名は、`related_to`（関連する）、`prerequisite`（前提になる）、`causes`（原因になる）、`contributes_to`（一因になる）、`contradicts`（矛盾する）、`supersedes`（新しい内容が古い内容を置き換える）である。どの種別を正式採用するか、どちら向きに接続するかは`L1-M1-S2`で定義する。

## 7. レコード内一意性・候補キー一覧

| 対象 | 主キー | 一意または重複候補となるキー | 判定 |
| --- | --- | --- | --- |
| `KnowledgeAssertion` | `assertion_id` | `(statement, scope)` | 意味的重複候補。自動一意にしない |
| `Concept` | `concept_id` | `(normalized_label, scope)` | 意味的重複候補。自動一意にしない |
| `KnowledgeEpisode` | `episode_id` | `source_locator` | 一意 |
| `Evidence` | `evidence_id` | `(assertion_id, source.source_locator, source.fragment_locator, evidence_kind, stance, knowledge_report)` | 再試行・重複候補。条件付き属性の省略は空値として比較する。論理効果は`L1-M1-S4` |
| `DerivedKnowledgeState` | `state_id` | `assertion_id` | 現在状態として一意 |
| `KnowledgeRelation` | `relation_id` | 始点、終点、つながり種別の組 | 重複可否と、同じつながりを一つの表現へ揃える規則は`L1-M1-S2` |

候補キーは、同じ内容かもしれないレコードを見つけるために比較する属性の組である。候補キーが一致しただけで同一レコードとは確定しない。データベースやコマンドライン処理で機械的に検証できる重複禁止と、Codexが意味を読んで判断する重複候補を区別する。

## 8. スキーマ全体で常に守る規則

1. `Evidence`（採用済みの根拠）が正本であり、`DerivedKnowledgeState`（計算済みの知識状態）は根拠を置換しない。
2. 命題、検索用索引語、つながりが保存されているだけでは、利用者本人がそれを知っていることを意味しない。
3. `DerivedKnowledgeState.status=reported_unknown`は、利用者本人が対象命題を知らないと明示した採用済みの根拠がある場合だけ使用する。質問、AIによる説明、情報への露出、根拠の不在から設定しない。
4. `DerivedKnowledgeState.status=no_evidence`は根拠を観測していないことを表し、`reported_unknown`と同一視しない。
5. `DerivedKnowledgeState.status=inferable`と`known`を同一視しない。
6. AIが作成した出典だけで採用済みの根拠を作成しない。利用者本人が情報を見たというだけで、知識を得たと扱わない。
7. 加工前の利用者表現は`Evidence.raw_content`（根拠の原文）、知識判定用に整理した命題は`KnowledgeAssertion.statement`（命題本文）へ分離する。
8. 知識記録領域は一人の利用者本人だけを対象とし、複数利用者の登録・切替・共有を表すレコードや属性を持たない。
9. 時点情報がないことを「現在も有効」と推定せず、製品版や時点を観測していないものとして扱う。
10. `Concept`と`Alias`は検索用の索引語であり、「初心者」「上級者」などの能力評価や知識状態を保持しない。
11. 論理スキーマは、特定のデータベース製品、文章を数値化する仕組み、検索用ライブラリ、JSON表現に依存しない。
