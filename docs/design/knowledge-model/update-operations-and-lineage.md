# Knowledge更新操作の事前・事後条件と履歴系譜

## 1. 目的

本書は、`KnowledgeStore`（利用者本人が示した知識の根拠と、その評価結果を保存する領域）へ変更を加える4種類の操作、`create`（新しい知識判定用命題を作る）、`attach-evidence`（既存命題へ採用済み根拠を加える）、`revise`（同じ対象の表現・適用条件・記録内容を訂正する）、`supersede`（古い命題を残して新しい命題から置換関係を張る）の論理契約を定義する。

論理契約とは、特定のデータベース製品やJSON（項目名と値で表すデータ交換形式）に依存せず、操作前に必要な条件、成功後に必ず成立する条件、失敗・再試行時に守る条件、変更前後を追跡する履歴の意味を定めた規則である。この契約が必要なのは、利用者本人が実際に示した`Evidence`（採用済みの根拠）を失わず、同じ要求の再試行で重複を作らず、古い`DerivedKnowledgeState`（根拠から計算した知識状態）を現在値として誤って返さないためである。

本書の固定入力は、[原典Issue #1](https://github.com/yukihito-jokyu/knowledge/issues/1)、計画を固定したCommit（Gitによる変更履歴の保存単位）`9bf911b9122bf4ec51ec48312cc310de29bfcdff`の[作業構成表](../../task-map.md)と[作業間接続表](../../task-connections.md)、直接の先行成果物である[Knowledge論理関連と参照整合性制約](./relations-and-integrity.md)と[Evidence由来Stateの整合性・導出契約](./evidence-derived-state.md)である。両成果物が共通して参照する[Knowledge論理スキーマ](./logical-schema.md)も、属性名と不変条件の定義元として使用する。

[設計判断記録](../../task-decomposition-decisions.md)の決定004、034から037、041を確認した。固定計画時点では知識状態が7種類だったが、決定041で`reported_unknown`（利用者本人が知らないと直接述べた状態）を加えた8種類へ承認済みで変更された。既存7種類の意味、依存関係、Gate（後続作業を開始してよいかを判定する通過条件）、成果物Owner（ファイルを変更する責任を持つ作業）は変わっていないため、本書は8状態を現在の確定入力として使用する。

## 2. 適用範囲と変えない境界

### 2.1 本書で確定すること

- 4種類の更新操作を選ぶ境界
- 操作共通および操作別の事前条件・事後条件
- 同じレコードとしてIDを保つ変更と、新しいIDを必要とする変更の境界
- 複数レコードを一つの操作で変える場合の不可分性
- 同じ要求の再試行、意味上の重複、同時更新競合の扱い
- 変更前後、決定主体、実行主体、操作時点、失敗した試行を追跡する履歴系譜
- 状態再計算中に古い状態を返さない論理表現

### 2.2 本書で選び直さないこと

| 確定事項 | 本書で変えない理由 |
| --- | --- |
| `Evidence`が正本で、`DerivedKnowledgeState`が再計算可能な導出物である | 根拠から現在状態を説明し直せることが原典の中核であり、導出結果で根拠を上書きできないため |
| 質問、AIの説明、情報を見た事実、根拠の不在だけでは利用者本人の既知・未知を決めない | 利用者本人の観測事実がない推測を知識記録へ混入させないため |
| `reported_unknown`を含む8種類の知識状態 | 決定041と先行成果物で確定済みであり、更新処理は状態の意味を追加・変更しないため |
| `supersedes`は新しい命題から古い命題への有向関係であり、自己参照と循環を禁止する | 新旧順序を逆転させず、旧命題へ戻れる系譜を保つため |
| `Evidence`を物理削除せず、参照中レコードの物理削除と連鎖削除を行わない | 出典、訂正前の観測、旧状態へ遡れることを守るため |
| Codexが意味を判断し、CLIが形式・参照・重複・不可分な保存を機械検証する | 文章の意味を文字列一致へ置き換えず、同じ形式入力へ決定的な検証を返すため |

### 2.3 後続作業へ委ねること

本書はコマンド名、引数、JSONの項目名、データベースの表・列・索引、Transaction（複数変更をまとめて確定または取消する仕組み）の実装方法を決めない。これらは`L1-M2`以降が、本書の論理効果を変えない形で定義する。

本書が定義する`operation_id`、変更前後のSnapshot（ある時点の完全な値）、現在状態の選択情報は、保存形式の指定ではない。後続が異なる表や文書へ分けても、同じ操作を一意に識別でき、完全な変更前後へ遡れ、古い状態を現在値として返さないなら契約を満たす。

## 3. 用語と責務

| 用語 | 本書での意味 | 必要な理由 |
| --- | --- | --- |
| Codex | 会話・作業内容の意味を読み取り、更新候補の同一性、根拠採用、操作選択を判断するAI側の処理主体 | 形式検証だけを行うCLIへ、文章の意味判断を誤って持ち込まないため |
| CLI（Command Line Interface／コマンドライン操作窓口） | Codexから明示的なコマンドと値を受け、決定的な検証・保存・取得を行うKnowledge CLI | 同じ形式入力へ同じ機械検証結果を返し、AI判断と永続化を分離するため |
| ID（Identifier／識別子） | 命題、根拠、状態、関係、操作、Revision等の一件を他の一件と区別して参照する値 | 名前や本文が変わっても対象と履歴を安定して結び付けるため |
| `KnowledgeAssertion`（知識判定用命題） | 「利用者本人がこの内容を知っているか」を独立して評価できる粒度へ正規化した一つの内容 | 粗い分野ラベルではなく、検索対象と知識状態の単位を固定するため |
| `Evidence`（採用済み根拠） | 命題について利用者本人の知識を判断するため採用した、本人の発言、説明、コード、訂正、判断 | AIの説明や単なる閲覧を本人の知識と誤認せず、状態を再計算できる正本を残すため |
| `DerivedKnowledgeState`（導出知識状態） | 採用済み根拠から計算した、命題一件に対する8種類の知識状態の一つ | 根拠そのものと再計算可能な現在評価を分離するため |
| `KnowledgeRelation`（知識関係） | 命題・概念等の二つのレコード間に、前提、矛盾、置換等の向きと種類を付けた接続 | 個別レコードを上書きせず、検索経路と新旧系譜を表すため |
| 操作要求 | 4種類の一つ、対象ID、変更したい論理値、変更理由、想定する変更前の版を一組にした要求 | 一回の意図を、個別の保存命令や再試行回数と区別するため |
| 論理遷移 | 操作前に成立していたレコードと現在状態選択が、一つの操作結果によってどのレコードと選択へ変わるかの対応 | 操作名だけから変更対象や保持対象を推測せず、部分変更を検出するため |
| `operation_id`（操作識別子） | 一つの論理的な操作要求へ、最初の試行から全再試行まで同じ値を付けるID | 応答を受け取れなかった再試行でも、同じ変更を二重適用しないため |
| Request fingerprint（要求照合値） | 操作種別、対象、変更内容、変更前提を正規化した後に求める内容照合値 | 同じ`operation_id`へ別内容を誤って再利用したことを機械的に検出するため |
| 冪等性 | 同じ操作要求を繰り返しても、最初に確定した後は論理結果が増減しない性質 | 通信切断や処理再開による命題・根拠・関係の重複を防ぐため |
| 論理的同一性 | 表記が変わっても「利用者本人がこれを知っているか」を同じ一件として評価する対象であること | `revise`でIDを保つ場合と、`supersede`で新しいIDを作る場合を分けるため |
| Revision（版） | 同じレコードIDについて、ある操作の直前または直後に成立していた完全な論理値 | 現在値だけでなく、訂正前の値と変更順序へ戻るため |
| Revision ID（版識別子） | 一つの不変なRevisionを指すID。業務上のレコードIDとは別 | 同じレコードのどの時点を前提に更新したかを機械的に比較するため |
| Snapshot（値の写し） | そのRevisionにおける全必須値と存在する任意値を省略せず保持した値 | 差分だけでは復元できない旧値を、後から正確に検証するため |
| 現在Revision | 一つの業務上のレコードIDについて、通常の取得で返してよい最新のRevision一件 | 履歴として残す旧版と、更新対象にする現在値を混同しないため |
| 系譜 | 操作ID、変更前Revision、変更後Revision、`supersedes`関係を辿って、新旧の成立経緯へ戻れるつながり | 訂正や統合・分割の後も、旧命題と旧根拠を失わないため |
| 不可分な変更 | 一組の変更が全部成功するか、外部から利用可能な現在値としては一件も成功しない性質 | 命題だけ存在して根拠がない、または関係だけ存在して参照先がない途中状態を防ぐため |
| 現在状態選択 | 一つの命題について、現在利用可能な`DerivedKnowledgeState`一件を示すか、再計算が必要で利用不可と示す情報 | 再計算中を8状態のいずれかへ誤変換せず、古い状態を返さないため |
| No change（変更なし） | 要求は妥当だが、目的の論理効果が既に存在しており新しい値を作らなかった結果 | 再試行成功と入力不正を区別し、重複を増やさず既存結果を返すため |
| Reject（拒否） | 前提違反、意味判断不足、同時更新競合、誤った操作選択により、論理変更を一件も適用しなかった結果 | 変更なしの正常結果や、一時的な実行失敗と区別するため |
| `ActorReference`（行為主体への参照） | 内容を決めた利用者本人・Codex・自動処理のいずれかを示す、先行スキーマの共通項目 | 意味を決めた主体と、決定済み内容を保存した処理を区別するため |
| `AuditMetadata`（作成・更新の記録） | 現在のレコード内容を誰がいつ成立させ、最後に変更すると決めたかを示す先行スキーマの共通項目 | 操作の試行履歴とは別に、現在値の内容決定へ遡るため |
| `scope`（適用範囲） | 命題や根拠が成り立つ技術分野、プログラミング言語、対象製品等の条件 | 同じ文でも別分野・別製品なら異なる評価対象になり得るため |
| `temporal`（時点・製品版情報） | 有効期間、適用製品版、観測・確認時点を表す`TemporalMetadata` | 世界上の有効時点と、保存操作を行った時点を混同しないため |
| Candidate（更新候補） | 完了済みの会話・作業から抽出した、まだ永続化すると決めていない命題と根拠の候補 | 候補抽出だけで知識記録を増やさず、既存命題との比較後に4操作または更新なしを選ぶため |

### 3.1 継承する8種類の知識状態

更新操作は状態の選択条件を変更しないが、再計算前後を説明するため、先行する導出契約から次の意味を継承する。8種類を列挙するのは、再計算中を別の知識状態へ誤って割り当てないためである。十分条件、禁止条件、根拠の競合解決は[Evidence由来Stateの整合性・導出契約](./evidence-derived-state.md)に従う。

| `status` | 日本語での意味 | 更新契約で区別する理由 |
| --- | --- | --- |
| `known` | 対象命題そのものを知っている | 強い直接根拠が更新された場合だけ、再計算後の正式な結果として公開するため |
| `partially_known` | 対象命題を構成する一部を知っている | 既知部分と不足部分を旧Snapshotから追跡できるようにするため |
| `inferable` | 前提から導けるが、対象自体を知っているとは確認していない | 前提根拠の変更後も自動的に`known`へ変換しないため |
| `contradicted` | 対象命題と両立しない理解を持っている | 根拠の訂正・競合解消による状態変更を、旧根拠を消さず追跡するため |
| `outdated` | 同じ主題の知識はあるが、現在の時点・製品版に合わない | `supersede`した事実だけで自動設定せず、根拠評価後に選ぶため |
| `reported_unknown` | 利用者本人が対象命題を知らないと直接述べた | 質問や根拠不在から推測せず、明示申告を含む再計算結果としてだけ公開するため |
| `no_evidence` | 必要な探索後も、状態判断へ採用できる根拠がない | 再計算未完了や「利用者が知らない」という意味へ読み替えないため |
| `uncertain` | 根拠はあるが、他の7状態へ確定できない | 再計算処理の失敗ではなく、根拠評価後も競合や不足が残る正式な結果として区別するため |

### 3.2 CodexとCLIの責務分離

責務は次のとおり分離する。

- **Codexによる意味判断**: 命題が既存命題と同じ意味か、同じIDの訂正でよいか、新旧の独立命題として残すべきか、根拠を採用できるか、どの範囲の状態を再計算するかを決める。判断理由と参照した根拠を操作要求へ含める。
- **CLIによる機械検証と保存**: 必須値、許可値、参照先、想定Revision、重複キー、`supersedes`循環、Request fingerprint、不可分性を検証し、Codexが決めた変更を追加の意味推測なしに保存する。
- **保存実行主体**: CLI等の自動処理は、Codexが決めたレコード内容の`AuditMetadata.updated_by`を自分へ置き換えない。一方、操作試行履歴の`executed_by`には、実際に保存を試みた自動処理を記録する。内容の決定者と保存実行者を混同しないためである。

## 4. 更新履歴が保持する論理情報

### 4.1 `KnowledgeUpdateOperation`（一つの操作要求の確定記録）

`KnowledgeUpdateOperation`は、一つの`operation_id`に対して最大一件だけ作る、確定後に上書きしない履歴である。保存方式は後続が決めるが、論理的に次の情報をすべて保持する。

| 属性 | 必須性・存在条件 | 意味、許可値、禁止値 | 類似属性との違い | 必要な理由 |
| --- | --- | --- | --- | --- |
| `operation_id` | 必須 | 構文上有効で、`KnowledgeUpdateOperation`の主識別子として未使用の操作ID。同じIDのAttemptが先に存在することは許可する。空値、不正形式、二件目のOperationへの再利用、確定後の変更を禁止する | `attempt_id`が一回の保存試行を分けるのに対し、これは最初の要求から全再試行と終端結果まで同じ値を使う | 同じ意図の全試行と確定結果を一つに関連付け、二重適用を防ぐため |
| `operation_kind` | 必須 | `create`、`attach-evidence`、`revise`、`supersede`のいずれか。空値、列挙外の操作、再計算を第5の操作として設定すること、確定後の変更を禁止する | `result`が操作の終わり方を示すのに対し、これは要求した論理変更の種類を示す | 公開する更新操作を4種類へ固定し、操作別の事前・事後条件を選ぶため |
| `request_fingerprint` | 必須 | 第10.1節の全意味要素を正規化して計算した照合値。空値、部分的な要求からの推測値、同じIDの先行Attemptと異なる値、確定後の変更を禁止する | `operation_id`が呼出側の相関値であるのに対し、これはそのIDに結び付いた要求内容が同じかを検証する値である | 同じIDに異なる要求を混ぜず、同一要求の安全な再試行を判定するため |
| `decided_by` | 必須 | 意味上の変更内容を決めた有効な`ActorReference`。先行スキーマどおり`actor_kind`は`user`、`codex`、`system`のいずれかとし、未知値と条件に反する`actor_id`を禁止する。CLIがCodexの判断を保存しただけなら`system`への置換を禁止する | `executed_by`が終端保存を実行した主体であるのに対し、こちらは操作選択、同一性、根拠採用、影響範囲を決めた主体である | 保存処理とは別に、変更内容の判断責任へ遡るため |
| `decision_rationale` | 必須 | 操作選択、論理的同一性、根拠の採否、影響範囲を検証できる空でない説明。定型語だけ、秘密値、根拠原文の無目的な複写、処理障害だけの説明を禁止する | Attemptの`diagnostic`が一試行の処理結果、`result_reason`が終端結果の理由を示すのに対し、これは変更内容を選んだ意味上の理由である | 文字列一致や操作名だけでは再現できない意味判断を監査するため |
| `requested_at` | 必須 | このOperationの`request_fingerprint`と一致する最初のAttemptの`received_at`と同じ時点で、`completed_at`以前。空値、照合値を計算できなかった拒否Attemptや後続再試行の受信時点、確定後の書換えを禁止する | Attemptの`received_at`が試行ごとに異なるのに対し、これは照合可能になった論理要求全体で一つの開始時点である | 再試行が増えても、同じ内容の意図を最初に受理した時点と全体所要期間を保つため |
| `expected_revisions` | 必須 | 全更新対象について、許可されたレコード種別、業務ID、現在と想定するRevision IDを重複なく列挙する。新規IDはRevision IDの代わりに「存在しないこと」を明示する。空一覧、対象の欠落、異種ID、同一対象の重複、現在Revisionを未確認の値で代用することを禁止する | `record_changes`が確定後の実変更を指すのに対し、これは保存前に一致していなければならない比較条件である | 読み取った後に別操作が変更した値を、古い判断で上書きしないため |
| `affected_assertion_ids` | 必須 | 状態再計算または現在状態無効化の対象とした、存在する命題IDの重複しない一覧。影響がないとCodexが判断した操作だけ空一覧を許可し、別種ID、重複、未検討を空一覧で表すことを禁止する | `result_references`が呼出側へ返す成果を示すのに対し、こちらは直接変更していない関連命題も含む再計算範囲である | 関連命題の古い状態を見落とさず、影響範囲の判断を再検証するため |
| `record_changes` | 必須 | 第4.3節の不変な`RecordChange`を指す、同じ`operation_id`に属する重複しない`change_id`の成立順一覧。`committed`では1件以上、`no_change`と`rejected`では空とし、別操作の変更、重複、Snapshotの独自コピーを禁止する | Attemptの`record_change_ids`が一試行分だけを指すのに対し、これは全試行で確定した知識レコード変更を一度ずつ集約する | 終端結果から完全な前後値へ戻り、複数試行に分かれた変更も成立順に追跡するため |
| `state_publication_changes` | 必須 | 第4.4節の不変な`StatePublicationChange`を指す、同じ`operation_id`に属する重複しない`publication_change_id`の成立順一覧。対象がなければ空とし、別操作の変更、重複、選択Snapshotの独自コピーを禁止する | `record_changes`が知識レコードの版変更を集約するのに対し、これは状態を返してよいかという選択変更だけを集約する | 古い状態をいつ利用不可にし、どの再計算結果をいつ公開したか試行横断で追跡するため |
| `result` | 必須 | `committed`、`no_change`、`rejected`のいずれか。空値、列挙外、Attemptだけが使う`replayed`、`recalculation_required`、`failed`、確定後の変更を禁止する | Attemptの`result`が途中・再生・一時失敗を含む一試行の結果であるのに対し、これは論理要求全体の終端結果だけを示す | 変更成功、既存効果の再利用、確定拒否を途中状態と混同せず判別するため |
| `result_references` | 必須 | `committed`では作成・改版して成立させた、`no_change`では再利用した命題・根拠・状態・関係の有効な業務IDを、種別付きで重複なく一件以上列挙する。`rejected`では空とする。Attempt ID、変更事実ID、存在しないID、Snapshot、異種ID、重複を禁止する | `record_changes`と`state_publication_changes`が監査用の変更事実を指すのに対し、これは呼出側が操作の業務結果を取得する入口である | 新規変更がない結果を含め、呼出側が目的の既存または新規レコードへ到達するため |
| `completed_at` | 必須 | 終端結果が成立した時点で、`requested_at`以後かつ終端化したAttemptの`completed_at`と同じ時点。空値、未完了試行の時点、開始より前の値、確定後の変更を禁止する | Attemptの`completed_at`が一試行の終了時点であるのに対し、これは論理要求全体が終端へ到達した時点である | 操作の確定順序と、最初の要求から終端までの所要期間を追跡するため |
| `executed_by` | 必須 | 終端化したAttemptで確定処理を実行した有効な`ActorReference`。`actor_kind`は`user`、`codex`、`system`のいずれかで通常は`system`とし、未知値、条件に反する`actor_id`、意味判断者への自動置換を禁止する | `decided_by`が内容の決定主体であるのに対し、こちらは終端記録を保存した人または処理であり、終端化したAttemptの`executed_by`と一致する | 判断責任とは別に、成功または拒否を確定した実行主体を監査するため |
| `result_reason` | 条件付き | `no_change`では既存効果を再利用した理由と参照先、`rejected`では違反規則と対象を必須とする。`committed`では結果から自明でない終端上の補足がある場合だけ許可し、それ以外は省略する。空値、定型語だけ、Attempt診断の無目的な複写、不要時の設定を禁止する | `decision_rationale`が操作選択の意味判断、Attemptの`diagnostic`が一試行の障害を示すのに対し、これは新規変更がない、または拒否した終端理由を示す | `no_change`と`rejected`を正常な変更成功から区別し、呼出側が次の行動を判断するため |

`KnowledgeUpdateOperation`は、現在レコードの`AuditMetadata`を代用しない。前者は要求、再試行、前後値、実行主体を記録し、後者は現在のレコード内容を誰がいつ決めたかを記録するため、役割が異なる。

### 4.2 `KnowledgeUpdateAttempt`（保存試行の記録）

一つの操作要求を複数回試せるよう、各試行を上書きしない`KnowledgeUpdateAttempt`として記録する。試行記録が存在するのは、構文上有効な`operation_id`を取得でき、記録用の`attempt_id`を割り当てられた場合だけである。どちらかを満たせない入力は第4.6節の処理診断へ記録し、操作履歴へ混入させない。

| 属性 | 必須性・存在条件 | 意味、許可値、禁止値 | 類似属性との違い | 必要な理由 |
| --- | --- | --- | --- | --- |
| `attempt_id` | 必須 | 一つの保存試行を一意に指す未使用のID。空値、再利用、試行中の変更を禁止する | `operation_id`が再試行をまとめるのに対し、これは一回ごとの実行を分ける | 失敗した試行を上書きせず、実行順と診断へ戻るため |
| `operation_id` | 必須 | 構文上有効な操作ID。空値、不正形式、試行後の変更を禁止する | `attempt_id`とは異なり、同じ論理要求の再試行で同じ値を使う | 一つの意図に属する全試行と確定結果を関連付けるため |
| `request_fingerprint` | 条件付き | 要求の必須意味要素を正規化できた時点で必須。正規化できない構造不備では省略し、推測値や部分値を禁止する | `operation_id`が呼出側の識別値であるのに対し、これは内容が同じかを検証する値である | 同じ操作IDへの別内容と、照合以前の入力不備を区別するため |
| `received_at` | 必須 | この試行を受理した時点。未来の終了時点より後の値を禁止する | Operationの`requested_at`が最初の要求時点であるのに対し、再試行ごとに異なる | 再試行の順序、待ち時間、失敗時点を監査するため |
| `completed_at` | 条件付き | 結果が確定した試行では必須で`received_at`以後。実行中だけ省略し、終了後の省略を禁止する | Operationの同名属性が論理要求全体の終端時点であるのに対し、この値は一試行の終端である | 中断中と終了済みを区別し、所要時間を計算するため |
| `executed_by` | 必須 | 実際に保存を試みた`ActorReference`。許可値は先行スキーマの`user`、`codex`、`system`だけで、未知の主体を禁止する | Operationの`decided_by`は内容の決定者、こちらは保存処理の実行者である | 意味判断の責任と、障害が起きた実行処理を分けて追跡するため |
| `result` | 終了済み試行で必須 | `committed`、`replayed`、`recalculation_required`、`rejected`、`failed`のいずれか。実行中は省略し、他の値を禁止する | Operationの3結果が論理要求全体の終端を表すのに対し、これは途中・再生・一時失敗も表す | 再試行してよい状態と、既存結果を返すだけの状態を判別するため |
| `diagnostic` | 条件付き | `recalculation_required`、`rejected`、`failed`では理由、規則、対象、再開可否を必須とする。`committed`と`replayed`では補足がある場合だけ許可し、秘密値や根拠原文の無目的な複写を禁止する | `decision_rationale`が操作選択の意味上の理由であるのに対し、これは一試行の処理結果を説明する | 拒否原因と再試行可能な障害を、意味判断から分けて是正するため |
| `record_change_ids` | 必須 | この試行の不可分な保存段階で確定した`RecordChange.change_id`の順序付き一覧。変更がなければ空。別試行の変更、重複ID、Snapshotの独自コピーを禁止する | Operationの`record_changes`が全試行を集約するのに対し、この一覧は発生させた試行だけを示す | 部分成功後も、どの試行でどの主変更が確定したかを失わないため |
| `state_publication_change_ids` | 必須 | この試行で確定した`StatePublicationChange.publication_change_id`の順序付き一覧。変更がなければ空。重複IDと独自コピーを禁止する | `record_change_ids`が知識レコードの版変更を指すのに対し、これは現在状態を返せるかの選択変更を指す | 古い状態を利用不可にした試行と、再計算完了を公開した試行を特定するため |
| `resume_cursor` | 条件付き | 安全な途中状態から後続処理が必要な`recalculation_required`、または安全な段階後に失敗した`failed`で必須。再開不要な結果では禁止する | `diagnostic`が人向けの理由であるのに対し、これは同じ操作をどこから再開するかを機械的に示す | 保存済み段階を二重適用せず、未完了段階だけを続けるため |
| `terminal_operation_id` | 条件付き | 新しい終端Operationを作った`committed`、または既存終端を返す`replayed`では必須。終端拒否を作った`rejected`でも必須とし、終端がない途中・失敗・衝突拒否では禁止する | `operation_id`が要求の相関値であるのに対し、これは実際に参照できる確定記録の存在を示す | 試行結果から、新規または既存の終端結果へ曖昧なく到達するため |

一つの不可分な保存段階で論理変更が確定した試行は、その段階で作った変更事実のIDを保持する。特に`recalculation_required`へ到達した試行は、主変更の完全な前後Snapshotを持つ`RecordChange`と、どの状態を利用不可にしたかを持つ`StatePublicationChange`を省略しない。操作全体が完了しない場合でも、既に確定した変更事実を失わないためである。

試行結果は次の5種類とする。

| 試行結果 | 意味 | 論理データへの効果 |
| --- | --- | --- |
| `committed` | 操作全体が終端へ到達した | 論理変更があれば`KnowledgeUpdateOperation.result=committed`、目的の効果が既存なら`result=no_change`を一件作る |
| `replayed` | 同じ`operation_id`と照合値の確定結果が既にあった | 新しい論理変更を作らず、既存の確定結果を返す |
| `recalculation_required` | 主変更は安全に保存されたが、影響する現在状態の再計算が未完了である | 古い状態を利用不可にしたまま、同じ操作IDで再開する位置を残す |
| `rejected` | 前提違反または同じIDへの別要求を検出した | 論理変更を作らない。未使用の操作IDに対する確定拒否なら`KnowledgeUpdateOperation.result=rejected`を一件作る |
| `failed` | 保存領域や処理の一時的失敗で確定結果を作れなかった | 利用可能な部分結果を公開しない。同じ操作IDで再試行できる |

状態再計算を一回の保存処理で完了できない場合は、命題・根拠等の変更と同時に現在状態を`recalculation_required`（再計算が必要）へ切り替える。この時点は「古い状態を返さないための安全な途中状態」であり、操作全体の`committed`ではない。試行履歴へ途中到達と再開位置を残し、同じ`operation_id`で再計算を再開する。全対象が`available`（利用可能）になった後だけ確定記録を`committed`にする。これは公開する5番目の更新操作ではなく、4操作の内部処理段階である。

試行結果と操作全体の結果は、次のとおり対応させる。二つの列挙を機械的に同名変換しないのは、試行だけが途中状態と既存結果の再生を表すためである。

| Attempt結果 | 新しいOperation結果 | 対応規則 |
| --- | --- | --- |
| `committed` | `committed`または`no_change` | 一件以上の変更事実を確定した場合は`committed`、新規変更を作らず既存の目的効果を返す場合は`no_change`にする |
| `replayed` | 作らない | 既存Operationの`committed`、`no_change`、`rejected`のいずれかをそのまま返し、二件目を作らない |
| `recalculation_required` | 作らない | 安全な途中状態であり、同じ操作IDの後続試行が終端化するまでOperationは存在しない |
| `rejected` | `rejected`または作らない | 照合値を計算できた未使用IDの確定拒否だけ`rejected`を作る。入力構造不備または既使用IDとの衝突では作らない |
| `failed` | 作らない | 一時失敗は論理要求の終端結果ではなく、同じ操作IDで再試行できる |

### 4.3 `RecordChange`（変更前後の完全な値）

`RecordChange`は、一つの知識レコード変更について前後の完全な値を保存する、確定後に上書きしない正本である。

| 属性 | 必須性・存在条件 | 意味、許可値、禁止値 | 類似属性との違い | 必要な理由 |
| --- | --- | --- | --- | --- |
| `change_id` | 必須 | 変更事実一件を指す未使用のID。空値、再利用、確定後の変更を禁止する | 業務上の`record_id`ではなく、そのIDに起きた一回の変更を識別する | OperationとAttemptが同じ変更事実を参照し、重複保存を検出するため |
| `originating_attempt_id` | 必須 | この変更を不可分に確定したAttemptのID。別の試行への付替えを禁止する | `operation_id`が再試行全体をまとめるのに対し、実際に保存した一試行を示す | 部分成功がどの試行で成立したかを追跡するため |
| `operation_id` | 必須 | この変更が属する論理要求のID。Attemptの`operation_id`と一致し、確定後の変更を禁止する | `originating_attempt_id`より広い、全再試行共通の相関値である | 操作全体の判断理由と個別変更を結ぶため |
| `record_kind` | 必須 | `assertion`、`evidence`、`derived_state`、`relation`のいずれか。他の値を禁止する | `change_kind`が作成か改版かを示すのに対し、こちらは変更したレコードの種類を示す | Snapshotをどの先行スキーマで検証するか決めるため |
| `record_id` | 必須 | `record_kind`に対応する業務ID。空値、異種レコードのIDを禁止する | `change_id`が変更事実を指すのに対し、これは版を重ねても同じ対象を指す | 同じ対象のRevision系列をまとめるため |
| `change_kind` | 必須 | `created`または`revised`だけを許可し、`deleted`を禁止する | `record_kind`とは異なり、変更前が存在するかを分類する | 変更前Snapshotの存在条件を機械検証し、物理削除を防ぐため |
| `before_revision_id` | 条件付き | `revised`では必須、`created`では禁止。変更直前の現在Revision IDだけを許可する | `after_revision_id`が変更後を指すのに対し、更新競合を検証した元の版を指す | どの版を上書きせず履歴化したか確認するため |
| `before_snapshot` | 条件付き | `revised`では必須、`created`では禁止。`before_revision_id`の完全な値と一致し、差分・要約を禁止する | `after_snapshot`との比較対象であり、現在値の別コピーではない | 訂正前の全値を復元し、変更理由を後から検証するため |
| `after_revision_id` | 必須 | 未使用のRevision ID。`before_revision_id`との同値、再利用、確定後の変更を禁止する | `record_id`を保つ`revised`でも、新しい版を一意に指す | 変更後Snapshotを現在Revisionへ安全に切り替えるため |
| `after_snapshot` | 必須 | `after_revision_id`の完全な値。先行スキーマの全必須属性と存在する全任意属性を含み、差分・要約を禁止する | `before_snapshot`が旧版、こちらが操作で成立した新版である | 操作結果を外部資料なしで再現・検証するため |
| `predecessor_revision_id` | 条件付き | `revised`では必須で`before_revision_id`と同じ値、`created`では禁止する | `before_revision_id`が今回比較した旧値、こちらは新版から旧版へ辿る系譜辺を明示する。同じ値を意図的に別役割で使う | 新Revision単体からも直前Revisionへ辿れ、分岐や黙示統合を検出するため |

Snapshotは、そのレコード種別について[Knowledge論理スキーマ](./logical-schema.md)が要求する全必須属性と、存在する全任意属性を保持する。差分、要約、内容照合値だけで代用しない。履歴Snapshotは不変であり、現在値の訂正後も変更しない。

各業務上のレコードIDには、作成後、通常の取得対象となる現在Revisionをちょうど一件だけ持たせる。`created`では変更後Revisionが最初の現在Revisionになり、`revised`では変更前Revisionが履歴だけになって変更後Revisionが現在Revisionになる。この切替と変更後Snapshotの保存は不可分に行う。履歴の保存方式や現在Revisionを指す列名は後続が決めてよいが、現在Revisionが0件または複数件になる途中状態を外部へ公開してはならない。

物理削除を表す`deleted`は設けない。失効や現在値からの除外は、Revisionと現在状態選択または`supersedes`関係で表し、旧Snapshotを残す。特に`Evidence.raw_content`（利用者本人が示した加工前の内容）を履歴から除去しない。

### 4.4 `StatePublication`（現在状態を公開できるかの選択情報）

一つの`KnowledgeAssertion`につき、外部から参照できる現在状態を次のどちらか一件で表す。この情報は知識状態の9番目の値ではなく、計算結果を現在値として利用してよいかを示す処理上の選択である。

| 属性 | 必須性・存在条件 | 意味、許可値、禁止値 | 類似属性との違い | 必要な理由 |
| --- | --- | --- | --- | --- |
| `assertion_id` | 必須 | 存在する一つの`KnowledgeAssertion`を指す。空値と別種IDを禁止する | `current_state_id`が計算結果を指すのに対し、こちらは状態を評価する命題を固定する | 一命題につき現在選択一件という制約を検証するため |
| `publication_revision_id` | 必須 | 選択情報の一版を指す未使用のID。再利用と上書きを禁止する | `current_state_id`は知識状態レコードのIDであり、こちらは「返してよいか」という選択の版である | 再計算要求と公開再開の前後へ遡るため |
| `publication_status` | 必須 | `available`または`recalculation_required`だけを許可し、8種類の知識状態や未知値を禁止する | `DerivedKnowledgeState.status`が知識評価を表すのに対し、これは評価結果を現在値として利用できるかを表す | 再計算未完了を第9の知識状態へ誤変換しないため |
| `current_state_id` | 条件付き | `available`では必須で、同じ`assertion_id`の存在する`DerivedKnowledgeState`一件を指す。`recalculation_required`では禁止する | `publication_status`が利用可否、こちらが利用可能な場合の具体的な計算結果を示す | 古い状態や別命題の状態を現在値として返さないため |
| `operation_id` | 必須 | この選択版を成立させた論理要求のID。空値と別操作への付替えを禁止する | `publication_revision_id`が選択版自体、こちらは変更理由と試行系列への相関を示す | どの知識変更が状態を無効化・再公開したか追跡するため |
| `changed_at` | 必須 | この選択版が成立した時点。直前版より前の値を禁止する | 状態の`calculated_at`が計算時点であるのに対し、こちらは公開選択の成立時点である | 再計算完了と外部公開の順序を検証するため |

`StatePublicationChange`は選択情報の変更前後を保存する、確定後に上書きしない正本である。

| 属性 | 必須性・存在条件 | 意味、許可値、禁止値 | 類似属性との違い | 必要な理由 |
| --- | --- | --- | --- | --- |
| `publication_change_id` | 必須 | 選択情報の変更事実一件を指す未使用のID。空値、再利用、確定後の変更を禁止する | `publication_revision_id`が選択情報の一版を指すのに対し、こちらは版を切り替えた一回の出来事を指す | AttemptとOperationから同じ変更前後へ到達し、重複保存を検出するため |
| `originating_attempt_id` | 必須 | この変更を不可分に確定したAttemptのID。別試行への付替えを禁止する | `operation_id`が再試行全体をまとめるのに対し、実際に保存した一試行を示す | 公開停止または再開がどの試行で成立したかを追跡するため |
| `operation_id` | 必須 | この変更が属する論理要求のID。Attemptの`operation_id`と一致し、確定後の変更を禁止する | `originating_attempt_id`より広い、全再試行共通の相関値である | 知識変更の判断理由と公開選択の変更を結ぶため |
| `assertion_id` | 必須 | 変更対象の`StatePublication.assertion_id`と同じ、存在する命題ID。空値、別命題、別種IDを禁止する | 選択版のIDではなく、どの命題の現在状態を選ぶ情報かを固定する | 一命題につき現在選択一件という制約を変更前後で検証するため |
| `change_kind` | 必須 | `created`または`revised`だけを許可し、`deleted`を禁止する | `publication_status`が利用可否を示すのに対し、こちらは選択情報に旧版があるかを分類する | 変更前Snapshotの存在条件を機械検証し、公開選択の物理削除を防ぐため |
| `before_publication_revision_id` | 条件付き | `revised`では必須、`created`では禁止。切替直前の現在`publication_revision_id`だけを許可する | `after_publication_revision_id`が切替後を指すのに対し、競合検証に使った元の版を指す | 古い選択を上書きせず、どの版から切り替えたか確認するため |
| `before_snapshot` | 条件付き | `revised`では必須、`created`では禁止。変更前Revisionの完全な`StatePublication`と一致し、差分・要約を禁止する | `after_snapshot`との比較対象であり、現在値の独自コピーではない | どの状態を公開していたか、または再計算待ちだったかを復元するため |
| `after_publication_revision_id` | 必須 | 未使用の`publication_revision_id`。変更前との同値、再利用、確定後の変更を禁止する | `assertion_id`を保つ改版でも、変更後の選択版を一意に指す | 外部へ返す現在選択を一件へ安全に切り替えるため |
| `after_snapshot` | 必須 | 変更後Revisionの完全な`StatePublication`。第4.4節の必須属性と存在する条件付き属性を含み、差分・要約を禁止する | `before_snapshot`が旧選択、こちらが操作で成立した新選択である | 再計算要求または公開再開の結果を外部資料なしで再現するため |

`created`では変更前RevisionとSnapshotを持たず、`revised`では両方を必須とする。変更後Revisionと完全なSnapshotは常に必須である。知識レコードの版変更と現在状態選択の変更を別一覧にしつつ、どちらも同じ厳密さで変更前後へ戻れるようにするためである。

同じ命題へ現在の`StatePublication`を二件公開しない。選択情報も同時更新の対象になるため、操作要求の`expected_revisions`へ想定`publication_revision_id`を含める。

`recalculation_required`を`no_evidence`や`uncertain`へ読み替えない。前者はまだ計算結果を利用できない状態、後二者は根拠を評価した後の正式な知識状態であり、意味が異なるためである。

### 4.5 変更前後情報の正本と参照・集約規則

変更前後の正本は、不変な`RecordChange`と`StatePublicationChange`だけである。Attemptは自分が確定した変更事実のIDを参照し、Operationは同じ操作IDに属する全Attemptの参照を成立順に一度ずつ集約する。したがって、OperationとAttemptが互いに別のSnapshotを所有したり、再試行時に同じ変更事実を作り直したりしてはならない。

物理保存上、読取り性能のためOperationやAttemptへ前後Snapshotを埋め込む場合でも、それは正本の複製であり、参照先の`change_id`または`publication_change_id`、Revision ID、完全なSnapshotと同一でなければならない。不一致はどちらかを選んで補正せず、履歴整合性違反として拒否する。`no_change`と`rejected`のOperation、`replayed`のAttemptは新しい変更事実を参照しない。

### 4.6 入力不備を記録する境界

知識更新履歴へ入れる最小条件は、記録用の`attempt_id`を割り当てられ、構文上有効な`operation_id`を入力から取得できることである。`operation_id`が欠落、空、形式不正である場合、または障害で`attempt_id`自体を割り当てられない場合は、`KnowledgeUpdateAttempt`、`KnowledgeUpdateOperation`、変更事実を一件も作らない。要求を操作系列へ安全に相関できないためである。

この境界より前の不備は、KnowledgeStoreの論理履歴とは別の処理診断へ、受信時点、秘密値を含まない要求ダイジェスト、違反項目、処理名を記録する。根拠原文や不正なIDを正規値として保存してはならない。処理診断は知識変更の証拠でも操作IDの予約でもない。

有効な`operation_id`は取得できたが、必須項目不足によりRequest fingerprintを計算できない場合は、照合値なしの`KnowledgeUpdateAttempt.result=rejected`だけを作り、Operationを作らず、その操作IDを予約しない。修正後の要求は同じIDで初めて照合可能な試行として受理できる。照合値まで計算できた後の意味・前提違反は未使用IDなら`Operation.result=rejected`として終端化し、既使用IDとの衝突は先行Operationを保持して拒否Attemptだけを追加する。

## 5. 全操作に共通する事前条件

CLIは変更を利用可能にする前に、次をすべて確認する。

1. `operation_id`、操作種別、変更理由、決定主体、要求時点、対象、想定Revisionが存在する。
2. Codexが命題の同一性、操作選択、根拠採用、影響する命題の範囲を決定し、`decision_rationale`に説明している。未決の意味候補をCLIが選ばない。
3. 同じ`operation_id`の確定結果が存在しない。存在する場合は第10章の再試行規則へ進む。
4. 現在値のRevision IDが`expected_revisions`と一致する。異なる場合は、古い読み取りに基づく上書きをせず競合として拒否する。
5. 新規作成予定の業務IDとRevision IDは存在せず、変更後の主識別子と候補キーが先行スキーマを満たす。
6. 変更後の全参照先が同じ`KnowledgeStore`に存在するか、同じ不可分な変更内で作成される。
7. `KnowledgeRelation`の接続種別、向き、重複、自己参照、循環、適用条件が先行する関連契約を満たす。
8. `Evidence`の出典、分類、強さと、`DerivedKnowledgeState`の8状態・根拠一覧・理由が先行する導出契約を満たす。
9. 物理削除、連鎖削除、必須参照の空値化、旧参照の新命題への自動付替えを要求していない。
10. 状態再計算の影響範囲を決め、変更と同時に新状態を公開するか、全旧状態を`recalculation_required`へ切り替える計画がある。

機械検証で確定できる違反は、違反した対象・規則・既存候補・循環経路を返して拒否する。意味上の重複や同一性が未確定なら、候補を返してCodexの判断を求め、推測して保存しない。

新規または改版後の`Evidence`は、`source`（出典参照）とその`originator`（原文・元コード・判断を作成または提示した主体）を必須とし、`source.originator.actor_kind=user`でなければならない。これは知識を評価される一人の利用者本人が出典作成者であることを示す先行スキーマの条件である。作成者不明、第三者作成、`actor_kind=codex`または`system`、AI生成内容だけの出典は禁止する。第三者やAIの内容を利用者が読んだ事実だけではEvidenceにせず、利用者本人が別に示した説明、訂正、判断をEvidenceにする場合は、その本人の発言・成果物を指す別の`source`を使う。この条件は`create`、`attach-evidence`、`supersede`で新しいEvidenceを作る場合と、`revise`でEvidenceの記録誤りを直す場合のすべてに適用する。

## 6. 4操作の選択表

| 操作 | 選ぶ条件 | IDの扱い | 主な変更 | 選んではならない場合 |
| --- | --- | --- | --- | --- |
| `create` | 採用価値のある根拠に対応する命題と意味的に同じ既存命題がない | 新しい`assertion_id`を作る | 命題、根拠、状態、必要な関係を作る | 同じ評価対象の既存命題がある、採用できる根拠がない |
| `attach-evidence` | 同じ評価対象の既存命題があり、新しい採用根拠を加える | 既存`assertion_id`を保ち、新しい`evidence_id`を作る | 根拠を追加し、状態を再計算する | 命題自体の意味・適用対象を訂正する、根拠が論理重複である |
| `revise` | 同じ評価対象のIDを保ったまま、表現・適用条件・誤記録を訂正できる | 対象の業務IDを保ち、新Revisionを作る | 変更前後Snapshotを残し、状態を再計算する | 旧内容と新内容を別々に評価・検索すべき、統合・分割・時代差の置換である |

文字列の完全一致または不一致だけでは操作を選ばない。たとえば、同じ意味を別の語順へ直す場合は不一致でも`revise`であり、同じ文でも適用製品版を分けて独立評価すべき場合は`supersede`になり得る。Codexが意味と評価単位を判断し、CLIは指定された結果の形式を検証する。

### 6.1 対象種別、4操作、変更種別の固定表

次表の`created`は新しい業務IDとRevisionを作ること、`revised`は同じ業務IDの新Revisionを作ること、`unchanged`は既存レコードを保持することを表す。`StatePublication`は知識レコードではなく現在状態の利用可否を制御するため、`RecordChange`ではなく`StatePublicationChange`へ記録する。

| 対象種別 | `create` | `attach-evidence` | `revise` | `supersede` | 境界と必要な理由 |
| --- | --- | --- | --- | --- | --- |
| `KnowledgeAssertion` | 1件`created` | `unchanged` | 対象1件`revised` | 旧1件以上は`unchanged`、新1件以上を`created` | 命題の同一性を保つ訂正だけ改版し、分割・統合・時代差は旧IDを残して新IDにするため |
| `Evidence` | 1件以上`created` | 論理重複でなければ1件以上`created` | 保存時の転記・分類・出典位置等の記録誤りだけ対象1件`revised` | 旧根拠は`unchanged`、新命題へ採用する本人根拠だけ新IDで`created` | 過去の観測を消さず、利用者による後日の訂正を旧根拠の改版と混同しないため |
| `DerivedKnowledgeState` | 再計算結果を`created` | 再計算結果を`created` | 直接改版せず再計算結果を`created` | 影響する新旧命題ごとの再計算結果を`created` | 導出物を手修正せず、使用根拠と8状態の計算結果を一つの不変な版として残すため |
| `KnowledgeRelation` | 必要な関係だけ`created` | `unchanged` | 同じ始点・終点・`relation_kind`を保つ記録訂正だけ`revised` | 新→旧の`supersedes`と必要な新関係を`created`、既存関係は`unchanged` | 関係の`revise`は許可するが、始点、終点、関係種別の変更は論理的に別の接続なので改版を禁止し、新関係として扱うため |
| `Concept` | 対象外・`unchanged` | 対象外・`unchanged` | 対象外・`unchanged` | 対象外・`unchanged` | 検索用索引語は4操作の更新対象ではなく、既存関係の参照先として読むだけだからである。作成・改版は別Ownerの契約に従う |
| `KnowledgeEpisode` | 対象外・`unchanged` | 対象外・`unchanged` | 対象外・`unchanged` | 対象外・`unchanged` | 会話・作業範囲はEvidenceの出典文脈として読み、知識更新操作から書き換えると根拠の成立範囲が後から変わるため |
| `StatePublication` | 新命題分を作成し、必要に応じて`recalculation_required`から`available`へ改版 | 影響命題分を改版 | 影響命題分を改版 | 新命題分を作成し、影響する既存命題分を改版 | 第9の知識状態を作らず、古い導出状態の公開停止と新状態の公開開始を追跡するため |

`KnowledgeUpdateOperation`、`KnowledgeUpdateAttempt`、`RecordChange`、`StatePublicationChange`は4操作の業務対象ではなく、実行に伴って作る履歴・制御記録である。そのため上表の対象レコード変更数へ数えず、それぞれ第4章の存在条件で作成する。表にない`deleted`、`DerivedKnowledgeState`の`revised`、`Concept`または`KnowledgeEpisode`の変更を4操作へ追加してはならない。

## 7. 操作別の事前条件と事後条件

次表は、各操作の正常な変更結果について、操作直前、再計算を分ける場合だけ現れる安全な途中状態、操作全体の確定後を対応付ける論理遷移表である。`A`は命題、`E`は根拠、`S`は導出状態、`P`は現在状態選択、`R`は関係を表す。この略記が必要なのは、表を読みやすくしつつ、どの種類のレコードを作成・保持・改版するかを省略しないためである。

| 操作 | 操作直前 | 一回で確定する場合 | 再計算を分ける場合の安全な途中状態 | 操作全体の確定後 | 保持する履歴 |
| --- | --- | --- | --- | --- | --- |
| `create` | 同じ評価対象の`A`が存在しない | 新`A`、1件以上の新`E`、必要な新`R`、新`S`、`P=available(新S)`を不可分に作る | 新`A`、新`E`、必要な新`R`を作り、`P=recalculation_required`として状態を返さない | 新`S`を作り、`P=available(新S)`へ切り替える | 全新規レコードの変更後Snapshotと、途中状態を含む試行履歴 |
| `attach-evidence` | 既存`A`、既存`E`集合、`P=available(旧S)`または既に再計算中 | 同じ`A`へ新`E`を加え、新`S`と`P=available(新S)`を不可分に作る | 新`E`を加え、影響する全`P`を`recalculation_required`へ切り替える | 新`S`を作り、影響する全`P`を`available(新S)`へ切り替える | 旧`A`、旧`E`、旧`S`を残し、新`E`、新`S`、選択変更の前後を残す |
| `revise` | 対象IDの現Revisionと、影響する`P` | 同じ業務IDの新Revision、新`S`、`P=available(新S)`を不可分に作る | 同じ業務IDの新Revisionを作り、影響する全`P`を`recalculation_required`へ切り替える | 新`S`を作り、影響する全`P`を`available(新S)`へ切り替える | 対象の変更前後Snapshot、旧`S`、選択変更の前後を残す |
| `supersede` | 1件以上の旧`A`と、その旧`E`・旧`S`・旧参照 | 1件以上の新`A`、必要な新`E`、新→旧の`R`、新`S`、影響する`P`を不可分に作る | 新`A`、必要な新`E`、新→旧の`R`を作り、影響する全`P`を`recalculation_required`へ切り替える | 新`S`を作り、影響する全`P`を`available(新S)`へ切り替える | 全旧レコードと旧参照を残し、新規レコードと選択変更の前後を残す |

目的の論理効果が既にある`no_change`では、上表の変更後へ新しいレコードやRevisionを追加せず、既存結果への参照だけを返す。前提違反による`rejected`または不可分な保存段階の確定前に起きた`failed`では、操作直前の利用可能な論理状態を変えない。主変更と`recalculation_required`への切替まで確定した後の一時失敗だけは、安全な途中状態を保って同じ操作IDで再開する。

### 7.1 `create`（新しい命題を作る）

事前条件:

1. 完了済み`KnowledgeEpisode`（根拠候補を評価する会話・作業範囲）から、採用価値のある`Evidence`が1件以上決まっている。採用できる根拠がない場合は「更新しない」とし、命題だけを作らない。
2. Codexが候補命題と既存命題を意味・`scope`・`temporal`で比較し、同じ評価対象が存在しないと判断している。
3. 新しい`assertion_id`、`evidence_id`、必要な`state_id`と`relation_id`が未使用である。
4. 同じ不可分な変更内で、命題を指す全根拠と状態の参照が成立する。

成功後の条件:

- 新しい`KnowledgeAssertion`と、少なくとも一件の新しい`Evidence`が存在する。
- 根拠に基づく`DerivedKnowledgeState`一件が`available`になるまで操作を確定しない。再計算を分割する場合、その間は`recalculation_required`であり状態を返さない。
- 作成した全レコードの変更前Snapshotは存在せず、変更後Snapshotと操作IDを履歴へ残す。
- 同じ意味の既存命題を新しく作らない。比較後に既存命題が見つかった場合は拒否し、採用根拠を追加するなら`attach-evidence`を選び直す。

### 7.2 `attach-evidence`（既存命題へ根拠を加える）

事前条件:

1. 対象`KnowledgeAssertion`が存在し、想定Revisionと一致する。
2. Codexが新しい根拠を対象命題または関連命題の状態判断へ採用できると決めている。
3. `Evidence.source.episode_id`と出典が存在し、`Evidence.source.originator.actor_kind=user`である。作成者不明、第三者作成、Codex・AI生成単体の出典を禁止する。
4. `(assertion_id, source.source_locator, source.fragment_locator, evidence_kind, stance, knowledge_report)`が一致する重複候補を確認している。

成功後の条件:

- 論理重複でなければ新しい`Evidence`を追加し、既存の命題・旧根拠を変更しない。
- 同じ論理的観測が既に存在する場合は新しい根拠を作らず`no_change`とし、既存`evidence_id`を返す。件数を増やして根拠の強さを上げない。
- 影響する命題の現在状態を全件再計算し、新しい状態だけを`available`にする。再計算中は旧状態を返さない。
- 利用者本人による訂正は、旧`Evidence`を書き換えず、新しい`evidence_kind=correction`の根拠として追加する。訂正前と訂正後の根拠を状態履歴から辿れるようにする。

### 7.3 `revise`（同じIDの新しい版を作る）

`revise`を使えるのは、同じ業務IDが指す評価対象、観測事実、または関係の論理的同一性を保ち、保存済みの表現・適用条件・分類の誤りを訂正する場合である。対象は`KnowledgeAssertion`、`Evidence`、または同じ始点・終点・`relation_kind`を保つ`KnowledgeRelation`に限定する。`DerivedKnowledgeState`は直接`revise`せず、根拠と命題から再計算した新しい`state_id`へ置き換える。`Concept`と`KnowledgeEpisode`は対象外である。

事前条件:

1. 対象レコードと想定Revisionが存在する。
2. Codexが変更前後を同じ論理的対象として扱える理由を記録している。
3. `KnowledgeAssertion`の`statement`、`language`、`scope`、`temporal`を直す場合、新旧を別々の命題として残す必要がない。
4. `Evidence`を直す場合、保存時の転記、分類、出典位置、適用条件等の記録誤りを直す操作である。利用者本人が後から以前の内容を訂正した場合は、旧根拠を`revise`せず`attach-evidence`で訂正根拠を追加する。
5. `KnowledgeRelation`を直す場合、始点、終点、`relation_kind`を保ち、`scope`、`temporal`、監査情報等の記録誤りを直す操作である。始点、終点、関係種別のいずれかを変える要求は拒否し、必要な新関係として再判断する。
6. 変更によって意味的重複となる候補、参照先、影響状態を確認している。

成功後の条件:

- 業務上のレコードIDを保ち、変更前Revisionを上書きせず新Revisionを作る。
- 履歴には変更前後の完全なSnapshot、直接の変更前Revision ID、操作ID、変更理由を残す。
- `AuditMetadata.created_at`と`created_by`を保ち、`updated_at`と`updated_by`だけを今回の内容決定へ合わせる。
- 影響する現在状態を再計算し、旧状態を現在値として返さない。
- 新旧が別の時点・製品版で独立して評価できる、または一件を複数へ分割・複数を一件へ統合する場合は成功させず、`supersede`を選び直す。

### 7.4 `supersede`（旧命題を残して新命題へ置き換える）

事前条件:

1. 旧`KnowledgeAssertion`が1件以上存在し、すべて想定Revisionと一致する。
2. 新しい`KnowledgeAssertion`を1件以上作る。新旧で同じ`assertion_id`を使わない。
3. Codexが、訂正、製品版変更、意味の分割・統合等により、新旧を別の評価対象として残す理由を記録している。
4. 新しい命題から古い命題へ必要な`supersedes`関係を列挙し、自己参照、論理重複、全経路の循環がない。
5. 新命題の状態に使う根拠を決めている。旧命題の`Evidence.assertion_id`を新命題へ自動付替えしない。同じ出典断片を新命題の根拠としても採用する場合は、新しい`Evidence`を作り、旧根拠も残す。

成功後の条件:

- 旧命題、旧命題の全Revision、旧根拠、旧状態、旧参照を物理削除または上書きしない。
- 新しい各命題と、新→旧方向の`supersedes`関係が不可分に作られる。
- 複数旧命題から一新命題への統合、一旧命題から複数新命題への分割を許可する。各新旧接続の理由を追跡できる。
- 旧命題を指す既存参照を新命題へ自動付替えしない。後続検索は`supersedes`を辿って新旧双方を取得できる。
- 新旧および意味上影響する命題の状態を再計算する。置換しただけで旧状態を自動的に`outdated`へ変更せず、先行する8状態導出契約に従う。

## 8. 状態再計算と不可分性

### 8.1 影響範囲

操作前に、少なくとも次を状態再計算候補へ含める。

- 追加・訂正した`Evidence.assertion_id`の命題
- `KnowledgeAssertion`の本文、適用範囲、時点を変更した命題
- 変更した根拠または命題を、構成要素、前提、矛盾、旧版として使い得る命題
- 新規または変更した`supersedes`を含む関係によって、導出経路が変わり得る命題

既存状態の`evidence_ids`に既に含まれる命題だけへ限定しない。新しい根拠で初めて競合や前提が生じる場合を見落とすためである。

### 8.2 同じ保存処理で再計算できる場合

命題・根拠・関係の変更、新しい`DerivedKnowledgeState`、`StatePublication=available`への切替を一つの不可分な変更として確定する。途中の新状態や、旧状態と新状態の二件を外部へ公開しない。

### 8.3 再計算を分ける場合

命題・根拠・関係の変更と同じ不可分な変更で、全影響命題の現在状態選択を`recalculation_required`にする。古い状態は履歴として残すが、現在状態として返さない。再計算失敗時も古い状態を暗黙に`available`へ戻さず、同じ`operation_id`で再開する。

全影響命題について新しい状態を作り、先行する導出契約と参照制約を検証した後、一つの不可分な変更で`available`へ切り替える。その後にだけ操作全体を`committed`として確定する。

## 9. 同一性、Revision、時間の不変条件

1. 業務上のIDは「どの評価対象または観測を指すか」を表し、Revision IDは「そのIDのどの時点の完全な値か」を表す。二つを兼用しない。
2. 作成済みの各業務上のIDには現在Revisionがちょうど一件あり、通常の取得と次の更新の`expected_revisions`はその一件を使う。旧Revisionは履歴取得で明示された場合だけ返す。
3. `revise`の変更後Revisionは、直接の変更前Revisionを一件指す。並行する二つの変更を黙って統合しない。
4. 新規作成のRevisionには変更前Revisionがない。`supersede`による命題間の新旧は、Revisionの前後ではなく`KnowledgeRelation.relation_kind=supersedes`で表す。
5. `AuditMetadata.created_at`は業務上のレコードが最初に成立した時点、`updated_at`は現在Revisionの内容を最後に決めた時点、操作の`completed_at`は一組の変更が確定した時点である。役割が異なるため一つの時点で代用しない。
6. 各変更後Revisionの監査時点は、その操作の確定時点より後にならない。変更前Revisionの監査時点より前にもならない。
7. `TemporalMetadata.valid_until`はその時点を含まない。`supersede`を作った時点を、旧命題の`valid_until`へ自動複写しない。世界上の有効期間と保存操作時点は別だからである。
8. 履歴Snapshotと操作履歴は確定後に上書きしない。誤った履歴記録を直す場合も、元記録を残して訂正履歴を追加する。

## 10. 再試行、重複、同時更新

### 10.1 同じ操作IDの再試行

| 状況 | 結果 |
| --- | --- |
| 同じ`operation_id`、同じRequest fingerprintで確定結果がある | 新しい変更を作らず`replayed`とし、既存結果を返す |
| 同じ`operation_id`、同じ照合値で未完了の安全な途中状態がある | 保存済みの試行履歴から同じ操作を再開する |
| 同じ`operation_id`、異なる照合値 | 操作IDの衝突として拒否し、どちらも追加変更しない |

Request fingerprintへ含める論理要素は、操作種別、対象ID、新規ID、変更後の論理値、想定Revision、根拠・関係の一覧、意味判断理由である。属性順や一覧順に意味がない項目は正規化してから計算する。正確なバイト表現はJSON契約の担当が決めるが、これらの意味要素を省略しない。

既に別のRequest fingerprintで使われた`operation_id`は、その先行操作が完了済みか未完了かにかかわらず後着要求へ再割当てしない。後着要求は拒否した試行として提示された照合値と衝突先を記録するが、先行する`KnowledgeUpdateOperation`を上書きせず、同じIDで二件目の確定記録も作らない。後着内容を実行するには、Codexが先行結果を読み直し、新しい`operation_id`で意味判断からやり直す。

### 10.2 新しい操作IDだが論理効果が重複する場合

- 同じ根拠候補キーかつ同じ意味上の観測なら、`attach-evidence`は`no_change`として既存根拠を返す。
- 同じ`KnowledgeRelation`論理キーなら、新しい関係を作らず既存関係を返す。
- 意味的に同じ`KnowledgeAssertion`がある場合、`create`は拒否し、必要なら`attach-evidence`へ選び直す。
- 件数が増えても意味が増えない重複を、多数決、根拠強度、検索順位へ利用しない。

### 10.3 同時更新競合

現在Revisionが`expected_revisions`と違う場合は拒否する。この方式は、読み取った版がまだ現在かを保存直前に比較し、一致した場合だけ変更する仕組みである。後から到着した処理が先に確定した変更を上書きすることを防ぐ。

競合後は、Codexが新しい現在値と履歴を読み直し、意味上の操作選択と影響範囲を再判断する。別内容へ変える場合は新しい`operation_id`を使う。CLIが二つの意味判断を自動統合しない。

## 11. 拒否時・失敗時の事後条件

### 11.1 拒否

- 命題、根拠、状態、関係、現在状態選択を一件も変更しない。
- 違反規則、対象ID、現在Revision、重複候補または循環経路を返す。
- 意味判断が必要なら、CLIの推測結果ではなく判断対象候補を返す。
- 未使用の操作IDに対する確定拒否では操作履歴と試行履歴を残し、`record_changes`を空とする。既使用IDとの衝突では、先行する操作履歴を変えず、拒否した試行に衝突先と提示された照合値を残す。

### 11.2 一時的な失敗

- 一つの不可分な保存段階の途中結果を外部へ公開しない。
- 状態再計算を分けた操作で主変更が既に確定している場合は、現在状態を`recalculation_required`のまま保ち、古い状態を返さない。
- 失敗試行を上書きせず、同じ操作IDで安全に再開できる位置と理由を記録する。
- 正本の`Evidence`と全履歴Snapshotを保持する。

## 12. 許可・拒否の具体例

| 状況 | 操作と結果 | 理由 |
| --- | --- | --- |
| 新しい会話から採用根拠を得たが、同じ意味の命題が存在しない | `create`を許可 | 新しい評価対象、根拠、状態を一組で作るため |
| 命題本文の語順だけを、意味を変えず正規化し直す | `revise`を許可 | 評価対象の同一性を保ったまま新Revisionにできるため |
| 旧製品版の命題を残し、現行版の異なる挙動を別に評価する | `supersede`を許可 | 旧版と現行版を別IDで検索・評価し、新→旧の系譜を残すため |
| 同じ出典断片から同じ分類の根拠を再登録する | `attach-evidence`を`no_change`にする | 同じ観測の件数を増やしても知識根拠は増えないため |
| 利用者本人が以前の説明を明示的に訂正した | 旧根拠を`revise`せず、訂正根拠を`attach-evidence`する | 過去の観測事実と訂正後の観測事実を両方残すため |
| 保存時に根拠の出典位置を誤記したことが判明した | `Evidence`を`revise`する | 利用者の後日の訂正ではなく、同じ観測の記録誤りを版管理して直すため |
| `supersedes`作成後に旧命題と旧根拠を削除する | 拒否 | 新旧系譜と正本の根拠が失われるため |
| 再計算に失敗したため旧状態を現在値へ戻す | 拒否 | 古い結果を正式な8状態として誤公開するため |
| 同じ操作IDへ別の変更後値を指定する | 拒否 | 一つの操作IDから二つの論理結果が生じ、再試行判定が壊れるため |

### 14.2 Issue #74 `L3-M2-S3`への引継ぎ

- Update Decision Markdown（Codexが更新判断を人と後続処理へ渡す文書）には、操作種別、対象・新規ID、意味的同一性の判断、採用根拠、変更理由、想定Revision、影響する命題、非永続化判断を含める。
- 再試行可能な決定では`operation_id`とRequest fingerprintの材料を含め、対象種別と`created`・`revised`・`unchanged`の予定を第6.1節に合わせる。
- 採用根拠には出典を作成した利用者本人の`ActorReference`を含め、作成者不明、第三者、AI生成単体を採用対象へ入れない。
- 「採用価値のある根拠なし」「意味判断未完了」「既存効果と重複」は、それぞれ更新しない理由を区別する。
- 4操作以外の公開操作を追加せず、状態再計算は選んだ操作の内部段階として扱う。

### 14.3 Issue #100 `L5-M1-S5`への引継ぎ

- retry（同じ操作の再試行）は同じ`operation_id`とRequest fingerprintを使い、restart（中断後の再開）も同じ未完了操作を引き継ぐ。
- reroute（別処理へ経路を変える）でも操作IDを保ち、別内容へ変える場合だけ新しい操作として再判断する。
- stop（停止）時は、不可分な保存段階の途中を公開せず、主変更後なら状態を`recalculation_required`のまま保つ。
- `KnowledgeUpdateAttempt`の5結果と`KnowledgeUpdateOperation`の3結果を第4.2節どおりに分け、AttemptとOperationには変更前後Snapshotを重複する正本として保存せず、第4.5節の変更事実IDを参照する。
- `operation_id`を取得できない要求は第4.6節どおり操作履歴へ入れず、処理診断と再試行可能な操作系列を混同しない。
- Budget（処理へ使える時間・回数等の上限）が尽きても、重複作成、古い状態の再公開、履歴削除を許可しない。

本書を引き渡せることと、各後続作業が直ちに着手できることは同じではない。各後続は、固定された作業間接続表にある本書以外の全着手依存と、該当するGateを別に確認しなければならない。
