# Episode入力・Source Reference・Evidence候補採否境界設計書

## 1. この文書の目的と適用範囲

Knowledge Acquisition（利用者本人が示した会話・作業から、知識を判断するための候補を取り出す処理）は、入力された一まとまりの会話または作業を読み、後続のKnowledge Update（既存の知識記録と比較して保存・更新を判断する処理）が評価できる候補を作る。この処理が、AIによる説明や単なる質問を利用者本人の知識として誤って扱わないために、入力として受け入れる範囲、出典を追跡する方法、Evidence候補（採用済み根拠になり得る候補）の採否をここで定める。

本書は、入力の観測と採否だけを担当する。採用候補を独立したKnowledge Candidate（後続が評価する知識候補）へ整形し、L1の属性へ対応付ける仕事はL3-M1-S2が担当する。候補をMarkdown（見出しと本文で構成する受渡し文書）へ並べ、候補なし・評価不能を後続へ伝える契約はL3-M1-S3が担当する。既存知識との同一性、保存するか、更新するかの判断も本書の対象外であり、L3-M2が担当する。

## 2. 固定入力と責務境界

この設計の原典はIssue #1である。原典は、根拠が観測されていないことを利用者本人が知らないことと同一視せず、AIが説明しただけでは知識を増やさず、Evidence（採用済みの根拠）を正本にするよう求める。計画固定版Commit `9bf911b9122bf4ec51ec48312cc310de29bfcdff` のTask Mapと接続台帳は、本書をL3-M1-S1だけが変更する単一Owner成果物とし、L3-M1-S2、L3-M1-S3、L5-M3-S1、L6-M3-S6へ読み取り専用で渡すことを定める。決定016は、入力不足と、十分に評価したが保存候補がない状態を区別することを追加で確定した。

直接の先行入力であるKnowledge論理スキーマは、以下をすでに定める。本書は意味を選び直さず、処理手順へ適用する。

- `KnowledgeEpisode`（評価対象の会話・作業範囲）は、前後の発言、編集、コマンド実行結果を含めて評価する完了済みのまとまりである。断片だけでは後続の訂正や文脈を失うため必要である。
- `SourceReference`（出典への参照）は、根拠候補の原文がどの会話またはファイルのどの位置にあるかを表す。採否を後から検証し、同じ断片の重複採用を避けるため必要である。
- `Evidence`（採用済みの根拠）は、利用者本人の知識を判断するために採用した加工前の発言、説明、推論、コード、訂正、技術判断である。候補と区別することで、観測しただけの情報を知識と誤認しない。

## 3. 入力として受け入れるEpisode

### 3.1 必須の入力

入力は、完了済みの`KnowledgeEpisode`一件と、その範囲内の原文断片および各断片の出典情報である。完了済みであるとは、評価対象に含める後続発言・訂正・作業結果が確定し、`ended_at`（一括評価してよい終了時点）が決まっている状態をいう。途中の会話や作業を確定的に評価すると、直後の訂正を取り逃がすため、終了時点がないEpisodeを候補採否の対象にしてはならない。

| 入力要素 | 意味と許可する値 | 必要な理由と禁止する状態 |
| --- | --- | --- |
| `episode_id` | 評価対象の会話・作業範囲を一意に指す識別子。空値、別Episodeとの共有を禁止する | すべての候補を同じ前後関係へ戻せるようにするため必要である。断片だけでは、後の訂正や同じ言葉の別意図を確認できない。 |
| `episode_kind` | `conversation`（発言中心の会話）または`task`（編集・コマンド実行を含む作業）のいずれか | 参照すべき原文の種類と位置の表し方を選ぶため必要である。両方を同時に示す値、未分類値を禁止する。 |
| `source_locator` | 会話・作業全体の元データへ再び到達する参照先。空値、候補の要約、断片だけを指す参照、別Episodeの参照先を禁止する | 根拠断片だけで判断できない場合に、Episode全体の前後関係へ戻るため必要である。Episode内の断片を指す`SourceReference.source_locator`とは、全体か断片かという対象範囲が異なる。 |
| `started_at` | 会話・作業の開始時点 | 評価範囲と出来事の順序を確定するため必要である。空値、推定時刻、終了時点より後の時刻を禁止する。 |
| `ended_at` | Episodeを一括評価できる終了時点。`started_at <= ended_at`を必須の時系列制約とする | 後続の訂正を含めた範囲を固定し、開始前に終了した矛盾するEpisodeを除外するため必要である。未終了、推定時刻、開始時刻だけの入力を禁止する。 |
| 原文断片 | 利用者本人の発言、説明、推論、コード、訂正、技術判断、または採否に必要な前後文脈 | 命題へ整理する前の内容を残し、採否理由を検証するため必要である。要約だけ、候補IDだけ、Codexの結論だけを原文の代用にしてはならない。 |
| `SourceReference` | 第3.2節に定める出典形式、取得先、断片位置、作成・提示者、Episodeへの参照 | 原文の場所・作成者・文脈を失わず、AIや第三者の内容を本人の知識として採用しないため必要である。 |

`audit`（作成・更新の記録）は、`KnowledgeEpisode`を保存するレコードが誰によりいつ作成・更新されたかを追跡するための必須属性である。ただし、本書はEpisodeを受け入れて候補採否を行う境界だけを定め、保存レコードの作成・更新・履歴の方式は後続のL1-M1-S4が定める。そのため、候補採否の追加必須入力には含めず、渡されたEpisodeが先行スキーマに従って保存・検証されることを前提にする。これにより、採否処理が保存履歴のOwnerを重複して持たない。

### 3.2 Source Reference（出典への参照）の確認

`SourceReference`は、内容が知識を示すかという意味ではなく、原文をどこから得たかを表す。内容の観測形式は後述のEvidence候補分類で判断するため、両方を一つの分類へ混ぜない。

| 属性 | 許可・禁止と意味 | 必要な理由 |
| --- | --- | --- |
| `source_kind` | `message`は会話内の発言、`file`はファイルから取得した原文だけを許可する。コード、訂正、自己申告という内容の意味を値にしてはならない | 会話とファイルでは再取得・表示・位置指定の方法が違うため必要である。内容分類を混ぜると、同じコードを会話に貼った場合とファイルから読んだ場合を追跡できない。 |
| `source_locator` | 元の会話またはファイルを再取得できる参照先。空値、候補の要約、別の候補IDを禁止する | 採否を再確認できる元データを特定するため必要である。 |
| `fragment_locator` | 発言番号、行範囲など、`source_locator`内の具体的位置。出典全体が一つの原文断片なら省略できるが、大きな出典から対象範囲を一意にする必要がある場合は必須とする。空文字列、候補の要約、別の候補IDを禁止する | 一つの長い発言・ファイルから別の行為を混同せず、同一断片の重複採用を検出するため必要である。一方、出典全体が一つの断片なら不要な位置情報を作らず、先行スキーマの条件付き属性と整合させる。 |
| `episode_id` | 入力のEpisodeと同一の識別子 | 原文を評価時の前後関係へ戻すため必要である。別EpisodeのIDを禁止する。 |
| `originator.actor_kind` と `originator.actor_id` | `actor_kind`は`user`（利用者本人）、`codex`（意味判断を行うAI）、`system`（定型的な自動処理）のいずれか。外部読込みという操作を主体値にしてはならない。`actor_id`は`user`では省略し、`codex`または`system`では設定で固定した処理名を必須とする | 原文を作成・提示した主体と、保存処理を実行した主体を混同せず、AI・自動処理の出典を具体的に追跡するため必要である。一人に固定した利用者本人へ不要な識別子を持たせない。 |
| `captured_at` | 出典を取得した時点。空値、推定時刻、原文の作成時刻だけを入れることを禁止する | 原文をいつ取得・観測したかと、根拠が示す時点の前後関係を検証するため必要である。 |
| `content_digest` | 元データの内容が同じか機械的に確認できる場合だけ設定する内容照合値。照合値を計算できない、または元データが変化しないことを別に確認できる場合は省略できる。空文字列、候補の要約、原文そのものを照合値として入れることを禁止する | 参照先の内容変更や、同じ参照先を別内容として取り違えることを検出するため必要である。常時必須にすると照合不能な取得を不当に評価不能にするため、条件付き属性とする。 |

`originator.actor_kind=user`である原文だけを、利用者本人の知識を示すEvidence候補として採用できる。現在の会話・作業の外にあるファイルでも、出典情報から利用者本人が作成したと確認できるなら候補にできる。作成者不明、第三者、Codex、または自動処理が作成・提示した内容は、読み込んだだけでは候補にしない。ただし、その内容について利用者本人が別の断片で説明、訂正、技術判断を示した場合は、その利用者本人の断片を候補にできる。

## 4. Evidence候補の採否手順

### 4.1 採否の前提

Evidence候補は、知識候補でも採用済み根拠でもない。利用者本人がある命題を知っているか、知らないと明示したか、または理解を訂正したかを判断する材料になり得る原文断片である。候補化は保存を意味せず、後続で命題との対応、強さ、既存知識との関係を評価できる状態にするだけである。

Codexが原文の意味を読み、以下の順で採否する。CLI（知識を保存・検索する決定論的なコマンドライン処理）は、意味的な採否を決めない。

1. Episodeの終了時点と、各原文断片の`SourceReference`が第3章を満たすか確認する。不足なら、十分な入力を評価した結果ではないため、候補なしにせず「評価不能」とする。
2. 断片の作成・提示者が利用者本人か確認する。本人以外の原文だけなら不採用とする。ただし、本人が示した別断片は独立に評価する。
3. 原文が、利用者本人の説明、推論、コード、訂正、知識についての明示申告、技術判断のいずれかを実際に示すか確認する。該当すれば候補として採用する。
4. 単なる質問、説明依頼、情報への露出、Codexの説明への短い受領、挨拶、操作依頼だけなら不採用とする。質問した事実から不知を推定してはならず、AIの説明を原文として採用してはならない。
5. 同じ出典断片に複数の行為がある場合は、主な観測行為を一つ選ぶ。別々の行為を根拠として残す必要があるときだけ、`fragment_locator`で範囲を分けて別候補にする。候補が重複する場合は、後続へ同じ観測を二重に渡さない。

### 4.2 採用する候補の観測形式

候補にする原文は、次の六分類のいずれか一つへ仮分類する。この分類は、後続がEvidenceの属性へ正規化する際に原文の主な行為を失わないために必要である。値の確定とL1属性への写像はL3-M1-S2が担当する。

| 観測形式 | 候補にする条件 | 候補にしない近い例と境界 |
| --- | --- | --- |
| 説明 | 利用者本人が仕組み、意味、条件を自分の言葉で示す | AIの説明を読んだだけ、引用だけ、説明してほしいという依頼は含めない。前提から結論への過程が中心なら推論を選ぶ。 |
| 推論 | 利用者本人が前提から結論へ至る考え方を示す | 結論だけの自己申告、明示的な訂正、技術選択はそれぞれ自己申告、訂正、技術判断と区別する。 |
| コード | 利用者本人が作成・提示したコードそのものが理解を示す | 本人以外が書いたコード、AIが提案したコード、単にファイルを開いた事実は含めない。コードに添えた説明は必要なら範囲を分ける。 |
| 訂正 | 利用者本人が以前の説明・判断の誤りを明示して正す | 単なる補足や曖昧な言い換えは訂正にしない。誤りを直す行為が明確なら、説明や推論を含んでも訂正を優先する。 |
| 知識についての明示申告 | 利用者本人が知っている、知らない、経験がある、概念を認識していると直接述べる | 質問、確認依頼、説明依頼だけは不知の申告にしない。短い概念認識は理解の証明ではない。 |
| 技術判断 | 利用者本人が設計・実装・運用上の選択と理由または適用条件を示す | Codexが決めた選択を本人が受領しただけの内容、作業を依頼しただけの内容は含めない。明示的な誤りの修正なら訂正を優先する。 |

### 4.3 必ず不採用にする原文

次の原文は、知識候補を作る材料に見えてもEvidence候補に採用しない。不採用理由を残すのは、保存候補がないことと、入力が足りず評価できなかったことを後続が区別するためである。

| 不採用の種類 | 該当する状態 | 不採用にする理由 |
| --- | --- | --- |
| AIのみの内容 | Codexまたは自動処理が説明・要約・コード・判断を出しただけで、利用者本人の別の説明等がない | AIが説明したことは利用者本人が理解・保持したことを示さないため。 |
| 質問・依頼のみ | 「これは何ですか」「説明してください」など、本人の知識内容を示さない発言 | 質問には不知、確認、深掘り、他者への説明依頼など複数の意図があり、不知の根拠にできないため。 |
| 露出のみ | 記事、ファイル、AI回答を本人が見た・受け取っただけ | 見たことと理解・保持したことは異なるため。 |
| 本人以外が作成した原文 | 作成者不明、第三者、Codex、自動処理のファイル・発言を読み込んだだけ | 他者またはAIの知識を利用者本人の知識として誤登録しないため。 |
| 非知識的な会話・操作 | 挨拶、受領、進捗確認、ファイル操作、コマンド実行の事実だけ | 命題を知っているかの判断材料がなく、不要な候補を蓄積しないため。 |

## 5. 三つの結果を混同しない境界

L3-M1-S3が最終の受渡し表現を定める前提として、本書では採否結果を次の三つに分ける。後続の再試行・終了をL5が正しく制御できるようにするため、正常な候補なしを入力不備と扱わない。

| 結果 | 成立条件 | 意味と後続への影響 |
| --- | --- | --- |
| 候補あり | 必須入力が揃い、利用者本人の原文から一件以上のEvidence候補を採用できた | L3-M1-S2へ、原文と出典を失わない候補集合を渡す。保存・更新の決定はまだしていない。 |
| 正常な候補なし | 必須入力が揃い、Episode全体を評価したが、採用条件を満たす原文が一件もない | 「利用者本人が何も知らない」ではない。L3-M1-S3の`no-candidate`表現へ渡し、L5は通常終了または次のEpisode処理を選べる。 |
| 評価不能 | Episode未終了、必須の出典情報がない、原文を取得できない、入力範囲が切断されて前後関係を確認できないなど、採否を安全に実施できない | 正常な候補なしと区別する。L3-M1-S3の入力不足表現へ渡し、再取得・再試行・停止を選ぶ責務はL5に残す。 |

この三分類は、知識状態の八分類とは別の分類軸である。ここで扱うのは入力評価の可否と候補の有無であり、`known`（知っている）や`reported_unknown`（本人が知らないと明示した）など、命題に対する利用者本人の状態を決めない。候補が一件あることだけから、知識状態を決めてはならない。

## 6. 後続への受渡しと未担当事項

本書から後続へ渡す最小入力は、Episode識別子と終了時点、原文断片、完全な`SourceReference`、採用・不採用の理由、前節の結果分類である。これにより、後続は原文へ戻って検証でき、同じ候補を二重に作らず、入力不足を正常終了と誤解しない。

| 直接の後続Task | 今回渡せるもの | 今回の成果物を渡せるか | そのTaskが今すぐ開始できるか |
| --- | --- | --- | --- |
| L3-M1-S2 | Episode入力、出典追跡、採用候補と不採用境界 | はい。S2がL1-M1後に先行して作る正規化仕様を、本書の入力・出典・採否境界と矛盾なく確定・統合するための読取り入力として渡せる | はい。着手依存はL1-M1だけであり、S1が未統合でも先行着手できる。ただし、本書はS2の正規化仕様を確定してMergeする完了・Merge依存である。入力観測と正規化の境界を揃えないまま完成扱いにしないため必要である。 |
| L3-M1-S3 | 三分類と、候補・出典を失わない受渡し対象 | はい。本書が確定すれば、候補あり・正常な候補なし・評価不能のMarkdown契約を開始できる | はい。本書の確定が着手条件であり、S2との両方を必要とする。 |
| L5-M3-S1 | Episodeの必須入力、入力不足と正常な候補なしの違い | はい。L5は起動・再試行・終了を判断するための入力境界として利用できる | いいえ。固定Task Map上、L5-M1とL3-M1-S3も着手条件であるため、本書だけでは全依存を満たさない。 |
| L6-M3-S6 | Episode入力・出典追跡・候補採否の境界 | はい。後続Adapterが受け取るproducer契約の読取り入力になる | いいえ。固定Task Map上、ほかのL3・L4 producer契約とL6-M3-S4も着手条件であるため、本書だけでは全依存を満たさない。 |

## 7. 完全性確認

- 利用者本人の原文だけを候補にする条件、AIの説明・質問・露出だけを不採用にする条件、本人作成が確認できる外部成果物を候補にできる条件を明記した。
- `source_kind`（取得形式）と、原文が示す行為の分類を分離した。これにより、出典の場所と知識を示す内容を混同しない。
- 候補あり、十分な評価後の正常な候補なし、入力不足による評価不能を分けた。後続が再試行と通常終了を誤らないために必要である。
- Candidateの正規化、受渡しMarkdown、既存知識との比較、保存・更新操作、L5による再試行・終了の制御は、本書で決めず担当Taskへ残した。
