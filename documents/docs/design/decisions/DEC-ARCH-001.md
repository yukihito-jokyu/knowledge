# DEC-ARCH-001: Knowledge Store の物理永続化・配置方式

- **Status:** decided
- **Level:** L3
- **論点:** Knowledge CLI が管理する個人知識データを、どの物理永続化・配置方式で初期提供するか。

## なぜ今決める必要があるか

FEAT-001 は Assertion、Evidence、Relation、Temporal 情報、Index、履歴を管理する基盤であり、保存・同期・秘密情報・Migration の境界は後続 Feature の実装契約と運用責任に影響する。

## 選択肢

### A. ローカル専用の埋め込み SQLite（推奨）

- **利点:** 単一の主ユーザー、個人会話 Evidence、自己完結する CLI と整合する。トランザクション・履歴・Migration を単一環境で扱え、外部運用を要しない。
- **欠点:** 複数端末同期・共同利用・中央バックアップは初期提供しない。
- **影響:** まずローカル利用を前提に設計し、将来の同期は論理 CLI 契約を保った追加機能とする。

### B. ローカルのドキュメント／ファイルベース Store

- **利点:** データの可読性と手動編集性が高い。
- **欠点:** Relation・時点差分・検索 Index・履歴の整合性、同時更新、Migration の管理が複雑になる。
- **影響:** CLI が高い整合性を保証する設計に追加の制約が必要になる。

### C. リモート Database／サービス

- **利点:** 複数端末同期、共有、バックアップを初期から扱える。
- **欠点:** 認証・認可、ネットワーク可用性、個人 Evidence のプライバシー、運用コストを新たに決める必要がある。
- **影響:** System Boundary と Security Policy が拡大し、初期設計と実装範囲が増える。

## 決定

**A. ローカル専用の埋め込み SQLite** を採用する。

## 決定理由

単一の主ユーザー、個人会話 Evidence、自作 Knowledge CLI という初期要件を、外部運用・認証・ネットワーク可用性の追加なしに満たす。将来の同期や共有は、JSON の論理契約を維持する追加機能として扱う。

## 当初の適用範囲

- Knowledge Store はローカルの SQLite に保存する。
- Knowledge CLI は唯一のデータアクセス経路とする。
- 初期提供では複数端末同期・共同利用・リモート共有を扱わない。
- Evidence および履歴の保全は SQLite のトランザクション境界で扱う。

## 推奨（決定前の比較）

**A. ローカル専用の埋め込み SQLite** を推奨していた。Issue #175 の「継続的に技術キャッチアップを行う単一の主ユーザー」「自作 Knowledge CLI」「個人会話 Evidence」を最小の運用・プライバシー境界で満たし、将来は JSON 論理契約を保って同期機能を追加できるためである。
