# DEC-FEAT-013: Conversation / Task Episode の取り込み境界

> **状態:** `decided`  
> **Decision Level:** L3 — Cross Feature / Contract  
> **決定者:** 人間  
> **対象Feature:** FEAT-004

## 論点

Knowledge Acquisitionへ渡すConversation / Task Episodeを、どのCodex連携または利用者操作から受け取るかを決める。

## 用語

- **会話（Conversation）:** あなたとCodexがやり取りした一連のメッセージ。たとえば、技術についてあなたが説明したり、考え方を述べたり、Codexが質問へ応じたりする流れを指す。
- **作業（Task）:** あなたがCodexと一緒に行った一つの作業。たとえば、コードの実装、レビュー、障害調査、設計の検討を指す。
- **エピソード（Episode）:** 今回の対象にする会話または作業の一区切り。会話全体、ある作業依頼から完了まで、あるいは利用者が選んだ一部、といった範囲になり得る。どの範囲を一区切りとするかが、このDecisionで決める内容である。
- **Knowledge Acquisition（知識候補の抽出）:** エピソードのうち、あなた自身が技術を説明した、理由を述べた、コードを書いた、以前の理解を訂正した、といった箇所から、「あなたの知識の根拠になり得る内容」を候補として抜き出す処理。候補をそのまま保存することではない。
- **Knowledge Update（知識の更新判断）:** 抽出された候補と、すでに保存されている知識を照合し、新規に残す、既存の根拠を追加する、表現を訂正する、旧知識を置き換えとして残す、または何もしない、のいずれかを決める処理。
- **取り込み:** 会話または作業のどの範囲を、上記の「知識候補の抽出」に渡す対象にするかを選ぶこと。AIの説明、記事を読んだこと、質問だけを知識として保存する意味ではない。

たとえば、あなたが「このコードでは再試行が必要なのは、通信失敗が一時的な場合だけだから」と説明したなら、その説明は候補になり得る。一方、Codexが同じ説明をしただけ、あなたが記事を読んだだけ、または「再試行とは何ですか」と質問しただけでは候補にしない。

## なぜ今決める必要があるか

入力境界によって、取り込み開始条件、対象データ、利用者の同意、エピソードの安定識別子、再実行時の重複防止、失敗時の再試行、およびCodex workflowの入出力契約が変わる。未決定のまま候補抽出や更新を詳細化すると、未承認の公開・横断契約を設計してしまう。

## 事実

- UI-002は要件整理でL3の未決定事項として登録され、FEAT-004へ影響すると明記されている。
- REQ-015は「意味のあるConversation / Task Episodeの終了後」の候補抽出を求める。
- BR-005はAI説明、閲覧、評価、要約、質問だけからの更新を禁止する。
- Knowledge Storeの変更はKnowledge Updateが決定し、Knowledge CLIだけが実行する。

## 選択肢

### A. 明示操作による取り込み

会話または作業の終了後、ユーザーが明示操作で対象エピソードをKnowledge Acquisitionへ渡す。

- 利点: 利用者の意図・同意が明確で、意図しない更新を避けやすい。エピソードの範囲を利用者が選べる。
- 欠点: 知識更新を希望するたびに操作が必要で、取り込み忘れが起こり得る。
- 影響: 明示操作と、操作により渡されるエピソードの一回分の境界を定義する。自動履歴読取・自動更新は含めない。

### B. エピソード終了時の自動取り込み

Codexが会話または作業の終了を検知すると、自動で対象エピソードをKnowledge Acquisitionへ渡す。

- 利点: 操作負担がなく、継続的な更新を逃しにくい。
- 欠点: 終了の定義、対象範囲、同意、誤検知、重複、会話内容のプライバシーを横断的に設計する必要がある。
- 影響: Codex lifecycle連携、明示的な除外または同意方針、安定したエピソードID、再実行規約が必要になる可能性が高い。

### C. 保存済み履歴からの後選択取り込み

保存済みの会話・作業履歴を一覧または連携から参照し、後で選んだエピソードを取り込む。

- 利点: 任意の過去エピソードを対象にでき、範囲を確認してから取り込める。
- 欠点: 履歴の保存場所・アクセス権・検索・選択UIまたは連携APIという追加の横断契約が必要になる。
- 影響: FEAT-004の範囲を越えた履歴所有・Codex連携・プライバシー設計の検討が必要になる。

## 決定

**Bを限定して採用する。** ユーザーが技術記事URLを渡してCodexへ評価を依頼し、CodexがそのURLに対するReading Value Assessmentの内容を完成させた時点で、当該URL評価ワークフローの会話・作業をKnowledge Acquisitionへ自動的に渡す。Assessment本文はまだ会話へ返さず、Knowledge Updateまで同じWorkflowで実行した後に変更せず返す。

初期の推奨だったAは採用しない。人間が明示した利用タイミングにより、対象が任意会話ではなくURL評価ワークフローに狭く固定されたため、Bの一般的な自動取り込みに伴う履歴全体の監視・選択UI・別作業の誤取り込みは生じない。

これは任意の通常会話、別目的の作業、または保存済み履歴全体を自動取り込みする決定ではない。対象はURL評価を依頼した一連のやり取りだけである。

候補抽出の対象となり得るのは、そのワークフロー内のユーザー由来の技術的説明・推論・コード・訂正・自己申告・技術判断である。Codexだけの説明、URL記事の内容、記事の閲覧、評価結果、要約、ユーザーの質問だけはEvidence候補にしない。

Reading Value Assessmentの内容を完成できなかった場合は候補抽出・更新判断を開始しない。候補抽出後も、Knowledge Updateが既存Knowledgeとの照合により`create`、`attach-evidence`、`revise`、`supersede`、`skip`のいずれかを決め、候補があること自体は保存を意味しない。
